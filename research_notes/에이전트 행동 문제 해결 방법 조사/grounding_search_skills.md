# Grounding agent decisions: research-first, skill use, fact verification (Claude Code, as of 2026-11-04)

Scope note: Official docs pages (code.claude.com, platform.claude.com) were fetched on 2026-11-04 and reflect current versions (they reference Claude Code v2.1.2xx-v2.1.305 and Opus 5.5). GitHub issues and blogs are dated individually. Anything from 2024-2025 is marked [older].

## Q1. Tool search / deferred tools: settings, alwaysLoad, and can WebSearch/WebFetch stay always loaded?

### Takeaway
For MCP tools there are documented controls (`ENABLE_TOOL_SEARCH`, server-level `alwaysLoad`, per-tool `_meta["anthropic/alwaysLoad"]`), but there is NO documented setting to make the built-in WebSearch/WebFetch load upfront; an issue asking for it was closed "not planned". The practical, non-pruning workaround is a SessionStart hook (matchers `startup`/`resume`/`compact`) that tells the model to batch-load them via `ToolSearch("select:WebSearch,WebFetch")` at the start, plus server instructions/keywords so search finds the right tools.

### Cited Findings
- "Tool search keeps MCP context usage low by deferring tool definitions until Claude needs them. Only tool names and server instructions load at session start" — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- "Tool search is enabled by default: MCP tools are deferred and discovered on demand." — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- `ENABLE_TOOL_SEARCH` values: (unset) "All MCP tools deferred and loaded on demand"; `true` same; `auto` "Threshold mode. Tools that would otherwise be deferred load upfront while their definitions total under 10% of the context window. At 10% or more, tool search turns on"; `auto:N` custom percentage; `false` disables. — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- Server-level: "If a server's tools should always be visible to Claude without a search step, set `alwaysLoad` to `true` in that server's configuration. The server's tools then load into context regardless of the `ENABLE_TOOL_SEARCH` setting. Use this for a small number of tools that Claude needs on every turn" — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- "Setting `alwaysLoad: true` also makes startup wait for the server's tools, capped at the standard 5-second connect timeout" — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- Per-tool (server author side): "To control how one of your server's tools loads, set `"anthropic/alwaysLoad"` in that tool's `_meta` object." `"alwaysLoad": false` on the server entry keeps even author-marked tools deferred (v2.1.287+). — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- Denying ToolSearch flips to upfront loading of all MCP tools: "If you deny `ToolSearch` or leave it out of `--tools`, MCP tools load upfront instead" — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp) (not viable with hundreds of connector tools).
- Server instructions help discovery: "Server instructions help Claude understand when to search for your tools, similar to how skills work." Also: "put the words Claude would search for near the start" of tool descriptions. — [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)
- The official tools reference describes ToolSearch only as "Searches for and loads deferred tools when tool search is enabled" and does not document which built-ins are deferred. — [Tools reference](https://code.claude.com/docs/en/tools-reference)
- Built-ins ARE deferred in practice: issue #54716 (opened Apr 29, 2026, v2.1.123) lists deferred built-ins incl. "`WebFetch`, `WebSearch`, and `AskUserQuestion`" and asks for an opt-out/allowlist setting such as `"deferredTools": {"mode": "allowlist", "include": ["TodoWrite", "WebSearch", "WebFetch"]}`. No maintainer reply; closed "not planned" for inactivity Jul 1, 2026; locked Sep 11, 2026. — [GitHub #54716](https://github.com/anthropics/claude-code/issues/54716)
- Workaround in #54716 (yasyf, Jul 12, 2026): a SessionStart hook injecting `additionalContext` telling the model to batch-load frequently used deferred tools with `ToolSearch("select:...")` on its first turn; yasyf also suggested an `alwaysLoad`-style option for built-ins. — [GitHub #54716](https://github.com/anthropics/claude-code/issues/54716)
- Issue #90085 (opened Aug 27, 2026, v2.1.221, open, no maintainer reply): "Since v2.1.69, built-in tools beyond the small always-loaded set... are deferred and only become callable after ToolSearch loads them"; reporter says subagents can't reach them and "The tool is silently absent from the subagent's inventory: no error, no warning". A Sep 23, 2026 commenter contradicts: general-purpose and custom subagents did get ToolSearch and loaded WebFetch. — [GitHub #90085](https://github.com/anthropics/claude-code/issues/90085)
- SessionStart hook capabilities: matchers include "`startup`, `resume`, `clear`, `compact`, `fork`"; "`hookSpecificOutput.additionalContext` adds context for Claude"; "Only `type: "command"` and `type: "mcp_tool"` hooks are supported." SubagentStart also accepts `additionalContext`. — [Hooks reference](https://code.claude.com/docs/en/hooks)
- API-level guidance from Anthropic: "Keep your 3–5 most frequently used tools non-deferred so Claude can call them without searching first." and "Add a system prompt section describing available tool categories" — [Tool search tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)
- Rationale for tool search: "Claude's ability to pick the right tool degrades once you exceed 30–50 available tools." — [Tool search tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)
- Observation in this very research session (2026-11-04, Claude desktop): WebSearch and WebFetch appeared only as names in the deferred-tool list among several hundred connector tool names and had to be loaded via `ToolSearch select:WebSearch,WebFetch` before use (direct observation, not a web source).

### Inferences
- Without pruning, the only official lever is on MCP tools. Since WebSearch/WebFetch are built-ins, the realistic options are (a) a SessionStart hook with matchers `startup|resume|compact` whose `additionalContext` instructs "first call ToolSearch select:WebSearch,WebFetch" (and also names relevant skills), and (b) a SubagentStart hook doing the same for subagents. Because `compact` is a SessionStart matcher, this also re-applies after compaction.
- An alternative path to "always loaded web search" is an MCP search/fetch server configured with `alwaysLoad: true` — this keeps a search capability visible on every turn without touching built-ins (not tested; inferred from docs).
- `ENABLE_TOOL_SEARCH=auto` would not help here: hundreds of connector tools far exceed 10% of context, so tool search would stay on.

### Gaps
- No official doc lists the set of always-loaded vs. deferred built-in tools or offers a setting to undefer a built-in; whether the API-level "loaded tools stay available after search" also persists across Claude Code compaction is not documented.
- Whether the #90085 subagent problem still reproduces on current versions is disputed in the thread itself.

## Q2. How skill triggering works and what improves it

### Takeaway
The model sees a listing of skill names + (budgeted) descriptions and decides on its own; descriptions are capped at 1,536 chars each, and when the listing exceeds ~1% of context the least-used skills lose their descriptions. Official levers: raise `skillListingBudgetFraction` / `SLASH_COMMAND_TOOL_CHAR_BUDGET`, demote low-value skills to `"name-only"` (not prune), front-load keywords, measure triggering with plugin evals / skill-creator, preload skills into custom subagents via `skills:`, re-invoke after compaction, and move must-always rules into hooks (including skill frontmatter hooks). Practitioner data shows prompt-level forcing hooks give only ~40–50% activation.

### Cited Findings
- `description`: "Claude uses this to decide when to apply the skill... Put the key use case first: the combined `description` and `when_to_use` text is truncated at 1,536 characters in the skill listing" — [Skills docs](https://code.claude.com/docs/en/skills)
- `when_to_use`: "Additional context for when Claude should invoke the skill, such as trigger phrases or example requests. Appended to `description`" — [Skills docs](https://code.claude.com/docs/en/skills)
- Budget/dropping: "The listing always contains every skill name, but if you have many skills, Claude Code drops some descriptions to fit the listing's character budget, which removes the keywords Claude needs to match your request. The budget scales at 1% of the model's context window. When the listing overflows, Claude Code drops descriptions starting with the skills you invoke least" — [Skills docs](https://code.claude.com/docs/en/skills)
- Fix: "To raise the budget, set the `skillListingBudgetFraction` setting (for example, `0.02` = 2%) or the `SLASH_COMMAND_TOOL_CHAR_BUDGET` environment variable to a fixed character count. To free budget for other skills, set low-priority entries to `"name-only"` in `skillOverrides`" ; per-entry cap configurable via `skillListingMaxDescChars`. — [Skills docs](https://code.claude.com/docs/en/skills)
- Diagnostics: "Run `/doctor` for an estimate of the listing's context cost"; "When the listing exceeds its budget, Claude Code also writes a warning to the debug log, visible with `--debug`"; `/skill-doctor` finds unused skills. — [Skills docs](https://code.claude.com/docs/en/skills)
- `skillOverrides` values `"on"`, `"name-only"`, `"user-invocable-only"`, `"off"`; "Plugin skills are not affected by `skillOverrides`. Manage those through `/plugin` instead." — [Skills docs](https://code.claude.com/docs/en/skills)
- Silent failure mode: "A field name must match the table exactly... Claude Code ignores a field it doesn't recognize without reporting an error." and malformed YAML loads the skill "with empty metadata, so `/skill-name` still works but Claude can't match against your `description`." Use `claude plugin validate .claude/skills` (v2.1.233+). — [Skills docs](https://code.claude.com/docs/en/skills)
- Measurement: "If the skill ships in a plugin, you can measure how often it triggers across realistic prompts... write an eval case with a `tool_used: Skill` grader and run it with `claude plugin eval` after each description change." Skill-creator's "Description tuning: generates should-trigger and should-not-trigger prompts, measures the hit rate, and proposes description edits" — [Skills docs](https://code.claude.com/docs/en/skills)
- Compaction: "Claude Code re-attaches the most recent invocation of each skill after the summary, keeping the first 5,000 tokens of each. Re-attached skills share a combined budget of 25,000 tokens... older skills can be dropped entirely after compaction" — [Skills docs](https://code.claude.com/docs/en/skills)
- Troubleshooting "Claude stops following a skill": "Claude skipped a rule that must hold every time: move the rule into a hook... define the hook in the skill's `hooks` frontmatter. That hook applies from the time the skill is invoked until the session ends." and "The conversation was compacted: invoke the skill again to restore its full content... put the most important instructions near the top of `SKILL.md`." — [Skills docs](https://code.claude.com/docs/en/skills)
- Subagents: "Each subagent starts with a fresh, isolated context window. It doesn't see your conversation history, the skills you've already invoked"; `skills` field: "The full content of each listed skill is injected into the subagent's context at startup, up to the first 32 distinct names... without it, the subagent can still discover and invoke project, user, and plugin skills through the Skill tool"; "Built-in agents don't preload skills." — [Sub-agents docs](https://code.claude.com/docs/en/sub-agents)
- "Explore and Plan start without your CLAUDE.md files and the git status snapshot to keep research fast and inexpensive. Other built-in and custom subagents load both, unless you set `omitClaudeMd`" — [Sub-agents docs](https://code.claude.com/docs/en/sub-agents)
- `disable-model-invocation: true` skills cannot be preloaded into subagents. — [Skills docs](https://code.claude.com/docs/en/skills)
- Over/under-triggering guidance: "If your prompts were designed to reduce undertriggering on tools or skills, these models might now overtrigger. The fix is to soften any aggressive language. Where you might have said 'CRITICAL: You MUST use this tool when...,' you can use more normal prompting" — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Practitioner measurement: Scott Spence (orig. Nov 6, 2025 [older]; update Sep 13, 2026): "Don't rely on 'autonomous activation' - use hooks to explicitly invoke skills when trigger words appear"; the simpler all-skills hook got "4/10 globally, 5/10 locally" across 20 fresh sessions; "The key (I found) is making it an INSTRUCTION, not a suggestion." — [scottspence.com](https://scottspence.com/posts/claude-code-skills-dont-auto-activate)
- User-reported triggering failures (mirrored, original GitHub pages not verified): #9716 skills not recognized; #20986 matching description ignored; #32184 "recall=0% in headless mode (claude -p)" (Mar 2026); #15136 closed Mar 6, 2026. — [claudeissues.com #20986](https://claudeissues.com/issue/20986-claude-ignores-skill-triggers-even-when-user-request-clearly-matches-skill-descr), [#32184](https://claudeissues.com/issue/32184-skill-auto-triggering-recall-0-in-headless-mode-claude-p-regardless-of-descripti)

### Inferences
- "Not pruning" is compatible with `skillOverrides: "name-only"` for rarely needed skills plus a raised `skillListingBudgetFraction`: every skill stays installed and invocable; only description space is reallocated toward the skills that matter. Plugin skills (most of this user's list) are not covered by `skillOverrides`, so raising the budget fraction is the main lever there.
- For general-purpose / Explore / Plan subagents (no preloaded skills, Explore/Plan no CLAUDE.md), the documented fix is custom subagent definitions in `.claude/agents/` with `skills:` lists, plus a SubagentStart hook injecting a short "relevant skills + load WebSearch/WebFetch" note.
- Because compaction keeps only the first 5,000 tokens per skill within 25k total, a SessionStart(`compact`) hook that reminds the model which skills were active and to re-invoke them is the closest automatic fix; the docs' manual fix is to re-invoke.
- Prompt-level "forced" activation hooks are probabilistic (~45% in one practitioner test); only hooks that act deterministically (deny/block/inject content) are reliable.

### Gaps
- No official activation-rate numbers for skill auto-invocation were found.
- No documented hook that can programmatically invoke a skill; `SessionStart` has a `reloadSkills` field but its semantics were not retrieved.

## Q3. Research/practice on "research before acting", retrieval-first agents, grounding and hallucination mitigation

### Takeaway
Anthropic's own guidance is (1) explicit "investigate before answering" prompting, (2) just-in-time retrieval via lightweight identifiers, and (3) for anything that must happen every time, a hook rather than CLAUDE.md, with a check the agent can run (tests/Stop hook) for "done" claims. Academic work frames search decisions as a calibration problem (over-search vs under-search) and finds confidence-based "search only when unsure" works only if overconfidence is corrected; package-hallucination studies show memory-only decisions about libraries remain a real risk.

### Cited Findings
- Anthropic sample prompt: "Never speculate about code you have not opened. If the user references a specific file, you MUST read the file before answering. Make sure to investigate and read relevant files BEFORE answering questions about the codebase. Never make any claims about code before investigating unless you are certain of the correct answer" — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Research prompting: "Encourage source verification: Ask Claude to verify information across multiple sources." and sample "develop several competing hypotheses. Track your confidence levels in your progress notes to improve calibration." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Caveat on self-verification prompts: on Claude Opus 5 "verification instructions carried over from prompts tuned for earlier models can cause over-verification... remove these instructions rather than rewriting them." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Context engineering (Sep 29, 2025 [older]): agents "maintain lightweight identifiers (file paths, stored queries, web links, etc.)" and "dynamically load data into context at runtime using tools"; Claude Code is a hybrid: "CLAUDE.md files are naively dropped into context up front" while glob/grep "retrieve files just-in-time." — [Anthropic engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Claude Code best practices: "If something has to happen every time, make it a hook, a deny rule, or a managed setting. `CLAUDE.md` is for guidelines, and Claude is allowed to decide a guideline doesn't apply." — [Best practices](https://code.claude.com/docs/en/best-practices)
- "If you keep adding emphasis to a `CLAUDE.md` line and Claude still misses it, that's a sign the line belongs in a hook." — [Best practices](https://code.claude.com/docs/en/best-practices)
- "Claude said it was done and it wasn't quite, usually because it had no way to check its own work." and "Claude stops when the work looks done. If it has nothing to run that tells it whether the work actually is done, 'looks done' is all it has to go on." Stop hook exit code 2 sends Claude back to work; cap of eight consecutive blocks (`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`). — [Best practices](https://code.claude.com/docs/en/best-practices)
- "A `prompt` or `agent` hook asks another model to decide, so it isn't deterministic either. For real enforcement, use a `command` or `http` hook" — [Best practices](https://code.claude.com/docs/en/best-practices); agent hooks "spawn a subagent that can use tools like Read, Grep, and Glob to verify conditions before returning a decision. Agent hooks are experimental" — [Hooks reference](https://code.claude.com/docs/en/hooks)
- `/verify` bundled skill: "has Claude build and run the app and look at the result." — [Best practices](https://code.claude.com/docs/en/best-practices)
- Adaptive retrieval & overconfidence (arXiv 2402.11457, 2024 [older]): retrieve only when the model lacks knowledge, but LLM overconfidence must be reduced for this to work. — [arXiv 2402.11457](https://arxiv.org/pdf/2402.11457v2)
- "To Search or Not to Search" (arXiv 2602.03304, WWW 2026) defines over-search and under-search as the two failure modes and diagnoses search decisions with counterfactual interventions. — [arXiv 2602.03304](https://arxiv.org/html/2602.03304)
- AdaSearch (arXiv 2512.16883, Dec 2025): search agents' search decisions measured against an oracle; reduces unnecessary calls. — [arXiv 2512.16883](https://arxiv.org/abs/2512.16883v1) (summary from search results, paper not fully read)
- KBM (arXiv 2411.06207 [older]): confidence as retrieve/no-retrieve signal; authors note confidence does not reliably show whether a specific fact is mastered. — [arXiv 2411.06207](https://arxiv.org/html/2411.06207v2) (from search snippet)
- Package hallucination: Spracklen et al. (2024 arXiv, USENIX Security '25 [older]) ~5.2% commercial vs 21.7% open-source models across 576,000 prompts (as cited by an OpenSSF talk listing); 2026 re-evaluation finds narrowed spread but nonzero mean — [arXiv 2605.17062](https://www.alphaxiv.org/abs/2605.17062); contradicted in part by Hillah et al. claiming "near-zero" for modern code models after alias correction — [arXiv 2606.13918](https://arxiv.org/html/2606.13918); rate rises to 40–73% on adversarial "slopsquat bait" prompts — [arXiv 2608.23897](https://www.alphaxiv.org/abs/2608.23897). (All from search summaries; numbers not cross-checked in the PDFs.)

### Inferences
- For the user's failure cases (Prisma support, RFC status, library choices), the literature's "search only when unsure" depends on calibrated self-knowledge that models lack; for fast-changing facts (library versions, standards status), a rule-based trigger ("any claim about third-party support/status/version requires a fetched source") is safer than confidence-based triggering.
- The deterministic analogue in Claude Code is a Stop hook or PreToolUse hook (command type) that checks for evidence (e.g., a WebFetch/Read in the transcript before a Write to a decision doc), rather than more CLAUDE.md emphasis.

### Gaps
- No controlled study found specifically measuring "research-first" prompting effects on Claude Code agents.
- Spracklen et al. original numbers were taken from a secondary listing; not verified in the paper.

## Q4. Time-stamping observations / stale state

### Takeaway
Practice converges on: record when each observation was made (and separately when it is valid), and re-check against current state before acting. Claude Code itself relies on git for state tracking and on structured notes; academic work (2026) shows trusting stale memory can be worse than no memory.

### Cited Findings
- "Folder hierarchies, naming conventions, and timestamps all provide important signals" — [Anthropic engineering, Sep 2025](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Structured note-taking: "the agent regularly writes notes persisted to memory outside of the context window" — [Anthropic engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- "Use git for state tracking: Git provides a log of what's been done and checkpoints that can be restored." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Skill content is a snapshot: "Claude Code does not re-read the skill file on later turns." — [Skills docs](https://code.claude.com/docs/en/skills)
- SpatialSTALE (arXiv 2608.04574, 2026): an agent that trusts raw stale memory "dies more than twice as often as the same agent given no memory at all" in its primary GPT-4o setting; tests an explicit read-time audit. — [arXiv 2608.04574](https://arxiv.org/pdf/2608.04574) (from search summary)
- Practitioner "two clocks": distinguish transaction time ("the moment the fact entered the agent's memory") from valid time; argues against relying on prompting/LLM judges and for a structural fix; cites STALE benchmark. — [tianpan.co, Jul 2, 2026](https://tianpan.co/blog/2026-07-02-your-agents-memory-needs-two-clocks)
- Tooling example: pysince stamps files at read time and compares mtime/content hash before edits, with TTL classes (permanent, slow, event-invalidated, ephemeral); small unvetted project. — [pysince on PyPI](https://pypi.org/project/pysince/0.2.7/)

### Inferences
- A cheap Claude Code implementation: a PostToolUse hook on Read/WebFetch/Bash that appends `[observed at <ISO time>]` via `additionalContext`, and a convention that notes/memory entries carry "observed-at + source". Before acting on any memory or earlier observation older than a threshold, re-observe.

### Gaps
- No official Claude Code feature found that timestamps tool results automatically; no authoritative standard for observation freshness in coding agents.
