## 1. Which autonomy and decision-rights frameworks fit a decision-rights table?

### Takeaway
No framework gives a ready-made table for coding agents. Three pieces fit together: (a) Feng et al.'s five user roles (operator, collaborator, consultant, approver, observer), which treat autonomy as a design choice made per agent; (b) Anthropic's principle that reads are free, while changes and high-stakes decisions need human approval; (c) a split of actions by reversibility and by who sees them. Within that split, OpenAI's governance paper has a section on constraining the action space and requiring approval. A per-row table ("who decides: user / agent decides and reports / agent decides silently") is the practical form of these. The frameworks set the axes. The rows have to come from the user's own patterns.

### Cited Findings
- Feng, McDonald & Zhang, "Levels of Autonomy for AI Agents" (arXiv 2506.12469, v1 14 Jun 2025, v2 28 Jul 2025) [older]. It defines five levels of increasing autonomy, named by the user's role: **operator, collaborator, consultant, approver, observer**. It argues autonomy is a deliberate design decision, separate from capability and environment, and proposes "AI autonomy certificates" to govern agent behavior in single-agent and multi-agent systems. Opening line: "Autonomy is a double-edged sword for AI agents, simultaneously unlocking transformative possibilities and serious risks." — [arXiv](https://arxiv.org/abs/2506.12469)
- Anthropic, "Our framework for developing safe and trustworthy agents" (4 Aug 2025) [older]: "humans should retain control over how their goals are pursued, particularly before high-stakes decisions are made." Claude Code "has read-only permissions by default" and "must ask for human approval before taking any actions that modify code or systems." Expense example: an agent "might identify that the company is overspending on software subscriptions," and a human should approve before it cancels subscriptions or downgrades tiers. That is the pattern of the agent finding something and the human deciding. Transparency: "Claude shows its planned actions through a real-time to-do checklist." — [Anthropic](https://www.anthropic.com/news/our-framework-for-developing-safe-and-trustworthy-agents)
- Anthropic, "Building effective agents" (19 Dec 2024) [older]: "Agents can then pause for human feedback at checkpoints or when encountering blockers." "it's also common to include stopping conditions (such as a maximum number of iterations) to maintain control." "The autonomous nature of agents means higher costs, and the potential for compounding errors." "We recommend extensive testing in sandboxed environments, along with the appropriate guardrails." — [Anthropic](https://www.anthropic.com/research/building-effective-agents)
- Anthropic prompting best practices, "Balancing autonomy and safety", sample prompt (written for Opus 4.6 and still on the current page): "Consider the reversibility and potential impact of your actions. You are encouraged to take local, reversible actions like editing files or running tests, but for actions that are hard to reverse, affect shared systems, or could be destructive, ask the user before proceeding." Examples it lists: "Destructive operations: deleting files or branches, dropping database tables, rm -rf"; "Hard to reverse operations: git push --force, git reset --hard, amending published commits"; "Operations visible to others: pushing code, commenting on PRs/issues, sending messages, modifying shared infrastructure"; "When encountering obstacles, do not use destructive actions as a shortcut. For example, don't bypass safety checks (e.g. --no-verify) or discard unfamiliar files that may be in-progress work." — [Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- OpenAI, "Practices for Governing Agentic AI Systems" (Dec 2023) [older]. The table of contents includes §4.2, "Constraining the Action-Space and Requiring Approval." I could not retrieve the paper text itself. Secondary summaries say it recommends human approval for irreversible or high-cost actions and outright prevention of some actions, and that it warns that approval on every action would negate the benefits of autonomy and that approval is only meaningful when reviewers have enough context. These details are unverified against the original. — [OpenAI PDF](https://cdn.openai.com/papers/practices-for-governing-agentic-ai-systems.pdf); summary: [VerifyWise](https://verifywise.ai/ai-governance-library/governance-frameworks/openai-practices-governing-agentic-ai-systems)
- Claude Code's auto-mode classifier is in effect a vendor-defined decision-rights default. It blocks by default: "Production deploys and migrations", "Force push", "`git reset --hard`, `git checkout -- .`, `git restore .`, `git clean -fd`, `git stash drop`, or `git stash clear`", "Merging a pull request no human has approved…", "Granting IAM or repo permissions", "Irreversibly destroying files that existed before the session", "Mass deletion on cloud storage". It allows by default: "Pushing to any branch of the repository you're working in, including the default branch." The classifier also blocks anything that "escalates beyond your request" or "targets unrecognized infrastructure." — [Permission modes](https://code.claude.com/docs/en/permission-modes)

### Inferences
- Feng et al.'s roles can label the columns of a decision-rights table per decision type. For example, requirements, scope, production vs staging and policy are at the "operator/collaborator" level, where the user decides. Routine engineering choices and facts the agent can verify are at the "approver/observer" level, where the agent decides and the user can see the result. This is my mapping. The paper does not give it.
- The default push behavior in auto mode conflicts with this user's pattern (the user always orders pushes explicitly), so an explicit `ask` rule is needed. The vendor default is not enough.
- Anthropic's three example classes (destructive, hard to reverse, visible to others) do not cover cause F, which is creation that accumulates cost: worktrees, containers, DBs, memory. The user's table needs a fourth class: creating durable resources that occupy disk or other resources and outlive the session.

## 2. What does research say about when LLM agents should ask clarifying questions and when they should proceed?

### Takeaway
Recent research on coding agents finds that both asking too much and asking too little hurt. Separating "detect underspecification" from "execute" improves results. Agents should save questions for underspecification that changes the outcome, and resolve everything they can find out from the environment on their own. Anthropic's own prompts say the same in operational terms: discover missing details with tools instead of guessing, and check in only when different readings would lead to materially different work.

### Cited Findings
- Edwards & Schuster, "Ask or Assume? Uncertainty-Aware Clarification-Seeking in Coding Agents" (arXiv 2603.26233; v1 27 Mar 2026, v3 7 Sep 2026, EMNLP 2026 camera-ready). Using an underspecified variant of SWE-bench Verified, a multi-agent scaffold that separates detecting underspecification from executing code reached a 69.40% resolve rate, "significantly" above a single-agent setup. The abstract says it closes much of the gap with fully specified instructions while "conserving queries on simple tasks while proactively seeking information on more complex issues." — [arXiv](https://arxiv.org/abs/2603.26233). A search snippet gives a single-agent baseline of 61.20% (OpenHands + Claude Sonnet 4.5), but I could not confirm that number on the arXiv page — [alphaXiv](https://www.alphaxiv.org/abs/2603.26233)
- Vijayvargiya et al. (CMU), "Ambig-SWE" / interactive agents with underspecified instructions (arXiv 2502.13069) [older, 2025]. It studies detecting underspecification, asking targeted questions, and using the answers. Per the search summary, the authors find that actionable, targeted clarifying questions drive the performance gains. I did not open the full text. — [arXiv PDF](https://arxiv.org/pdf/2502.13069v3)
- Anthropic `<default_to_action>` sample: "If the user's intent is unclear, infer the most useful likely action and proceed, using tools to discover any missing details instead of guessing." The opposite sample is `<do_not_act_before_instructions>`: "When the user's intent is ambiguous, default to providing information, doing research, and providing recommendations rather than taking action. Only proceed with edits, modifications, or implementations when the user explicitly requests them." — [Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Opus 5.5 guide, "Unattended agentic runs": it lists unwanted stops, including "a list of decisions for the user when, by your own account, none of them blocks the rest of the work," and "an offer to carry on with something unless the user would prefer otherwise." It defines wanted stops as "the ones where nothing can move without them, or where the thing blocking you is deliberately protected from you." It also says "This does not override the need for confirmation on risky or destructive actions," and that the addition should be left out of "human-in-the-loop applications, where someone is there to answer." — [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)
- The same guide recommends looking through relevant sources before acting on loosely specified tasks: "Before taking any action, explore broadly with tool calls … including ones the task does not explicitly mention, and use what you find." Anthropic reports that this raised correct completion on multi-app tasks. — [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)

### Inferences
- Ask-vs-act can be applied as two tests in order. (1) Can the agent settle it by observing or by common engineering sense? Then decide or verify it, and report. (2) Is it in the user-only column (requirements, scope, environment identity, tech choice, policy), or would different readings lead to materially different work? Then ask, putting the full proposal in the question. This fits trait 2-13 (asking what it could verify) and trait 2-3 (making up values that only the user can supply) at the same time.
- The Edwards & Schuster finding that separating detection from execution helps suggests a light procedure: before acting, list the unknowns, classify each against the decision-rights table, then proceed. My extrapolation; the paper tested a multi-agent scaffold, not a prompt.
- For trait 6-7 (asking the same decision every turn), the Opus 5.5 "don't list non-blocking decisions" text gives a vendor-worded instruction. It has to be paired with the user's standing approvals recorded somewhere persistent, such as the per-project table, so a settled decision is not asked again.

### Gaps
- I found no study that measures whether repeated identical questions annoy users (trait 6-7) or how agents should handle subagent questions. No sourced guidance on whether an orchestrator should answer a subagent's question itself.

## 3. Anthropic's official scope-control prompts for Opus 5 / 5.5 and Claude Code

### Takeaway
The main official text is the Opus 5 "Task scope" prompt ("Deliver what was asked, at the scope intended…"). It still applies to Opus 5.5, because the Opus 5.5 guide says Opus 5 patterns "remain a reasonable starting point" and adds no new scope prompt. It pairs with the "Avoid over-engineering" sample and the reversibility sample. Anthropic's own docs also say plainly that prompt and CLAUDE.md text does not enforce anything; enforcement is permissions and hooks.

### Cited Findings
- Prompting Claude Opus 5, "Task scope and over-verification": "Claude Opus 5 can also expand the scope of a task, adding steps that weren't requested or applying its own judgment about what the task should be. For narrow tasks, constrain scope explicitly:" Sample: "Deliver what was asked, at the scope intended. Make routine judgment calls yourself, and check in only when different readings of the request would lead to materially different work. If the request seems mistaken or a better approach exists, say so in a sentence and continue with the task as asked rather than quietly narrowing, widening, or transforming it. Finish the whole task, and stop short of actions that are clearly beyond what was asked." — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- The same page on over-verification: "If your prompt contains explicit verification instructions … remove them: instructions like these cause over-verification on Claude Opus 5." — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- Subagent control sample: "Delegate to a subagent only for large tasks that are genuinely independent and parallelizable … Do not delegate work you can finish yourself in a handful of tool calls, and do not use subagents to verify or double-check your own work. If one subagent can complete the task, use one rather than several, and keep spawn counts low." Deterministic caps: "`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` and `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` environment variables and the SDK's `max_budget_usd`." Also: "Claude Code adds a delegation instruction of its own on Claude Opus 5 only when you use its `claude_code` system prompt preset." — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- Opus 5.5 guide: "Existing Claude Opus 5 prompts should perform well without changes, and the patterns in Prompting Claude Opus 5 remain a reasonable starting point." It reports that Opus 5.5 "sustains long-running autonomous work better than Claude Opus 5 … with parallel subagents and little oversight." It has no separate scope section. — [Prompting Claude Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5)
- Overengineering sample (for Opus 4.5/4.6, still on the page): "Avoid over-engineering. Only make changes that are directly requested or clearly necessary. … Scope: Don't add features, refactor code, or make "improvements" beyond what was asked. A bug fix doesn't need surrounding code cleaned up. … Abstractions: Don't create helpers, utilities, or abstractions for one-time operations. Don't design for hypothetical future requirements." — [Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- The same page on tone: "Where you might have said "CRITICAL: You MUST use this tool when...," you can use more normal prompting such as "Use this tool when..." instead." Newer models overtrigger on aggressive language. — [Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Enforcement boundary: "Permission rules are enforced by Claude Code, not by the model. Instructions in your prompt or `CLAUDE.md` shape what Claude tries to do, but they don't change what Claude Code allows." — [Permissions](https://code.claude.com/docs/en/permissions)
- Auto mode and conversation boundaries: if you tell Claude "don't push," the classifier blocks matching actions. But boundaries "are not stored as rules and can be lost to context compaction," so "For a hard guarantee, add a deny rule instead." — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- Hooks: "Hooks are user-defined shell commands … which gives you deterministic control: certain actions always happen rather than relying on the LLM to choose to run them." — [Hooks guide](https://code.claude.com/docs/en/hooks-guide)

### Inferences
- The Opus 5 scope sentence covers traits 4-1 (scope expansion), 2-13 (routine judgment calls) and 4-2 (quietly transforming the task) in one place. The analysis file already proposes it (해결 D). The research confirms it is the current official text for the 5.x line.
- "Finish the whole task, and stop short of actions that are clearly beyond what was asked" is about scope only. It does not say who decides creations like branches or worktrees, so that still needs the permissions layer.
- If the user's CLAUDE.md contains old-style "always verify / use a subagent to verify" rules, they may themselves cause over-verification and extra subagent spawning on 5.x models.

### Gaps
- I found no Anthropic text written specifically for Claude Code (as opposed to the API) about decision-rights tables. Claude Code's built-in system prompt is not published.

## 4. Claude Code permission rules: syntax, semantics, coverage limits, modes, sandbox, hooks

### Takeaway
Use `permissions.ask` with command-prefix rules (`Bash(git push *)`) for the user's "only when I order it" actions. Ask rules are the one rule type that still prompts in auto mode and even in bypassPermissions. A Bash rule is a match on the command text, not a security boundary: `git -C . push`, `/usr/bin/git`, `sh -c` and scripts get around it. Two layers back it up. A PreToolUse hook, which runs in every mode, parses commands such as `git -C`. The sandbox limits where writes can land. Parameter rules (`Agent(isolation:worktree)`) gate worktree creation by subagents.

### Cited Findings — syntax and precedence
- "Rules are evaluated in order: deny, then ask, then allow. The first match in that order determines the outcome, and rule specificity doesn't change the order." "a matching ask rule prompts even when a more specific allow rule also matches the same call." — [Permissions](https://code.claude.com/docs/en/permissions)
- Format: "`Tool` or `Tool(specifier)`." "Put the `*` after the subcommand. … `Bash(git log *)` allows only `git log` commands, and `Bash(git *)` allows every git command." "A `*` at the end, with a space before it, also matches the bare command." "The space before a trailing `*` is part of the rule. `Bash(ls *)` requires a space after `ls`, so `lsof` doesn't match." "The `:*` suffix is an equivalent way to write a trailing wildcard … only recognized at the end of a pattern." — [Permissions](https://code.claude.com/docs/en/permissions)
- Compound commands: "Deny and ask rules apply when any subcommand matches them, including a command nested inside a subshell, a command substitution, or a control-flow body such as a `for` loop. An ask rule like `Bash(git clean *)` still prompts you for `cd /tmp && git clean -f` or `echo "$(git clean -f)"`, even in auto mode." Separators recognized: `&&`, `||`, `;`, `|`, `|&`, `&`, newlines. — [Permissions](https://code.claude.com/docs/en/permissions)
- Wrappers stripped before matching: `timeout`, `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin`, `noglob`, and bare `xargs`. "A deny or ask rule matches past any leading assignment, so `Bash(rm *)` in deny still matches `FOO=bar rm -rf tmp/`." Not stripped: "`direnv exec`, `devbox run`, `mise exec`, `npx`, and `docker exec`." — [Permissions](https://code.claude.com/docs/en/permissions)
- **Coverage limit (key):** "It doesn't match the same program invoked in a different form, so a deny or ask rule covers the invocation Claude usually produces and isn't a security boundary around the program." Examples: `Bash(git push *)` does not stop "`git -C . push origin main`, `git -c push.default=current push origin main`, `git 'push' origin main`"; `Bash(rm *)` does not stop "`/bin/rm -rf build/`, `bash -c 'rm -rf build/'`". The doc's recommended alternatives: "use sandboxing" for filesystem and network enforcement; "To inspect the full command text with your own logic before it runs, use a PreToolUse hook." — [Permissions](https://code.claude.com/docs/en/permissions)
- "Bash permission patterns that try to constrain command arguments are fragile." The example `Bash(curl http://github.com/ *)` is defeated by options placed before the URL, a different protocol, redirects, or variables. — [Permissions](https://code.claude.com/docs/en/permissions)
- `Bash(command:rm *)` parameter-style rules on the primary content field are ignored with a startup warning, because they "would be bypassable by a compound command." — [Permissions](https://code.claude.com/docs/en/permissions)
- Parameter rules (deny/ask only): "Deny and ask rules can match a top-level input parameter on any built-in tool with `Tool(param:value)`." Examples: "`Agent(isolation:worktree)` | Agent calls that request a git worktree"; "`Bash(run_in_background:true)`". "A parameter the model omits is never matched." — [Permissions](https://code.claude.com/docs/en/permissions)
- MCP: "`mcp__<server>__*`" or "`mcp__<server>__<tool>`". Plugin servers use "`mcp__plugin_my-plugin_database-tools__*`". "When Claude Code loads a settings file, it skips any `mcp__` rule that has parentheses." Deny and ask accept tool-name globs ("`mcp__*`"). Allow globs must be anchored to a specific server. — [Permissions](https://code.claude.com/docs/en/permissions)
- Read-only commands are auto-approved in every mode; "to require a prompt for one of these commands, add an `ask` or `deny` rule for it." "`cd` with `git`: prompts when the `cd` changes into a different directory." — [Permissions](https://code.claude.com/docs/en/permissions)
- Redirects: output redirect targets are checked against Edit rules, protected paths and working directories. "A rule such as `Bash(git commit *)` allows the command, not the target." — [Permissions](https://code.claude.com/docs/en/permissions)
- Settings scopes: "if user settings allow a permission and project settings deny it, the deny rule blocks it … a user-level deny blocks a project-level allow." Managed settings are highest. — [Permissions](https://code.claude.com/docs/en/permissions)

### Cited Findings — behavior by mode
- Modes table: `default` (Manual) asks for everything except reads; `acceptEdits` auto-approves edits plus `mkdir`, `touch`, `mv`, `cp`; `auto` runs "Everything, with background safety checks"; `dontAsk` denies anything that would prompt; `bypassPermissions` runs "Everything" and is for "Isolated containers and VMs only". — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- Auto mode decision order: "Allow, ask, and deny rules resolve immediately, with exceptions. … Ask rules that match on command content, such as `Bash(git push *)`, fall back to a permission prompt." "To require a human checkpoint while staying in auto mode, add `permissions.ask` rules. Auto mode still shows those prompts." When entering auto mode, broad allow rules are dropped (blanket `Bash(*)`, wildcarded interpreters, package-manager run commands, `Agent` allow rules). — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- bypassPermissions: "Deny rules block in every mode, including `bypassPermissions`." "Allow rules have no effect in `bypassPermissions`." "Even in `bypassPermissions` mode, each of the actions no mode auto-approves gets a prompt or a denial." I did not fully verify whether ordinary user `ask` rules count among "actions no mode auto-approves." The fetched summary says ask rules still prompt, but the full section was truncated. Warning: "Only use this mode in isolated environments like containers, VMs, or dev containers without internet access." `permissions.disableBypassPermissionsMode: "disable"` "works from any scope. A user can set it in their own settings to lock themselves out of bypass mode." — [Permission modes](https://code.claude.com/docs/en/permission-modes); [Permissions](https://code.claude.com/docs/en/permissions)
- dontAsk: "Claude Code denies calls matching your explicit `ask` rules rather than prompting." — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- Protected paths (`.git`, `.claude`, `.vscode`, shell rc files, etc.): prompted in default and acceptEdits, sent to the classifier in auto, denied in dontAsk, allowed in bypassPermissions; "Settings in `permissions.allow` do not pre-approve protected-path writes." — [Permission modes](https://code.claude.com/docs/en/permission-modes)

### Cited Findings — hooks
- "PreToolUse hook decisions don't bypass permission rules. … a matching deny rule blocks the call, and a matching ask rule still prompts even when the hook returned `"allow"` or `"ask"`." "A hook that exits with code 2 stops the tool call before permission rules are evaluated, so the block applies even when an allow rule would otherwise let the call proceed." — [Permissions](https://code.claude.com/docs/en/permissions)
- "a hook that returns `permissionDecision: "deny"` blocks the tool even in `bypassPermissions` mode or with `--dangerously-skip-permissions`. `PreToolUse` hooks fire before any permission-mode check, in every permission mode, including `dontAsk`." — [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- JSON output: `{"hookSpecificOutput": {"hookEventName": "PreToolUse", "permissionDecision": "deny"|"ask"|"allow", "permissionDecisionReason": "..."}}`. "you can also return `"ask"` to show the user the normal permission prompt." A misplaced top-level `permissionDecision` is silently ignored. — [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- The `if` field filters a hook by permission-rule syntax, for example `"if": "Bash(git *)"` with `"matcher": "Bash"`. The guide has worked examples blocking `rm -rf` and `drop table` with exit 2. — [Hooks guide](https://code.claude.com/docs/en/hooks-guide)
- Caveat on mods: with no managed settings and no Team/Enterprise `/login`, "a mod can approve a call your `PreToolUse` hook blocked" and can skip ask prompts. — [Hooks guide](https://code.claude.com/docs/en/hooks-guide); [Permissions](https://code.claude.com/docs/en/permissions)

### Cited Findings — sandbox
- "The sandbox is off by default." Enable with `/sandbox` or `sandbox.enabled: true`. Default writes are allowed to "the working directory, a per-user temp directory, and any directories you've added." Network is proxied against `allowedDomains`, which "start empty." `filesystem.denyWrite`/`denyRead` and `network.deniedDomains` are available. — [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Limits: Read/Edit/Write/WebFetch, hooks and MCP servers "run outside it"; "`docker` is incompatible with the sandbox" and needs `excludedCommands` (which "runs with your full access"). The `dangerouslyDisableSandbox` retry can be turned off with `"allowUnsandboxedCommands": false`. It runs on macOS, Linux and WSL2. — [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Interaction: with `autoAllowBashIfSandboxed` at its default `true`, sandboxed commands skip a bare `Bash` ask rule, but "Content-scoped ask rules like `Bash(git push *)` still force a prompt." — [Permissions](https://code.claude.com/docs/en/permissions)

- Loss of work (trait 3-12): deny or ask on `Bash(git push --force *)`, `Bash(git push -f *)`, `Bash(git reset --hard *)`, `Bash(git clean *)`, `Bash(git stash drop *)`, `Bash(rm -rf *)`, `Bash(git worktree remove *)`. Auto mode already blocks several of these by default, but Manual and bypass modes need explicit rules.
- Memory creation: gating writes to the auto-memory directory with an `Edit(~/.claude/projects/**/memory/**)` ask rule is plausible, because the docs list `~/` as a path anchor shared with the Read/Edit rules. I did not confirm the exact anchoring semantics for Edit (gitignore-style) in this session; check them before use.
- Because `git -C <dir> push` is common in agent output (agents often run git with `-C`), the text-match rules need a backup: a PreToolUse hook with `"if": "Bash(git *)"` that normalizes away `-C`/`-c` and returns `"ask"` for commit/push/merge/worktree/branch-create. The hook also runs in bypass mode. This addresses the coverage limit the docs themselves name.
- The sandbox limits where writes can land (the working directory) and could help with disk growth, but it does not cover Docker, which must be excluded. So it cannot stop the "hundreds of GB" container/DB growth. Ask rules and hooks are the main control there.
