Scope: traits 4-3, 5-3..5-5, 5-7..5-9 in /Users/kms1212/agent-traits-2026-11-04/analysis.md, plus the user's decision to deny the built-in generic subagents and add one custom general subagent that refuses when a better-fitting agent exists. ## Q1. What Anthropic documents about subagent selection, permissions, built-ins, fork mode and caps

### Takeaway
Selection is done only by the parent model, which matches the task against each agent's `description`. The subagent plays no part in it. Built-ins can be blocked one by one with `permissions.deny: ["Agent(<name>)"]`, and that covers `Agent(fork)` too. Depth, concurrency and spend each have a deterministic cap. A per-agent allowlist on which types may be spawned (`Agent(a, b)` in `tools`) works only for the main-thread agent started with `claude --agent`, not inside subagents.

### Cited Findings
- Selection: "Claude automatically delegates tasks based on the task description in your request, the `description` field in subagent configurations, and current context. To encourage proactive delegation, include phrases like "use proactively" in your subagent's description field." — [Claude Code: Subagents](https://code.claude.com/docs/en/sub-agents)
- Best practice: "Write descriptions that single out one subagent: Claude uses the description to decide when to delegate. Make each description specific enough to route to the right subagent, and keep the combined set within the 15,000-token description budget" — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Budget: "Keep descriptions brief: Claude Code shows a startup warning when your subagents' combined descriptions pass the 15,000-token limit, and still loads every subagent." The page also says: "Trim the `description` fields of your subagents, and move detail into each subagent's system prompt, which only loads when that subagent runs." — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Explicit invocation skips matching: "To guarantee Claude uses a specific subagent, mention it by name in your prompt ... This bypasses automatic matching and directly invokes the named subagent." — [Agent SDK: Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- Disabling: "You can prevent Claude from using specific subagents by adding them to the `deny` array in your settings. Use the format `Agent(subagent-name)` ... This works for both built-in and custom subagents." Example: `"deny": ["Agent(Explore)", "Agent(my-custom-agent)"]`. CLI equivalent: `claude --disallowedTools "Agent(Explore)"`. — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Other switches: "To remove only the built-in `Explore` and `Plan` subagents, set `CLAUDE_CODE_DISABLE_EXPLORE_PLAN_AGENTS=1`" (v2.1.198+). "In non-interactive mode and the Agent SDK, set `CLAUDE_AGENT_SDK_DISABLE_BUILTIN_AGENTS=1` to remove all built-in types and supply only your own." "To prevent Claude from delegating to any subagent, deny the `Agent` tool itself with `permissions.deny`." — [Subagents](https://code.claude.com/docs/en/sub-agents)
- The default type when none is given: "When Claude calls the Agent tool without a `subagent_type`, it gets the built-in `general-purpose` subagent ... Setting `CLAUDE_AGENT_SDK_DISABLE_BUILTIN_AGENTS=1` removes that default, and such a call fails with `subagent_type is required`." — [Agent SDK: Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- Built-ins listed: Explore (read-only), Plan (read-only, plan mode), general-purpose ("A capable agent for complex, multi-step tasks that require both exploration and action"), plus `claude` (catch-all), `statusline-setup`, `claude-code-guide`. — [Subagents](https://code.claude.com/docs/en/sub-agents). Note: in this user's live session the agent list also shows a `claude` agent described as "Catch-all for any task that doesn't fit a more specific agent", so it has to be denied as well if the goal is to block all generic built-ins.
- Fork: "A fork is a subagent that inherits the entire conversation so far instead of starting fresh ... Use a fork when any other subagent would need too much background to be useful, or when you want to try several approaches in parallel from the same starting point." "Claude can start a fork on its own while fork mode is on, as it is by default." Two ways to stop forks: "Stop forks only: add `"Agent(fork)"` to `permissions.deny`" or "Turn fork mode off: set `CLAUDE_CODE_FORK_SUBAGENT` to `0`". "While fork mode is on, Claude also can't wait for a subagent in interactive terminal, VS Code, or desktop sessions". "Fork mode is on by default from Claude Code v2.1.302". "A fork can't spawn further forks." — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Allowlist limits: "The `Agent(agent_type)` allowlist syntax applies only to an agent running as the main thread with `claude --agent`. In a subagent definition, listing `Agent` in `tools` lets that subagent spawn subagents of its own while the depth limit allows it, but any type list inside the parentheses is ignored." — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Depth: "By default, a subagent can spawn subagents of its own, up to three layers below the main conversation. At the depth limit, Claude Code withholds the `Agent` tool from every subagent except a fork, so a subagent at the limit does its delegated work itself and returns one summary." Set `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`; "Set `1` to turn nesting off." — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Concurrency: "By default, when 20 subagents are running in a session, spawning another with the Agent tool fails with `Concurrent subagent limit reached`, and the error tells Claude not to retry ... set `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` ... Sessions with ultracode active are exempt ... Requires Claude Code v2.1.217 or later." "There's no limit on the total number of subagents Claude can spawn over a session." — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Spend: `maxBudgetUsd` / `max_budget_usd` "refuses to spawn more subagents, returning `Budget limit reached`, stops background subagents that are still running, and ends the query with the `error_max_budget_usd` result subtype." — [Agent SDK: Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- Opus 5 system prompt: "`claude_code` preset: when the model is Opus 5, Claude Code adds a line to its system prompt telling Claude not to call the Agent tool unless it's asked to. The Agent tool stays available." "Either instruction only steers Claude, so set the limits as well." — [Agent SDK: Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- Skills are not inherited: "Subagents do not inherit your session's skills." The `skills` field "controls which skills are preloaded, not which skills the subagent can access: without it, the subagent can still discover and invoke project, user, and plugin skills through the Skill tool during execution." Up to 32 skills can be preloaded. "Built-in agents don't preload skills." — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Lifecycle hooks: `SubagentStart` and `SubagentStop` fire per agent type, and the matcher is the agent's `name` (or `plugin:agent` for plugin agents). — [Subagents](https://code.claude.com/docs/en/sub-agents)

### Inferences
- The proposed deny list is `Agent(general-purpose)`, `Agent(Explore)`, `Agent(Plan)`, `Agent(fork)`. The user's environment also has the built-in `claude` catch-all, which should probably be denied too, or the main agent will route generic work there instead of to the custom general agent. Setting `CLAUDE_CODE_FORK_SUBAGENT=0` additionally restores the ability to wait on a subagent, which `Agent(fork)` deny alone may not do.
- With `general-purpose` denied, the custom general agent should state a clear "fallback only" role in its description, so that the routing model picks it only when nothing else fits. That makes the parent-side choice the first line of routing defense and the subagent's self-check the second.
- Because the subagent-level `Agent(a,b)` allowlist is ignored, nested spawning cannot be restricted by type from inside a subagent definition. Use `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=1` or omit `Agent` from `tools`. This directly addresses 5-3.
- Since built-in agents preload no skills and subagents do not inherit skills, the custom general agent should list its key skills in `skills:` so that "general-purpose runs with no skills" stops happening.

### Gaps
- I did not confirm whether `Agent(claude)` deny works on the `claude` catch-all exactly as it does on other built-ins. The docs only say deny "works for both built-in and custom subagents".
- I did not fetch the docs for a `PreToolUse` hook on the `Agent` tool (matching `tool_input.subagent_type`). Such a hook would be a deterministic router check before spawn. See Q2.

## Q2. Router, dispatcher and triage patterns, how they handle a wrong pick, and whether self-refusal by the chosen agent is a known pattern

### Takeaway
All the major frameworks route at the caller: a classifier, a supervisor, or the LLM choosing among `transfer_to_X` tools whose descriptions it reads. The usual fix for a wrong pick is a handoff back to the supervisor or triage agent, plus fallback or catch-all agents and logging of misroutes. I found no documented pattern in which a specialist that was picked checks the registry and refuses in favor of a better one. The closest are "handoff back to supervisor" (LangGraph) and agents told to refuse out-of-scope requests (the Claude Code `db-reader` example). The user's design is therefore new, and it has predictable costs and failure modes (see Inferences).

### Cited Findings
- Anthropic, "Building effective agents" (**Dec 19, 2024, older material**): "Routing classifies an input and directs it to a specialized followup task." "Routing works well for complex tasks where there are distinct categories that are better handled separately." Orchestrator-workers: "a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results." General guidance: "we recommend finding the simplest solution possible, and only increasing complexity when needed." "The autonomous nature of agents means higher costs, and the potential for compounding errors." — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- OpenAI Agents SDK: "Handoffs are represented as tools to the LLM" (e.g. `transfer_to_refund_agent`). "If you have multiple possible destinations, register one handoff per destination and let the model choose among them." `is_enabled` "is evaluated while the SDK prepares the available handoffs", meaning before the model answers. "Nested handoff history is available as an opt-in beta and is disabled by default." For a specialist that should not take over the conversation, it offers `Agent.as_tool(...)`. The page has nothing on handing back or recovering from a wrong agent beyond a triage-agent example. — [OpenAI Agents SDK: Handoffs](https://openai.github.io/openai-agents-python/handoffs/)
- LangGraph supervisor: `create_handoff_tool` builds a `transfer_to_<agent_name>` tool. `add_handoff_back_messages` on `create_supervisor` controls "Whether to add a pair of (AIMessage, ToolMessage) to the message history when returning control to the supervisor." The official migration guide says the `langgraph-supervisor` package is no longer actively maintained and recommends a subagents pattern on `create_agent` in which a tool calls the subagent directly. — [langgraph-supervisor reference](https://reference.langchain.com/python/langgraph-supervisor/handoff/create_handoff_back_messages); [migration guide](https://docs.langchain.com/oss/python/migrate/langgraph-supervisor.md) (search-result summary, not fetched in full)
- Out-of-scope refusal inside a specialist (Claude Code example): the `db-reader` prompt says "If asked to INSERT, UPDATE, DELETE, or modify schema, explain that you only have read access", and a `PreToolUse` hook acts as backstop: "The system prompt tells the subagent to refuse write requests, so the hook is a backstop". — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Industry router guidance (secondary, vendor and glossary sources found by search, not fetched in full): misrouting is the main risk. Vague scope text is the most common cause. A catch-all or fallback agent handles requests with no match. Routing decisions should be logged with the candidates so misroutes can be reviewed. The search found no source describing a specialist that declines and hands the task back. — e.g. [Atender: why did the wrong specialist answer](https://atender.com/docs/knowledge/settings/why-did-the-wrong-specialist-answer), [qubittool: Router Agent](https://qubittool.com/en/glossary/router-agent)
- MAST taxonomy ("Why Do Multi-Agent LLM Systems Fail?", Cemri et al., arXiv 2503.13657, v3 revised 26 Oct 2025): 14 failure modes in 3 groups. Prevalence includes FM-1.1 "Disobey task specification" 11.8%, FM-1.2 "Disobey role specification" 1.5%, FM-1.3 "Step repetition" 15.7%, FM-1.5 "Unaware of termination conditions" 12.4%, FM-2.2 "Fail to ask for clarification" 6.8%, FM-2.3 "Task derailment" 7.4%, FM-2.6 "Reasoning-action mismatch" 13.2%, FM-3.1 "Premature termination" 6.2%, FM-3.2 "No or incomplete verification" 8.2%, FM-3.3 "Incorrect verification" 9.1%. The authors recommend that "the role of each agent should be clearly specified". — [arXiv HTML](https://arxiv.org/html/2503.13657)
- Cognition, "Don't Build Multi-Agents" (**2025-06-12, older material, by a competitor**): "Actions carry implicit decisions, and conflicting decisions carry bad results"; "Share context, and share full agent traces, not just individual messages"; "The simplest way to follow the principles is to just use a single-threaded linear agent". — [Cognition](https://cognition.com/blog/dont-build-multi-agents)
- A subagent's final message is the only thing that reaches the parent, and Claude Code (v2.1.210+) scans it: tags that imitate the harness are neutralized and `Human:`/`Assistant:` turn markers are escaped. — [Agent SDK: Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- Agents with the `SendMessage` tool get a list of the other named agents *running* in the session. That is not the list of definitions. — [Agent SDK: Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)

### Inferences (the refusing general agent: design notes and failure modes)
- **Where the check runs.** Self-refusal is a second, caller-side routing check run in the callee. It costs one full subagent spawn (system prompt, CLAUDE.md, preloaded skills, the registry scan) per misroute, plus a round trip, and the parent has to understand the refusal and re-dispatch. To keep that cheap, the check should come first, be read-only, and use only frontmatter (`name` + `description`). The agent should not read bodies of other agents.
- **"Even slightly more suitable" will over-trigger.** Nearly every task partly overlaps some specialist description. A strict threshold invites refusal loops: general → refuses → parent picks specialist X → X does not really fit → parent goes back to general, or does the work itself (4-3 again). Mitigations: (a) the refusal names exactly one target agent and one short reason, in a fixed machine-readable first line (for example `REDIRECT: <agent-name> — <reason>`); (b) state in CLAUDE.md, or in the general agent's own prompt as an instruction to the caller, that a task redirected once must go to the named agent and that the general agent never refuses the same task twice (pass a marker such as "redirected-from: general" in the prompt so the general agent skips the check); (c) the general agent never refuses when the caller has explicitly said "use general" (name invocation "bypasses automatic matching", per the SDK doc).
- **Visibility mismatch.** The general agent can only see filesystem definitions (see Q4). Agents from managed settings, `--agents` JSON, or SDK `agents={...}` are not on disk, so the scan will miss them. It may also find agents that are denied in `permissions.deny` or in disabled plugins and redirect to them, and the redirect fails. The scan should filter by the deny list in `~/.claude/settings.json`, `.claude/settings.json`, `.claude/settings.local.json` and by enabled plugins (`~/.claude/plugins/installed_plugins.json` and `enabledPlugins` in settings).
- **A deterministic alternative or supplement.** Do the validation before spawn instead of after: a `PreToolUse` hook on the `Agent` tool (or a `SubagentStart` hook) could compare `subagent_type` with the prompt and block with exit code 2 and a message naming a better agent. This is the "router validation" pattern, and it avoids paying for the spawn. It is not documented as such. It is an inference from the documented hook mechanics (PreToolUse exit 2 "returns an error message to Claude", as in the `db-reader` example) and from SubagentStart matching by agent type. A keyword-based hook is brittle, though, and an LLM-based check costs about as much as the self-check.
- **Root fix is at the description layer.** Docs and router guides agree that misrouting comes mostly from vague or overlapping descriptions. Rewriting descriptions so that each "single[s] out one subagent", and marking the general agent "use only when no other agent fits", will likely prevent more misroutes than callee-side refusal catches.
- MAST's large share for "Disobey task specification" (11.8%) and "Step repetition" (15.7%) suggests a refusal loop would show up as both. Log every REDIRECT (through `SubagentStop` hook output) so that loops can be measured.

### Gaps
- No primary source found describing callee-side self-refusal or redirect as an established pattern, or its measured effects. This should be presented as novel and untested.
- AutoGen (Selector/Swarm group chat) was not researched within the tool budget.
- I did not verify how the Claude Code parent model actually behaves when a subagent returns a refusal, for example whether it re-dispatches or just does the work itself. This needs a local test.

## Q3. Sizing delegated work against context, when to parallelize, and where to place verification

### Takeaway
Anthropic's current guidance (Opus 5, 2026) is to delegate only large, truly independent, parallelizable tracks, not anything doable in "a handful of tool calls". It also says to use one subagent rather than several where one suffices, and never to use subagents to verify one's own work, because Opus 5 already self-verifies and explicit verification instructions cause over-verification. Per the multi-agent research post, each delegation needs an objective, an output format, a tool guide and clear boundaries, and effort should scale with complexity. Work that does not fit one context should go to separate sessions, not one overloaded subagent.

### Cited Findings
- Opus 5 delegation: "Claude Opus 5 delegates to subagents more readily than prior models. Delegation is worthwhile for genuinely independent, sizeable tracks of work, but it multiplies cost and time when applied to small tasks." Recommended prompt: "Delegate to a subagent only for large tasks that are genuinely independent and parallelizable, such as a wide multi-file investigation. Do not delegate work you can finish yourself in a handful of tool calls, and do not use subagents to verify or double-check your own work. If one subagent can complete the task, use one rather than several, and keep spawn counts low." — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- Opus 5 verification: "Claude Opus 5 verifies its own work without being told to. If your prompt contains explicit verification instructions ("include a final verification step for any non-trivial task," "use a subagent to verify"), remove them: instructions like these cause over-verification on Claude Opus 5, and removing them reduces wasted tokens with no loss in quality. The same applies to legacy harness scaffolding that adds separate verification steps." Also: "Avoid instructing re-checks it already performs ... these compound with the model's own behavior and add cost without improving results." — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- Opus 5 strengths: "coordinates teams of subagents well, with effective writer-verifier patterns and few cases of agents overwriting each other's work. For cost-sensitive workloads, cap delegation". It "performs best when given the complete task specification up front and left to run". 1M-token context, "instruction following, tool calling, and reasoning stay consistent throughout the window". — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- Review scope: if a review prompt says "only report high-severity issues" the model may report less; "ask it to report everything and filter in a separate pass instead." — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- Main thread vs subagent: use the main conversation when "The task needs frequent back-and-forth or iterative refinement ... You're making a quick, targeted change ... Latency matters". Use subagents when "The task produces verbose output you don't need in your main context ... The work is self-contained and can return a summary." — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Too big for one context: "For work that needs to keep running in parallel or won't fit in one context window, run it in separate sessions and let Claude pass findings between them." Warning: "Running many subagents that each return detailed results can consume significant context, and each subagent spends tokens of its own while it runs." — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Context hand-off: "The only content you pass from parent to subagent is the Agent tool's prompt string, so include any file paths, error messages, or decisions the subagent needs directly in that prompt." — [Agent SDK: Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- Per-agent compaction: `autoCompactWindow` (100000–1000000) makes a subagent compact earlier. `maxTurns` returns output "marked as partial" and the agent can be resumed. — [Subagents](https://code.claude.com/docs/en/sub-agents); [Agent SDK: Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- Scale to dozens or hundreds of agents: "Subagents work well for a few delegated tasks per turn. For runs that coordinate dozens to hundreds of agents, use the `Workflow` tool, which moves the orchestration into a script". — [Agent SDK: Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- Multi-agent research post (Anthropic, June 2025, **older material, research rather than coding**): "Simple fact-finding requires just 1 agent with 3-10 tool calls"; "direct comparisons might need 2-4 subagents with 10-15 calls each"; "complex research might use more than 10 subagents with clearly divided responsibilities". "Each subagent needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries." "Without detailed task descriptions, agents duplicate work, leave gaps, or fail to find necessary information." "Early agents made errors like spawning 50 subagents for simple queries". "multi-agent systems use about 15× more tokens than chats". "most coding tasks involve fewer truly parallelizable tasks than research". Tasks that "involve many dependencies between agents are not a good fit for multi-agent systems today". "LLM agents are not yet great at coordinating and delegating to other agents in real time." — [How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- Parallel works best for independent paths: "This works best when the research paths don't depend on each other." — [Subagents](https://code.claude.com/docs/en/sub-agents)
- MAST on verification: "many existing verifiers perform only superficial checks, despite being prompted to perform thorough verification"; "sole reliance on final-stage, low-level checks is inadequate". The authors argue for multi-level verification (low-level correctness plus high-level objective). — [arXiv 2503.13657](https://arxiv.org/html/2503.13657)

### Inferences
- **Placement rule for 5-7 (duplicated heavy verification).** Verify once per artifact, at the level that owns it. The worker runs targeted tests for what it changed (Opus 5 does this without being told). The coordinator runs the full suite or review once, at integration, and does not ask each worker to run it, nor run it again after the workers have. Remove all "use a subagent to verify" and "double-check" lines from CLAUDE.md, skills and agent prompts, as the Opus 5 guide says. A separate reviewer agent is justified only as a deliberate writer-verifier step on the final diff (MAST's "high-level objective check"), not at every layer.
- **Sizing rule for 5-3 and 5-8.** Use three bands: (1) a handful of tool calls → do it inline, never delegate; (2) a self-contained track whose inputs, reading and output fit comfortably in one window → one subagent with objective, output format, tools and boundaries, plus `maxTurns`/`autoCompactWindow` as a backstop; (3) anything that "won't fit in one context window" or must outlive the turn → split into separate sessions or a Workflow script, never one oversized subagent. The docs give no numeric token threshold. Any number (for example "estimated reading under half the window") is a local policy to set by testing.
- **Parallel vs sequential rule for 5-4 and 5-9.** Run in parallel only when the tracks share no files or state and none needs another's output ("research paths don't depend on each other"; dependencies are "not a good fit"). Otherwise run in sequence. Resource safety (OOM) is not covered in any Anthropic doc found. The concurrency cap counts agents, not memory, so heavy local commands (test suites, builds) need their own limit: a project rule that only the coordinator runs heavy commands, or a hook or semaphore script. Setting `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` low (for example 3–5, as the SDK example uses 5) bounds the worst case.
- **4-3 (coordinator does others' work, or hands off its own).** The docs' main-thread vs subagent criteria are a usable test: back-and-forth, quick targeted change, or latency-sensitive → keep it. Verbose, self-contained, summary-returnable → delegate. Owning the result means the coordinator integrates and verifies once. It does not redo a worker's task.

### Gaps
- No Anthropic doc found that gives memory or CPU-aware parallelism guidance or a numeric context-fraction rule for sizing a subagent task.
- The research-system post is from June 2025 and is about research rather than coding. Its subagent counts are illustrative, not coding guidance.

## Q4. How a subagent can discover available agent definitions

### Takeaway
Filesystem agents live in `.claude/agents/` (project), `~/.claude/agents/` (user), and each enabled plugin's `agents/` directory. All are Markdown with YAML frontmatter, where only `name` and `description` are required and the `name` field is the identity. Managed-settings agents, `--agents` CLI JSON and SDK programmatic agents have higher priority but are not files a subagent can scan. No documented API lists "available agent types" to a subagent.

### Cited Findings
- Priority table: Managed settings (1), `--agents` CLI flag (2), `.claude/agents/` (3), `~/.claude/agents/` (4), "Plugin's `agents/` directory" (5). "When multiple subagents share the same name, Claude Code uses the one from the higher-priority location." — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Format: Markdown with YAML frontmatter. Only `name` and `description` are required. Claude Code scans these directories recursively, and identity comes only from the `name` field. "Names can't contain `:`, which is reserved for plugin-scoped identifiers such as `my-plugin:reviewer`". If a plugin puts the agent in a subfolder, the subfolder becomes part of the scoped name (e.g. `my-plugin:review:security`). — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Watching: "Claude Code watches `~/.claude/agents/` and `.claude/agents/` ... the next delegation uses the updated definition, with no restart needed." A new `agents` directory, `--add-dir` directories, and `--disable-slash-commands` sessions need a restart. — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Programmatic SDK agents "take precedence over filesystem-based agents with the same name". — [Agent SDK: Subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
- Plugin agents ignore `permissionMode`, `mcpServers`, `hooks`, `initialPrompt` frontmatter. — [Subagents](https://code.claude.com/docs/en/sub-agents)
- Local observation on this machine (not a doc): `~/.claude/agents/` does not exist yet. Plugin agent dirs are at `~/.claude/plugins/marketplaces/<marketplace>/plugins/<plugin>/agents/` and `~/.claude/plugins/synced/<...>/agents/`. Installed and enabled state is in `~/.claude/plugins/installed_plugins.json`. There is also a `~/.claude/plugins/cache` directory.

### Inferences
- A practical discovery step for the general agent is one read-only command at start, for example `grep -H -m2 -E '^(name|description):' ~/.claude/agents/**/*.md .claude/agents/**/*.md <enabled plugin agents dirs>`. Map plugin agents to `plugin:name`. Drop names matched by `Agent(...)` deny rules and its own name. More reliable still: the parent's Agent tool description already contains the authoritative list of available agent types with descriptions (as seen in this session's system prompt), but a fresh subagent does not inherit it. The cheapest robust design may be for the coordinator's instructions, not the subagent, to do the "is there a better fit?" check, with the subagent's scan only as a backstop.
