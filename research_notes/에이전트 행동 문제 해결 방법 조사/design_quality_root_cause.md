# Steering LLM coding agents toward sound design and root-cause fixes

Scope: what official guidance, research, and practitioner sources say about overengineering, design defaults, planning, design-standard encoding, root-cause fixing, and large refactors. Researched 2026-11-04. Fetched pages are marked with their dates. Sources that predate Opus 5 are marked [older].

## Q1. What do Anthropic's docs say about overengineering, minimal solutions, planning before coding, and design defaults (Opus 5 / Claude Code)?

### Takeaway
Anthropic's current docs treat overengineering and scope expansion as known model defaults. They counter them with short, plainly worded, positively framed scope instructions, not emphasis. Rules that must never bend go into hooks or deny rules. Project knowledge the model can't see goes into short CLAUDE.md lines, path-scoped rules, or skills. A spec written first (via an interview) and then a fresh session is the recommended way to settle requirements before building. The current best-practices page doesn't present plan mode as the main tool.

### Cited Findings
- Overengineering is documented as a model tendency [older: written about Opus 4.5/4.6, still on the current page]: "Claude Opus 4.5 and Claude Opus 4.6 have a tendency to overengineer by creating extra files, adding unnecessary abstractions, or building in flexibility that wasn't requested. If you're seeing this undesired behavior, add specific guidance to keep solutions minimal." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- The official sample anti-overengineering prompt includes: "Don't add features, refactor code, or make "improvements" beyond what was asked." It also says "Don't create helpers, utilities, or abstractions for one-time operations. Don't design for hypothetical future requirements. The right amount of complexity is the minimum needed for the current task." The defensive-coding line reads: "Don't add error handling, fallbacks, or validation for scenarios that can't happen. Trust internal code and framework guarantees. Only validate at system boundaries (user input, external APIs)." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Anthropic's sample for test-gaming asks for principled, general solutions: "Tests are there to verify correctness, not to define the solution. Provide a principled implementation that follows best practices and software design principles." It continues: "If the task is unreasonable or infeasible, or if any of the tests are incorrect, please inform me rather than working around them." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Observation before claims: "Never speculate about code you have not opened. ... Make sure to investigate and read relevant files BEFORE answering questions about the codebase." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)
- Opus 5 scope expansion: "Claude Opus 5 can also expand the scope of a task, adding steps that weren't requested or applying its own judgment about what the task should be." The recommended prompt is: "Deliver what was asked, at the scope intended. ... If the request seems mistaken or a better approach exists, say so in a sentence and continue with the task as asked rather than quietly narrowing, widening, or transforming it." — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- Opus 5 over-verification: "If your prompt contains explicit verification instructions ... remove them: instructions like these cause over-verification on Claude Opus 5." On self-checks: "Avoid instructing re-checks it already performs." — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- Opus 5 works best with the whole specification up front: "it performs best when given the complete task specification up front and left to run." — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- Positive examples beat prohibitions (stated for communication style, plausibly general): "Positive examples of the communication style you want tend to be more effective than instructions about what not to do." — [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- Emphasis causes overtriggering: "If your prompts were designed to reduce undertriggering on tools or skills, these models might now overtrigger. The fix is to soften any aggressive language." — [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices). The Claude Code best-practices page says the same in its outdated-advice table: "Current ones follow a plainly worded line, and piling on emphasis mostly makes Claude over-apply the rule. If it's a rule that can't bend, turn it into a hook or a deny rule. If the line is getting lost in a long file, the file needs to be shorter." — [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- Instructions come in two kinds. Prompts, CLAUDE.md, and skills are non-deterministic: "there's no *guarantee* that it'll follow your instructions." Hooks, deny rules, and managed settings are deterministic: "Claude Code (the harness) *has* to execute this." — [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- On repeated misses: "If you keep adding emphasis to a `CLAUDE.md` line and Claude still misses it, that's a sign the line belongs in a hook. The reverse holds too: if you have hooks for things that are only preferences, delete them and let Claude decide." The page also says "`CLAUDE.md` is for guidelines, and Claude is allowed to decide a guideline doesn't apply," and "keep the enforced set small." — [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- Requirements before design, through an interview and a spec: "Interview me until you could write the spec, then write it to SPEC.md." Then: "Once `SPEC.md` exists, start a fresh session to build from it, so the build begins with a clean context and a written definition of done." — [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- Path-scoped rules and skills for design standards: "If a rule only matters in one part of the codebase, put it in `.claude/rules/` with a `paths:` filter so it only loads when Claude is actually working there." Skills hold team knowledge: "A more capable model knows more about engineering, but not how *your* team does a release." The rule for what to write down is "only write down what Claude can't find on its own." — [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- Review can cause overengineering: "A reviewer that's asked to find problems will always find *something*. If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen." Anthropic recommends reviewing against the spec and adding "skip style". — [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- A fresh reviewer helps; delegating the same task doesn't: "Handing the same task to a subagent doesn't make the answer any better. A fresh reviewer does help, because it hasn't seen your reasoning." `/code-review` "reviews the diff in a fresh subagent that never saw your conversation." — [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- Repeated corrections: "If you've corrected the same thing twice and it's still wrong, a third correction mostly adds to a conversation that already contains two failed attempts for Claude to keep re-reading. `/clear` plus one new prompt that folds in what you learned works better almost every time." — [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- Root-cause-oriented bug prompt example: "users report login fails after the session times out. look at token refresh in src/auth/, write a failing test that reproduces it, then fix it." — [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)

### Inferences
- The docs back the analysis's "Solution D/E" direction (remove emphasis and over-verification, use positive examples, enforce only zero-exception rules in hooks). They warn that piling on more rules makes the model over-apply them, which matches the observed failure.
- Anthropic's anti-overengineering prompt is about scope (no extra features, helpers, or defensive code). It doesn't cover the user's domain-modeling failures: type codes vs classes, hierarchies, mechanism/policy, package cohesion, business relationships. No official doc tells Claude which design to prefer. Those standards have to come from the project, as path-scoped rules or a design skill with positive examples.
- The "minimum complexity" line could be read as "use an enum or table, not a class." The project's design skill should say what counts as the right modeling unit, so that "minimal" doesn't mean "flat data."
- Interview, then SPEC.md, then a fresh session matches the user's "requirements before design" ordering (trait 2-23/2-24). Reviewing against SPEC.md with "skip style" counters the reviewer-driven overengineering spiral.

### Gaps
- I didn't find a current official page on plan mode as a design-quality tool. The 2026 best-practices page doesn't feature plan mode; it pushes interview/spec, checks, and hooks. Earlier (2025) versions emphasized "explore, plan, code, commit" [older, not re-fetched].
- No Anthropic doc addresses domain modeling, OO design, type hierarchies, or root-cause analysis methods (Five Whys) directly.

## Q2. What evidence exists on LLM code design quality, and which mitigations work?

### Takeaway
Industry and academic evidence points the same way. AI-era code shows more duplication and less moving/refactoring of code. Agent refactorings are mostly shallow (renames, type changes, annotations), not structural design changes. Architecture conformance varies a lot by model. The mitigations with consistent backing are computational "sensors" (architecture tests, fitness functions, duplication/complexity checks) plus a steering loop that hardens the harness when an issue recurs. Controlled studies of those mitigations' effect on agents are scarce.

### Cited Findings
- GitClear 2025 (industry, correlational): moved code (a reuse/refactoring signal) fell from 24.8% of changed lines in 2021 to 9.5% in 2024, and copy/pasted code rose from 8.4% to 12.3%. 2024 was the first year copy/paste exceeded moved lines. These figures come from secondary coverage of [GitClear's report](https://www.gitclear.com/ai_assistant_code_quality_2025_research), for example [devclass, 2025-02-20](https://devclass.com/2025/02/20/ai-is-eroding-code-quality-states-new-in-depth-report/). The primary report was not fetched, and the study doesn't prove AI wrote the duplicated lines. [older, early 2025]
- Agentic refactoring (Horikawa et al., arXiv 2511.04824, Nov 2025; 15,451 refactoring instances in 12,256 PRs from Java projects): "agentic refactoring contains a slightly larger share of low-level, consistency-oriented edits than human refactoring (27.6% vs. 24.4%)". The top operations are "Rename Variable (7.6%)" and "Change Variable Type (6.8%)". It "yields small but statistically significant improvements in structural metrics, particularly for medium-level changes," but "the measured metric improvements from these frequent low-level refactorings remain limited." — [arXiv 2511.04824](https://arxiv.org/abs/2511.04824)
- Ottenhof et al. (MSR 2026; agents include Claude Code, Copilot, Cursor, Devin, Codex): agent refactorings are "dominated by annotation changes," while developers show "the diverse structural improvements typical of developers." Cursor showed "a statistically significant increase in refactoring smells." — [arXiv 2601.20160](https://arxiv.org/abs/2601.20160)
- Architecture conformance (Slater, arXiv 2512.04273, Dec 2025, single-task pilot): "0% violation rate for GPT-5.1" under Hexagonal Architecture constraints, while "Llama 3 demonstrated an 80% Architectural Violation Rate," often "bypassing interface adapters to create illegal circular dependencies between Domain and Infrastructure layers." — [arXiv 2512.04273](https://arxiv.org/abs/2512.04273)
- Böckeler / martinfowler.com (2026-04-02), on the harness framework. Guides "anticipate the agent's behaviour and aim to steer it before it acts". Sensors "observe after the agent acts and help it self-correct". Computational controls are "deterministic and fast". Inferential ones (AI review) are "slower and more expensive; results are more non-deterministic." — [Harness engineering for coding agent users](https://martinfowler.com/articles/harness-engineering.html)
- Same source, steering loop: "Whenever an issue happens multiple times, the feedforward and feedback controls should be improved." An architecture-fitness category "groups guides and sensors that define and check the architecture characteristics of the application," with ArchUnit module-boundary checks as the example. — [martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)
- Same source, harnessability: "Not every codebase is equally amenable to harnessing." Without strong typing or clear module boundaries, "those controls aren't available to build." — [martinfowler.com](https://martinfowler.com/articles/harness-engineering.html)
- Practitioner reports (blogs, not controlled studies): ArchUnit rules run in CI so a boundary breach fails the build and the agent must fix it — [DEV: ArchUnit as a guardrail for AI-generated code](https://dev.to/lbobylev/archunit-as-a-guardrail-for-ai-generated-code-2bpe). A Python project ran 18 architecture tests (~0.4 s) to stop Claude Code crossing layer boundaries — [DEV](https://dev.to/pedromurinelo/how-i-prevented-claude-code-from-breaking-my-architecture-with-18-tests-that-run-in-04-seconds-1f1o). Fitness functions and ArchUnit/NetArchTest/PyTestArch/arch-go are framed as architecture governance — [O'Reilly Radar](https://www.oreilly.com/radar/how-agentic-ai-empowers-architecture-governance/). archfit outputs repair tasks meant for agent loops — [archfit](https://pkg.go.dev/github.com/alexei-led/archfit@v0.12.1).

### Inferences
- Agents don't do structural design refactoring on their own (renames and annotations dominate). Design improvement has to be asked for explicitly and checked, not hoped for.
- Several of the user's traits are mechanically checkable: duplicated utilities (2-27), exporting everything, overly fine package splits (2-12), dependency direction (mechanism depending on policy, 2-9), and centralized registries (2-8). These belong in computational sensors: duplication detectors, unused-export checks, dependency rules, package metrics. A rule in prose is weaker.
- Judgments like "type code should be a class" or "does the model carry business relationships" are not computationally checkable. They need guides (a design skill with good/bad examples) plus a fresh-context reviewer prompted against the design standard and spec.

### Gaps
- No controlled study found that measures whether design-rule skills, ADRs, or architecture tests reduce agent design defects. The evidence is practitioner reports.
- No study found on LLM agents modeling type codes as enums vs polymorphic classes, or on package granularity specifically.
- The primary GitClear report was not fetched; its numbers come from secondary coverage.

## Q3. Which established design references fit the specific failures?

### Takeaway
Classic refactoring and architecture references map directly onto the listed failures and could be cited as the "outside standard" in a design skill. I verified only Fowler's catalog entry and the strangler fig article this session. The other references below are from background knowledge, without fetched quotes.

### Cited Findings
- Fowler's Refactoring catalog entry "Replace Type Code with Subclasses" shows a `createEmployee(name, type)` with a type value turned into `Engineer`/`Salesman`/`Manager` subclasses. The listed aliases are "Replace Type Code with State/Strategy" and "Extract Subclass", and the inverse is "Remove Subclass". The motivation text wasn't in the fetched page. — [refactoring.com catalog](https://refactoring.com/catalog/replaceTypeCodeWithSubclasses.html)

### Inferences
These mappings come from background knowledge and are unverified this session:
- Traits 2-7 (behavior as values/enums/tables) and 2-10 (ignoring type hierarchies) map to Fowler's "Replace Type Code with Subclasses", "Replace Conditional with Polymorphism", and "Replace Primitive with Object", and to Larman's GRASP Polymorphism and Information Expert, plus his generalization guidelines ("100% rule", "Is-a rule").
- 2-9 (mechanism and policy mixed) maps to the mechanism/policy separation principle (Wulf et al., Hydra, 1975) and Martin's Clean Architecture dependency rule (policy shouldn't depend on details).
- 2-12 (packages split too finely) and 2-27 (duplicated utilities, exporting everything) map to Martin's package cohesion principles (REP, CCP, CRP) and coupling principles (ADP, SDP, SAP), plus Parnas's information hiding (1972).
- 2-8 (per-unit declarations centralized in one file) maps to the Open-Closed Principle and Information Expert (a declaration lives with the unit it describes).
- 2-11 (DB/API without business relationships) maps to Evans's Domain-Driven Design (ubiquitous language, aggregates) and Larman's domain model before design classes.
- 2-22 (no stepwise refinement) maps to Wirth's "Program Development by Stepwise Refinement" (CACM 1971).
- 3-1 (symptom patching) maps to Five Whys (Toyota/Ohno) and to the reproduce-with-a-failing-test-then-fix pattern in Anthropic's docs (Q1).
- Characterization tests (Feathers, *Working Effectively with Legacy Code*, 2004) are meant to pin behavior temporarily during refactoring, not to freeze tangled behavior as the spec. The user's complaint is consistent with misuse of the technique.
- Following Anthropic's "positive examples" advice, a design skill could quote each principle with a small before/after example, like Fowler's catalog format.

### Gaps
- Exact quotes and URLs for Larman, Martin (REP/CCP/CRP), Wirth, Parnas, Feathers, Wulf, and Five Whys weren't fetched; I hit the tool-call budget. The report writer should cite them as book references or verify them separately.
- The motivation text for Fowler's "Replace Type Code" entry wasn't available on the fetched page.

## Q4. What works for large refactors with agents (incremental, strangler fig, top-down) vs full rewrites?

### Takeaway
Anthropic's own harness research and Fowler's strangler fig guidance agree: one-shot and big-bang rewrites tend to fail. Work in one feature or one unit at a time from a written requirements list. Leave a mergeable clean state after each step. Replace incrementally behind existing seams. Use `/batch` with a reviewed plan for mechanical changes across many files.

### Cited Findings
- Anthropic, "Effective harnesses for long-running agents" (2025-11-26) [older]: "the agent tended to try to do too much at once—essentially to attempt to one-shot the app." The fix was that "the next iteration of the coding agent was then asked to work on only one feature at a time," guided by "a comprehensive file of feature requirements expanding on the user's initial prompt," and leaving a "clean state," meaning "the kind of code that would be appropriate for merging to a main branch." — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Fowler, "Strangler Fig Application" (2024-08-22) [older]: on big-bang replacement, "we've seen this simple-sounding plan go down in flames most of the time." Also: "much of that behavior is stuff that isn't really wanted, so building it is a waste," and "the reduced risk and earlier value from the gradual approach outweigh its costs." — [martinfowler.com](https://martinfowler.com/bliki/StranglerFigApplication.html)
- Claude Code's mechanical-change tool: "`/batch migrate every handler to the v2 response helpers` splits the work into 5 to 30 units and shows you the plan. Once you approve it, each unit gets its own worktree and opens a PR." — [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)
- Before unattended runs, check: "Does it know what done looks like? A goal condition, a spec file, or a failing test it has to turn green." — [Best practices for Claude Code](https://code.claude.com/docs/en/best-practices)

### Inferences
- The user's repeated full rewrites (3-6) are the documented failure mode, both one-shotting and big-bang replacement. A better sequence, assembled from these sources:
  1. Write the requirements/spec (interview, then SPEC.md).
  2. Write a top-level design: modules and the domain model, checked against the design skill.
  3. Add architecture tests encoding the target boundaries. They will fail at first, which documents the gap.
  4. Migrate one unit at a time with a strangler pattern, keeping each step mergeable.
  5. Review each step against the spec and design standard in a fresh context.
- Characterization tests should be scaffolding that gets deleted or replaced by spec-derived tests once a unit is migrated, so tangled behavior isn't frozen.

### Gaps
- No empirical study found comparing agent-driven incremental refactoring with agent-driven rewrites on outcomes.
- No official Anthropic guidance found on top-down decomposition or stepwise refinement by name.
