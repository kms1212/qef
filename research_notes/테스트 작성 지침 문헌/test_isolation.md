## Q1. What do xUnit Test Patterns, Kent Beck's Test Desiderata, Software Engineering at Google (and Fowler) say about test independence and fixture setup?

### Takeaway
All four sources agree: each test should build (or own) the state it changes, results must not depend on run order, and a fixture shared across tests that tests *mutate* is the canonical cause of erratic/flaky tests. Meszaros gives the escalation ladder explicitly: Fresh Fixture first; if too slow, Immutable Shared Fixture (shared read-only reference data + per-test fresh data for anything mutated); a mutable Shared Fixture only as last resort. "Chained tests" (later tests relying on data earlier tests created) are named as an anti-pattern with specific failure modes (Lonely Test, cascade of false failures).

### Cited Findings

**xUnit Test Patterns (Meszaros) — [General]**
- Erratic Test definition: "One or more tests are behaving erratically; sometimes they pass and sometimes they fail." Impact: removing the failing test to "Keep the Bar Green" produces a "Lost Test"; keeping a known failure "may obscure other problems". — [Erratic Test](http://xunitpatterns.com/Erratic%20Test.html)
- Cause **Interacting Tests**: "Tests depend on each other in some way." Symptoms: a test that works alone fails when another test is added/removed, another test fails or starts to pass, or a test is renamed/moved. — [Erratic Test](http://xunitpatterns.com/Erratic%20Test.html)
- Root cause: "Interacting Tests are usually caused by tests using a Shared Fixture … with one test depending in some way on the outcome of another test." "Anything the outlives the lifetime of the test can lead to interactions" (sic). — [Erratic Test](http://xunitpatterns.com/Erratic%20Test.html)
- Three reasons tests interact: depending on another test's fixture setup, depending on SUT changes made by another test, or "a collision caused by some mutually exclusive action … between two tests run in the same test run." Dependent tests then fail "for the wrong reason … giving a 'false negative'". — [Erratic Test](http://xunitpatterns.com/Erratic%20Test.html)
- "In general, depending on the order of test execution is not a good thing to do"; most xUnit frameworks "do not make any guarantees about the order of test execution". — [Erratic Test](http://xunitpatterns.com/Erratic%20Test.html)
- Remedy order for Interacting Tests: "Using a Fresh Fixture … is the preferred solution … It is pretty much guaranteed to solve the problem." If a Shared Fixture must be used, use an Immutable Shared Fixture by "creating from scratch those parts of the fixture that they intend to modify." For an unsatisfied dependency on data another test was supposed to create: "use Lazy Setup … to create them in both tests", put setup in a Creation Method / Test Helper. For leftover data collisions: Automated Teardown. — [Erratic Test](http://xunitpatterns.com/Erratic%20Test.html)
- Detection technique: "A quick way to find out whether we have any tests that do depend on each other is to run the tests in a different order from normal. Running the entire test suite in reverse order would do the trick nicely." — [Erratic Test](http://xunitpatterns.com/Erratic%20Test.html)
- **Lonely Test**: a test that "can be run as part of a suite but cannot be run by itself because it depends on something in a Shared Fixture that was created by another test (e.g. Chained Tests)". Fix: Fresh Fixture or Lazy Setup. — [Erratic Test](http://xunitpatterns.com/Erratic%20Test.html)
- **Interacting Test Suites**: "usually caused by tests in separate test suites trying to create the same resource. … the first one succeeds and the second one fails while trying to create the resource." (This matches the user's name-collision failures.) — [Erratic Test](http://xunitpatterns.com/Erratic%20Test.html)
- **Unrepeatable Test**: behaves differently on first vs subsequent runs; "The most common cause … is the use, either deliberate or accidental, of a Shared Fixture." — [Erratic Test](http://xunitpatterns.com/Erratic%20Test.html)
- **Test Run War**: random failures "when several people are running tests simultaneously"; "can only happen when we have a globally Shared Fixture"; DB contention from concurrent update/delete or read locks. Preferred fix Fresh Fixture; simpler fix "give each test runner their own Database Sandbox", which "will not, however, eliminate other sources of Erratic Test". — [Erratic Test](http://xunitpatterns.com/Erratic%20Test.html)
- **Resource Leakage** tip: "set the size of all resource pools to 1" so leaks fail fast. — [Erratic Test](http://xunitpatterns.com/Erratic%20Test.html)
- **Fresh Fixture**: "Each test constructs its own brand-new test fixture for its own private use." "When each test creates a Fresh Fixture, it prevents Erratic Tests … and is more likely to result in Tests as Documentation". "If we cannot use a Fresh Fixture because it slows the tests down too much, we should consider using an Immutable Shared Fixture … before resorting to a Shared Fixture." — [Fresh Fixture](http://xunitpatterns.com/Fresh%20Fixture.html)
- Fresh Fixture caveat: a per-test partition key in a shared DB "does not result in a Fresh Fixture since subsequent test runs could use the same fixture." — [Fresh Fixture](http://xunitpatterns.com/Fresh%20Fixture.html)
- **Shared Fixture** is motivated by "How can we avoid Slow Tests?" Two forms: a Prebuilt Fixture reused across runs, or "a fixture created by one test and reused by another test within the same test run". "The biggest issue … it can lead to 'collisions' between tests possibly resulting in Erratic Tests". Also leads to Fragile Fixture and Obscure Test (fixture not visible in the test). — [Shared Fixture](http://xunitpatterns.com/Shared%20Fixture.html)
- Shared Fixture slowness diagnosis: slow fixture setup "most commonly occurs when testing with real test databases … exacerbated by using the API of the system under test (SUT) to create the reference data since the SUT often does a lot of input validation". — [Shared Fixture](http://xunitpatterns.com/Shared%20Fixture.html)
- **Incremental / Chained Tests** variation: each test "builds upon the actions of a previous test operating on a Shared Fixture". Unlike a human tester, automated tests "just keep running … The resulting test results can obscure the real cause of the failure in a sea of red." Mitigation if kept: start each test with **Guard Assertions** "that document the assumptions the Test Method makes about the state of the fixture". — [Shared Fixture](http://xunitpatterns.com/Shared%20Fixture.html)
- Hard-coding DB keys of shared fixture objects into tests "would result in a Fragile Fixture"; keep references via a registry/finder instead. — [Shared Fixture](http://xunitpatterns.com/Shared%20Fixture.html)
- **Immutable Shared Fixture**: partition the fixture into "stuff that every test needs to have present but which is never modified by any tests" and "objects which any test needs to modify or delete. These objects should be built by each test as a Fresh Fixture." Rule: "if any test perceives something done by another test as a change to an object in the Immutable Shared Fixture, then it shouldn't be allowed". Typically reference data. — [Shared Fixture](http://xunitpatterns.com/Shared%20Fixture.html)
- **Anonymous Creation Method / Distinct Generated Value**: a creation helper "automatically creates a Distinct Generated Value … as the unique identifier for the object it is creating", "invaluable for avoiding Unrepeatable Test … by ensuring that every object we create is unique even across multiple test runs." Tests pass only the attributes they care about (Parameterized Anonymous Creation Method). — [Creation Method](http://xunitpatterns.com/Creation%20Method.html)

**Kent Beck, Test Desiderata — [General]**
- Isolated: "tests should return the same results regardless of the order in which they are run." Deterministic: "if nothing changes, the test result shouldn't change." Fast: "tests should run quickly." Specific: "if a test fails, the cause of the failure should be obvious." Predictive: "if the tests all pass, then the code under test should be suitable for production." — [Test Desiderata](https://testdesiderata.com/)
- Trade-offs: properties can interfere (more predictive → slower); the page notes composability can make tests both faster and more predictive (i.e., not every trade-off is real). — [Test Desiderata](https://testdesiderata.com/)

**Software Engineering at Google — [General]**
- Ch.11: "a test should contain all of the information necessary to set up, execute, and tear down its environment." "Tests should assume as little as possible about the outside environment, such as the order in which the tests are run." Also: they "should not rely on a shared database." — [SWE at Google ch.11](https://abseil.io/resources/swe-book/html/ch11.html)
- Ch.11 flakiness cost: "If each test has even a 0.1% of failing when it should not, and you run 10,000 tests per day, you will be investigating 10 flakes per day." "as you approach 1% flakiness, the tests begin to lose value." Google's flaky rate "hovers around 0.15%". "In most cases, flakes appear because of nondeterministic behavior in the tests themselves." — [SWE at Google ch.11](https://abseil.io/resources/swe-book/html/ch11.html)
- Ch.11 mix target: ~80% unit, 15% integration, 5% end-to-end. — [SWE at Google ch.11](https://abseil.io/resources/swe-book/html/ch11.html)
- Ch.14 (Larger Testing): large tests "are not isolated—these tests can collide with one another." "If a large test is nonhermetic, it is almost impossible to guarantee determinism: other tests or user state may interfere with it." Hermeticity = "the SUT's isolation from usages and interactions from other components than the test in question"; a hermetic SUT has "the least exposure to sources of concurrency and infrastructure flakiness." Shared environments: "the test might conflict with other simultaneous uses". — [SWE at Google ch.14](https://abseil.io/resources/swe-book/html/ch14.html)
- Ch.14 test data: distinguishes seeded data ("preinitialized into the system under test") from test-sent data; seeding "is often orders of magnitude more complex than the setup work done in a unit test"; writing seed data directly to storage "might bypass triggers and checks performed by the actual binaries that perform the writes." — [SWE at Google ch.14](https://abseil.io/resources/swe-book/html/ch14.html)

**Martin Fowler, "Eradicating Non-Determinism in Tests" — [General]**
- "Keep your tests isolated from each other, so that execution of one test will not affect any others." "Properly isolated tests can be run in any sequence." — [Fowler](https://martinfowler.com/articles/nonDeterminism.html)
- On explicit ordering/dependencies between tests, he favors isolation because it "gives you more flexibility in running subsets of tests and parallelizing tests." — [Fowler](https://martinfowler.com/articles/nonDeterminism.html)
- Rebuild state vs clean up: prefers rebuilding because with clean-up "one test will contain the bug, but another test will fail"; concedes "Rebuilding the database each time can add a lot of time". Trick: "conduct your tests inside a transaction, and then to rollback the transaction at the end of the test." Warns to "be wary of exceptions that occur during the tear-down." — [Fowler](https://martinfowler.com/articles/nonDeterminism.html)
- Quarantine: "Place any non-deterministic test in a quarantined area. (But fix quarantined tests quickly.)"; quarantined tests "are not helping you with your regression coverage." — [Fowler](https://martinfowler.com/articles/nonDeterminism.html)

### Inferences
- The user's situation (UI tests that create data later tests depend on, so they "cannot be removed or reordered") is, by Meszaros's vocabulary, a **Shared Fixture built by Chained Tests**, and the later tests are **Lonely Tests**. The name collisions they hit are **Interacting Tests / Interacting Test Suites** (two tests creating the same resource). The literature's fix is not to preserve the chain but to give each dependent test its own setup (Fresh Fixture via a Creation Method, or Lazy Setup), with read-only reference data allowed to be shared (Immutable Shared Fixture).
- A practical agent rule derivable from Meszaros: "a test may read shared seed data but must create (with a unique generated identifier) anything it mutates or asserts the existence/count of."
- "Run in reverse/shuffled order" and "run each spec alone" are the documented cheap checks for hidden dependencies.
- Guard Assertions are the documented mitigation if a chain must temporarily remain: fail fast with a message pointing at the precondition, rather than a cascade.

- Could not consult the printed book text; the web draft warns content changed. The "Faster Tests Without Shared Fixtures" and "Transaction Rollback Pain" sidebars were referenced but not available on the fetched pages.
- Test Desiderata page gives one-line definitions only; Beck's longer Medium essays on each property were not fetched.

## Q2. Playwright official docs: isolation, fixtures, worker-scoped fixtures, parallelism, per-worker DB/data, auth state reuse

### Takeaway
[Playwright] Playwright isolates browser state per test (fresh BrowserContext) but explicitly does **not** isolate server/DB state; the docs say keep tests isolated, call `test.describe.serial` "not recommended", and show worker-scoped fixtures keyed on `workerIndex`/`parallelIndex` to give each worker its own DB user/account. For auth, the recommended pattern is a setup project that saves `storageState`; when tests modify server-side state, use one account per parallel worker.

### Cited Findings
- [Playwright] Best practices: "Each test should be completely isolated from another test and should run independently with its own local storage, session storage, data, cookies etc." — [Best Practices](https://playwright.dev/docs/best-practices)
- [Playwright] "If working with a database then make sure you control the data." "Only test what you control." — [Best Practices](https://playwright.dev/docs/best-practices)
- [Playwright] Workers are OS processes; "You can't communicate between the workers." Each has its own isolated browser context. "Above all, keep your tests isolated from one another." — [Parallelism](https://playwright.dev/docs/test-parallel)
- [Playwright] Default scheduling: "Tests in a single file are run in order, in the same worker process" (files run in parallel). `fullyParallel` makes all tests in all files parallel. — [Best Practices](https://playwright.dev/docs/best-practices); [Parallelism](https://playwright.dev/docs/test-parallel)
- [Playwright] Serial mode: "You can annotate inter-dependent tests as serial. If one of the serial tests fails, all subsequent tests are skipped." "Using serial is not recommended." — [Parallelism](https://playwright.dev/docs/test-parallel)
- [Playwright] Worker ids: each worker has a unique `workerIndex` (starts at 0) and a `parallelIndex`; a restarted worker (after failure) keeps the same `parallelIndex` but gets a new `workerIndex`. Docs suggest using the worker index "to isolate user data in the database between tests running on different workers"; example worker-scoped `dbUserName` fixture creates a DB user per worker at worker start and deletes it at worker end; "All tests run by the worker reuse the same user." — [Parallelism](https://playwright.dev/docs/test-parallel)
- [Playwright] Fixtures: "Test fixtures are isolated between tests." Only fixtures a test uses are set up. "Test-scoped fixtures are torn down after each test"; worker-scoped "only torn down when the worker process … is torn down." Declare with `{scope: 'worker'}`. Example: an `account` fixture "shared by all tests in the same worker", username `'user' + workerInfo.workerIndex`. Automatic fixtures via `{ auto: true }`. — [Fixtures](https://playwright.dev/docs/test-fixtures)
- [Playwright] Global setup: project dependencies are "the recommended approach, as it integrates better with the Playwright test runner" (HTML report, traces, fixtures); `globalSetup` "lack[s] some features". Example: a `setup db` project ("create new database") with a `teardown` project that deletes data "after all tests have run". — [Global setup and teardown](https://playwright.dev/docs/test-global-setup-teardown)
- [Playwright] Auth: create a `setup` project as a dependency; save `page.context().storageState({ path: authFile })`; testing projects set `storageState` so "Tests start already authenticated". — [Authentication](https://playwright.dev/docs/auth)
- [Playwright] Shared account breaks when tests change server-side state (e.g., one test checks a setting another test changes, in parallel) → "tests must use different accounts"; recommended "One account per parallel worker" when "Your tests modify shared server-side state", using a worker-scoped fixture; "Use parallelIndex as a unique identifier for each worker." — [Authentication](https://playwright.dev/docs/auth)
- [Playwright] API login: when the app "supports authenticating via API that is easier/faster than interacting with the app UI", log in with `request.post(...)` and save `request.storageState(...)`. — [Authentication](https://playwright.dev/docs/auth)
- [Playwright] API testing use cases include "Prepare server side state before visiting the web application in a test" and "Validate server side post-conditions after running some actions in the browser"; example creates an issue via API then checks it in the UI list. — [API testing](https://playwright.dev/docs/api-testing)

### Inferences
- Playwright's browser-level isolation is automatic; data-level isolation is the author's job. With one shared server + DB, the documented Playwright mechanisms for data isolation are (a) per-worker identity/data via worker-scoped fixtures keyed by `parallelIndex`, and (b) per-test data via test-scoped fixtures with teardown.
- `parallelIndex` is the better key for long-lived per-worker resources (stable across worker restarts), `workerIndex` for something that must be unique per process lifetime — this follows from the documented restart semantics.
- Because serial mode skips all following tests on first failure, serial chains reduce diagnostic signal (consistent with Meszaros's "sea of red").

### Gaps
- Playwright docs do not prescribe how to isolate a single shared Postgres per worker beyond the per-worker user example; schema/database-per-worker is not shown on the fetched pages.

## Q3. Documented patterns for parallel E2E against a real DB, and their trade-offs

### Takeaway
Four documented families: (1) separate DB/schema per runner/worker (Meszaros "Database Sandbox", "DB Schema per TestRunner"; Rails per-worker DB suffix; Postgres template cloning), (2) unique data per test in a shared DB (Meszaros "Database Partitioning Scheme" + Distinct Generated Values), (3) transactional rollback (Meszaros, Fowler, Rails default) — which needs the test and the SUT to share one uncommitted transaction and so generally does not fit a browser test against a separately running server, and (4) cleanup/reset before tests (Cypress) or truncation per sandbox. Each trades isolation strength against setup cost and infrastructure work.

### Cited Findings
- [General] **Database Sandbox**: "a database is a primary cause of Erratic Tests … due to the fact that data may persist between tests"; give each user/runner a separate DB. It "will not prevent Unrepeatable Tests … or Interacting Tests" because tests within one run still share it. — [Database Sandbox](http://xunitpatterns.com/Database%20Sandbox.html)
- [General] Variants: **Dedicated Database Sandbox** (separate instance; "preferred … most flexibility"); **DB Schema per TestRunner** ("we can share an Immutable Shared Fixture … defined in a common schema and put each user's mutable fixture in their own private schema"); **Database Partitioning Scheme** (separate data sets in one DB; "less database administration overhead but more data administration overhead"; at test level "we give each test a unique key such as a CustomerNumber … This ensures that other tests within the same test run use different data", but it "still does not prevent Unrepeatable Tests unless we also use Distinct Generated Values"). — [Database Sandbox](http://xunitpatterns.com/Database%20Sandbox.html)
- [General] The app must be configurable so "the database to be used can be changed without modifying the code". — [Database Sandbox](http://xunitpatterns.com/Database%20Sandbox.html)
- [General] **Transaction Rollback Teardown**: the test "starts a new test transaction, sets up the fixture, exercises the SUT … At the end of the test, it rolls back". Leaves the DB "in exactly the same state". Prerequisite: SUT methods must "not start their own transaction and must never commit"; "we have to be sure that we are not doing anything that results in a commit anywhere in the tests or the code they exercise." — [Transaction Rollback Teardown](http://xunitpatterns.com/Transaction%20Rollback%20Teardown.html)
- [General] **Table Truncation Teardown**: not first choice for Fresh Fixtures; requires that you want all data in those tables removed and that "each Test Runner … has its own Database Sandbox"; "will not work if we are using a Database Partitioning Scheme"; suits DB Schema per TestRunner with immutable data in a separate shared schema. — [Table Truncation Teardown](http://xunitpatterns.com/Table%20Truncation%20Teardown.html)
- [Other tool: Rails] Default: "Rails automatically wraps tests in a database transaction that is rolled back once completed." Parallel tests fork processes and "The databases will be suffixed with the number corresponding to the worker." Parallel transactional code can "block each other because they are already nested under the implicit test transaction" → disable with `use_transactional_tests = false`. — [Rails Testing Guide](https://guides.rubyonrails.org/testing.html)
- [Other tool: Postgres] "`CREATE DATABASE` actually works by copying an existing database"; any DB can be named as `TEMPLATE`. Limitation: "no other sessions can be connected to the source database while it is being copied." — [PostgreSQL: Template Databases](https://www.postgresql.org/docs/current/manage-ag-templatedbs.html)
- [Other tool: Cypress] Anti-pattern "Coupling multiple tests together"; "Tests should always be able to be run independently from one another and still pass." Anti-pattern "Using after or afterEach hooks to clean up state"; best practice "Clean up state before tests run." "If the state you are trying to clean lives on the server - by all means, clean that state." Their reference app "resets and re-seeds its database via a custom Cypress task". — [Cypress Best Practices](https://docs.cypress.io/app/core-concepts/best-practices)
- [Community, not official] Testcontainers practice: one Postgres container per test process plus a fresh database per test; choose database-per-test "when pools, background consumers, advisory locks, migrations, or explicit commits make transaction wrapping unrealistic"; migrate+seed once then clone per test via template DB. — [qaskills blog](https://qaskills.sh/blog/testcontainers-postgres-per-test-database); [pytest-testcontainers](https://pypi.org/project/pytest-testcontainers/) (discourages function-scoped containers, favors session-scoped container + fresh DB per test; its speedup figure is unverified)

### Inferences (trade-off table)
| Pattern | Isolation | Cost / prerequisites | Fit for "one real server + one shared Postgres + browser tests" |
|---|---|---|---|
| Unique data per test (generated names/keys, test owns what it mutates) | Strong between tests if every created/asserted entity is unique and assertions are scoped to it; weak for global views (counts, "list is empty", global settings) | Cheapest; no infra change; requires creation helpers and scoped assertions; DB grows unless cleaned | Best first step; directly fixes name collisions; enables `workers > 1` only if no test mutates global state |
| Per-worker account/tenant (Playwright `parallelIndex` fixture) | Strong if the app is multi-tenant/user-scoped | Low; documented by Playwright | Good when data is naturally partitioned by user/org |
| Per-worker schema or database (template clone) | Strongest | Server must route to a DB per worker — with a single running server this needs either one server per worker or a tenant/DB selector; template copy needs no connections to template | High effort with one shared server process; natural if each worker can start its own server |
| Transaction rollback | Strong, fast | Test and SUT must share one uncommitted transaction; no commits anywhere | Generally not applicable to browser→HTTP server→DB (server runs its own transactions in another process); fits in-process integration tests |
| Reset/truncate before each test or file | Strong per sandbox | Must be per-sandbox (Meszaros); serializes if DB is shared | Only safe with `workers: 1` or per-worker sandbox |
- The rollback inapplicability for out-of-process servers is an inference from Meszaros's "must never commit" prerequisite plus the fact the Playwright browser talks to a separately running server; I did not find an official doc stating it for Playwright explicitly.

### Gaps
- Official Testcontainers docs were not fetched (search surfaced only community/vendor pages); per-test DB guidance above is community practice.
- No primary source found that quantifies the speedup of template-cloned DBs vs truncation for Postgres.

## Q4. Keeping runtime low without reducing what is verified

### Takeaway
Documented levers: set up state via API/DB instead of the UI (test each UI flow once, use it as a precondition elsewhere through APIs), reuse authentication state, make tests independent so they can run in parallel and be sharded (sharding balances best with `fullyParallel`), run only changed/failed specs during iteration, and remove fixed sleeps. Isolation is the precondition for most of these: dependent tests block parallelism, sharding, and subset runs.

### Cited Findings
- [Playwright] API setup: "Prepare server side state before visiting the web application in a test." — [API testing](https://playwright.dev/docs/api-testing); API login when it "is easier/faster than interacting with the app UI" — [Authentication](https://playwright.dev/docs/auth)
- [Other tool: Cypress] Anti-pattern "using your UI to log in"; "programmatically log into your application, and take control of your application's state"; "use cy.request() to get the session directly from your server". "Resetting tests is much slower than adding more assertions" (so don't split E2E tests into tiny single-assertion tests). — [Cypress Best Practices](https://docs.cypress.io/app/core-concepts/best-practices)
- [General] Seeding directly into storage "might bypass triggers and checks performed by the actual binaries that perform the writes" (argument for using the app's own API rather than raw SQL for setup when those checks matter). — [SWE at Google ch.14](https://abseil.io/resources/swe-book/html/ch14.html); contrast: creating reference data through the SUT API is slow because "the SUT often does a lot of input validation" — [Shared Fixture](http://xunitpatterns.com/Shared%20Fixture.html)
- [General] "Engineers don't wait for slow tests." "The best way to speed up a test is often to reduce its scope or to split a large test into two smaller tests". Timeouts "should be made tunable and reduced when running tests." — [SWE at Google ch.14](https://abseil.io/resources/swe-book/html/ch14.html)
- [General] "The slower a test suite, the less frequently it will be run, and the less benefit it provides." `sleep()`/`setTimeout()` add "unnecessary speed limits"; "actively poll for a state transition". — [SWE at Google ch.11](https://abseil.io/resources/swe-book/html/ch11.html); Fowler: "Never use bare sleeps … use a callback or polling." — [Fowler](https://martinfowler.com/articles/nonDeterminism.html)
- [General] Isolation "gives you more flexibility in running subsets of tests and parallelizing tests." — [Fowler](https://martinfowler.com/articles/nonDeterminism.html)
- [Playwright] Sharding: `--shard=x/y`; "Tests are split at the individual test level" with `fullyParallel: true`, otherwise file-level granularity (uneven shards). Merge with blob reporter + `npx playwright merge-reports`. — [Sharding](https://playwright.dev/docs/test-sharding)
- [Playwright] CLI: `--only-changed [ref]` "Only run test files that have been changed between 'HEAD' and 'ref'. Defaults to running all uncommitted changes. Only supports Git." `--last-failed` "Only re-run the failures." `--repeat-each <N>` and `--fail-on-flaky-tests` exist (useful to flush out order/flaky issues). `--workers` default 50% of logical cores. — [CLI](https://playwright.dev/docs/test-cli)
- [Playwright] Auth reuse via `storageState` avoids logging in per test. — [Authentication](https://playwright.dev/docs/auth)

### Inferences
- For the user's suite (~8 of 10 minutes is serial UI tests), the documented sequence is: (1) remove inter-test data dependencies by moving each test's preconditions into API/fixture setup with unique generated data (keeps the same UI verifications, since the UI flow that *creates* the data is still tested once in its own test); (2) then raise `workers` and enable `fullyParallel`; (3) optionally shard in CI. Steps 2–3 are unsafe before step 1 — the docs' own warning about shared server state applies.
- `--only-changed` selects by changed *test files*, not by changed product code, so it does not on its own select specs affected by a source change (per the CLI description). For local iteration it is still a valid narrowing; full runs remain needed before merge.
- `--repeat-each` and running a single spec in isolation are cheap agent-executable checks that a newly written test is independent and deterministic.

### Gaps
- No primary source found for "affected-test selection" from product-code changes in Playwright (dependency-graph based); only test-file-change selection is documented.
- No source quantifies UI-vs-API setup speed difference for Playwright specifically; Cypress's statement is qualitative.
