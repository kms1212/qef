# Test-layer allocation: what belongs in unit / component / integration / E2E-UI tests

Context for the report writer: the target project is TypeScript, Vitest unit tests for web and server (web tests use faked server responses), Playwright UI tests against a real server and one shared DB. Two failures: (a) 55 of 146 Playwright tests re-checked screen branches (text, button presence) already covered by web unit tests with faked responses; (b) when told to remove the duplication, agents deleted UI tests that were the only check of the real server-to-screen contract (e.g., a permission-limited user completing a request against the real server). The user wants overlapping tests made non-overlapping, not deleted. The existing qef testing skill (`skills/testing/SKILL.md`) already covers: say which product-code change would make the test fail; hand-computed expectations; test behavior, not constants and wording; mocks only for slow or external layers and faithful to the real structure; switch to integration when mock setup outgrows the test; mutation-style "would a plausible defect fail some test" check. It has **no rule about layer allocation, cross-layer duplication, or what an E2E/UI test should verify**. That is the gap these notes cover.

All sources were fetched on 2026-11-08.

## Q1. What do the pyramid, trophy, Google sizes/scopes, and honeycomb each say belongs at which layer?

### Takeaway
All four models agree on the principle: put each check in the cheapest layer that can actually detect the failure. Keep the top layer (broad E2E/UI against real parts) for what only it can see: real components, configuration and wiring working together along important user journeys. They disagree on how big the middle (integration) layer should be, mostly because they define "unit" and "integration" differently.

### Cited Findings
**Test pyramid (Cohn, via Fowler and Vocke)**
- Origin: "Most people know about the the Test Pyramid due to Mike Cohn, when he described it in his 2009 book Succeeding with Agile." — [Fowler, TestPyramid bliki](https://martinfowler.com/bliki/TestPyramid.html)
- Core point: "you should have many more low-level UnitTests than high level BroadStackTests running through a GUI." Tests run end-to-end through the UI are "brittle, expensive to write, and time consuming to run." — [Fowler, TestPyramid](https://martinfowler.com/bliki/TestPyramid.html)
- Fowler says the pyramid's cost premise is conditional: "If my high level tests are fast, reliable, and cheap to modify - then lower-level tests aren't needed." — [Fowler, TestPyramid footnote 2](https://martinfowler.com/bliki/TestPyramid.html)
- "UI test" and "end-to-end test" are different axes: "teams conflate the concepts of end-to-end tests, UI tests, and customer facing tests. These are all orthogonal characteristics… a rich javascript UI should have most of its UI behavior tested with javascript unit tests." — [Fowler, TestPyramid](https://martinfowler.com/bliki/TestPyramid.html)
- He proposes a middle layer of "SubcutaneousTests" run through the service/API layer, which "can provide many of the advantages of end-to-end tests but avoid many of the complexities of dealing with UI frameworks." — [Fowler, TestPyramid](https://martinfowler.com/bliki/TestPyramid.html)
- Vocke's two rules: "Write tests with different granularity" and "The more high-level you get the fewer tests you should have." — [Vocke, The Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)
- On UI testing, Vocke writes: "Testing your user interface doesn't have to be done in an end-to-end fashion… can be as simple as writing some unit tests for your frontend javascript code with your backend stubbed out." SPA framework tools let you "thoroughly test these interactions in a pretty low-level (unit test) fashion." — [Vocke](https://martinfowler.com/articles/practical-test-pyramid.html)
- Vocke on integration tests: "I like to treat integration testing more narrowly and test one integration point at a time by replacing separate services and databases with test doubles." — [Vocke](https://martinfowler.com/articles/practical-test-pyramid.html)
- Narrow vs broad integration tests. Narrow ones "exercise only that portion of the code in my service that talks to a separate service" and use doubles. Broad ones "require live versions of all services" and "exercise code paths through all services, not just code responsible for interactions." Fowler prefers narrow tests. With narrow tests in place, E2E is "only a final smoke test with a very limited range of paths tested." — [Fowler, IntegrationTest bliki](https://martinfowler.com/bliki/IntegrationTest.html)

**Google (Software Engineering at Google, Testing Blog)**
- Sizes cover resources: "small tests run in a single process, medium tests run on a single machine, and large tests run wherever they want." Scopes cover how much code is validated. Narrow scope validates "a small, focused part of the codebase". Medium scope verifies "interactions between a small number of components". Large scope validates "the interaction of several distinct parts of the system." — [SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)
- Target mix: "around 80% … narrow-scoped unit tests that validate the majority of our business logic", "15% medium-scoped integration tests that validate the interactions between two or more components", "5% end-to-end tests that validate the entire system." — [SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)
- "unit tests cannot verify the interactions between components." Large tests are reserved "for full-system end-to-end tests that are more about validating configuration than pieces of code." — [SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html)
- Named antipatterns. The ice cream cone is "engineers write many end-to-end tests but few integration or unit tests." The hourglass comes from tight coupling that makes dependencies hard to instantiate in isolation. — [SWE at Google ch. 11](https://abseil.io/resources/swe-book/html/ch11.html). Wacker defines the hourglass as a team that "uses end-to-end tests where integration tests should be used." — [Google Testing Blog, Just Say No to More End-to-End Tests (2015)](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html)
- Wacker gives "a 70/20/10 split" as "a good first guess", adding that "The exact mix will be different for each team, but in general, it should retain that pyramid shape." — [Google Testing Blog](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html)
- Wacker on the middle layer: "An integration test takes a small group of units, often two units, and tests their behavior as a whole… If two units do not integrate properly, why write an end-to-end test when you can write a much smaller, more focused integration test that will detect the same bug?" — [Google Testing Blog](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html)
- Larger tests exist for fidelity: "The primary reason larger tests exist is to address fidelity." Unit tests miss unfaithful doubles, configuration ("Unit tests alone cannot verify this compatibility") and emergent behavior. Larger tests are meant "to ensure the overall behavior for specific user journeys is as intended." — [SWE at Google ch. 14](https://abseil.io/resources/swe-book/html/ch14.html)
- Chapter 14 also says: "A good design includes a test strategy that identifies risks and larger tests that mitigate them," and larger tests "must still be made as small as possible." — [SWE at Google ch. 14](https://abseil.io/resources/swe-book/html/ch14.html)

**Testing trophy (Kent C. Dodds)**
- The trophy has four layers: static (Flow/ESLint, i.e. types and lint), unit, integration and E2E. The motto, credited to Guillermo Rauch, is "Write tests. Not too many. Mostly integration." It holds that "Integration tests strike a great balance on the trade-offs between confidence and speed/expense." — [Dodds, Write tests](https://kentcdodds.com/blog/write-tests)
- Definitions: a unit is "a single function, class, or object that contains logic", with collaborators absent or mocked. "Integration tests are those which test multiple units integrating with one another." Integration tests may cover "entire pages with HTTP requests mocked via MSW." E2E is "the place where you attempt to validate that things work without any (or more practically 'as little as possible') mocking in place." — [Dodds, The Testing Trophy and Testing Classifications](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications)
- "the idea behind integration tests is to mock as little as possible". In practice that means network requests (MSW) and animations. Moving up the trophy raises cost and slowness and also the "confidence coefficient". Each check should go to the layer that fits it, e.g. coupon-calculator edge cases belong in unit tests and type errors in static analysis. — [Dodds, Static vs Unit vs Integration vs E2E Tests](https://kentcdodds.com/blog/static-vs-unit-vs-integration-vs-e2e-tests)
- Testing Library principle: "The more your tests resemble the way your software is used, the more confidence they can give you." — [Testing Library, Guiding Principles](https://testing-library.com/docs/guiding-principles)
- Mapping to the target project: a web Vitest test that renders a screen with faked server responses is a trophy "integration" test (page plus mocked HTTP). It is not an E2E test. Playwright against the real server and DB is the trophy's E2E layer.

**Testing honeycomb (Spotify, microservices)**
- There are three kinds. Integrated tests ("A test that will pass or fail based on the correctness of another system") should be the fewest, "ideally none". Integration tests "verify the correctness of our service in a more isolated fashion while focusing on the interaction points", exercising "both input and output of the service". Implementation-detail tests are for code "naturally isolated and [with] an internal complexity of their own." — [Spotify Engineering, Testing of Microservices (2018)](https://engineering.atspotify.com/2018/01/testing-of-microservices)
- Rationale: "The biggest complexity in a Microservice is not within the service itself, but in how it interacts with others." Too many unit tests "restricts how we can change the code without also having to change the tests." — [Spotify](https://engineering.atspotify.com/2018/01/testing-of-microservices)

**Disagreements between sources**
- Size of the middle layer: the pyramid and Google (80/15/5, 70/20/10) put most tests in unit tests. The trophy and honeycomb put most in integration. Fowler attributes much of this to definitions: the "difference is probably illusory due to different definitions of 'unit test'." — [Fowler, TestPyramid](https://martinfowler.com/bliki/TestPyramid.html). Dodds's "integration" (component plus mocked network) is roughly Fowler's "sociable unit test" or Vocke's UI unit test with the backend stubbed.
- Fowler links Adrian Sutton's LMAX account that "end-to-end tests can play a large and valuable role", and footnote 2 drops lower-level tests when high-level ones are cheap. The cost premise is therefore empirical, not a law. — [Fowler, TestPyramid](https://martinfowler.com/bliki/TestPyramid.html)
- Spotify's "integrated" (depends on another system being correct) is not Google's "large". A Playwright test against one's own real server and DB is "integration" in the honeycomb sense, since it does not depend on another team's system. It is large/E2E in Google's and the pyramid's sense.

### Inferences
- Every model separates two questions that the agents merged. (1) Does this screen show the right thing for each server response? That is screen logic, a lower layer, and the faked-response web tests own it. (2) Does the real server, with real auth, data and serialization, produce a response the real screen handles correctly along a journey a user takes? Only a layer with real parts can answer that, here Playwright. Failure (a) ran question 1 in the Playwright layer. Failure (b) deleted the only tests of question 2.
- Because names disagree across sources, the agent guideline should define layers by **what is real vs faked** in the test (which boundaries are crossed for real), not by labels such as "unit" or "integration".

### Gaps
- I did not read Cohn's *Succeeding with Agile* (2009) directly. Cohn's views are reported via Fowler's bliki and Vocke.
- I found no primary source giving a percentage mix for a frontend+server monolith with a single shared DB. Google says the mix varies by team.

## Q2. When is duplicating an assertion across layers waste, and when does the higher-level test hold unique value?

### Takeaway
The sources say a high-level test is waste when it only re-checks conditions that lower-level tests "confidently" cover. The same sources say to keep the high-level test, narrowed to "the part that the lower-level tests couldn't cover", whenever it adds confidence that lower tests cannot give. The usual cases are the real wiring, configuration or contract behind the doubles the lower tests use. The prescribed fix for overlap is to trim the higher test's assertions to its unique part, not to delete it wholesale.

### Cited Findings
- Vocke frames duplication as a cost: "duplicating tests throughout the different layers of the pyramid… there is [such a thing as too many tests]. Every single test in your test suite is additional baggage and doesn't come for free." — [Vocke, Avoid Test Duplication](https://martinfowler.com/articles/practical-test-pyramid.html)
- Two rules: "If a higher-level test spots an error and there's no lower-level test failing, you need to write a lower-level test" and "Push your tests as far down the test pyramid as you can." — [Vocke](https://martinfowler.com/articles/practical-test-pyramid.html)
- The condition for removal: "If you have tested all conditions confidently on a lower-level test, there's no need to keep a higher-level test… It just doesn't add more confidence." — [Vocke](https://martinfowler.com/articles/practical-test-pyramid.html)
- **The counter-rule, which matters most for failure (b):** "Let's phrase this differently: If a higher-level test gives you more confidence that your application works correctly, you should have it." His example: a controller unit test "won't tell you whether the REST endpoint this Controller provides actually responds to HTTP requests. So you move up the test pyramid and add a test that checks for exactly that - but nothing more. You don't test all the conditional logic and edge cases that your lower-level tests already cover… Make sure that the higher-level test focuses on the part that the lower-level tests couldn't cover." — [Vocke](https://martinfowler.com/articles/practical-test-pyramid.html)
- On deletion Vocke is conditional, and he prefers replacement: "I delete high-level tests that are already covered on a lower level (given they don't provide extra value). I replace higher-level tests with lower-level tests if possible." — [Vocke](https://martinfowler.com/articles/practical-test-pyramid.html)
- On E2E he writes: "you have lots of lower levels in your test pyramid where you already tested all sorts of edge cases and integrations with other parts of the system. There's no need to repeat these tests on a higher level." — [Vocke, End-to-End Tests](https://martinfowler.com/articles/practical-test-pyramid.html)
- Fowler calls high-level tests "a second line of test defense": "If you get a failure in a high level test, not just do you have a bug in your functional code, you also have a missing or incorrect unit test… before fixing a bug exposed by a high level test, you should replicate the bug with a unit test." — [Fowler, TestPyramid](https://martinfowler.com/bliki/TestPyramid.html)
- What only the real layer catches is the gap between doubles and reality. "a test might pass when the fake is used, but this same code path might not work properly in the real implementation." Mocks "are very likely to exhibit behavior that violates the API contract of the type being mocked." "A fake must have its own tests to ensure that it conforms to the API of its corresponding real implementation." — [SWE at Google ch. 13](https://abseil.io/resources/swe-book/html/ch13.html)
- "We prefer realistic tests because they give more confidence"; "A real implementation is preferred if it is fast, deterministic, and has simple dependencies." — [SWE at Google ch. 13](https://abseil.io/resources/swe-book/html/ch13.html)
- On double drift, testing against a double "raises the question of whether the double is indeed an accurate representation of the external service." Contract tests check "the contract of external service calls, but not necessarily the exact data." — [Fowler, ContractTest bliki](https://martinfowler.com/bliki/ContractTest.html)
- Dodds: mocking removes confidence in the connection between the code under test and the mocked dependency. — [Dodds, Write tests](https://kentcdodds.com/blog/write-tests) (paraphrase; the fetched text did not give a verbatim sentence)
- Larger tests cover unfaithful doubles, configuration and emergent behavior, which "Unit tests alone cannot verify." — [SWE at Google ch. 14](https://abseil.io/resources/swe-book/html/ch14.html)

### Inferences
- In the target project, every web Vitest test with a faked server response rests on an assumption that the real server returns that response for that user and state. Nothing at the unit layer checks that assumption. A Playwright test that runs a permission-limited user through a request against the real server is the only test of it. Per Vocke's counter-rule and Google ch. 13–14, that test has unique value. The duplicated part is only its branch-by-branch screen assertions (text, button presence for each case).
- The literature supports the user's correction: overlap is solved by **narrowing** the higher test to "exactly that - but nothing more". Keep the journey and the real-boundary assertion, such as a request accepted or rejected by the real server and the resulting persisted state, and move or leave exhaustive UI-branch assertions to the lower layer. Vocke's "delete" is explicitly conditional on "given they don't provide extra value."
- Another option suggested by Google ch. 13 and Fowler's ContractTest is a contract test. It checks that the real server's responses match the fakes the web unit tests use, so some real-boundary coverage can move down a layer instead of living only in Playwright. Make that move only when such a test is added. Deleting the Playwright test first loses the coverage.

### Gaps
- No source quantifies how much duplicated assertion is acceptable. All the guidance is qualitative ("confidently", "extra value").
- I did not find a primary source that tells you to treat one test as a mixture of a unique part and a duplicated part and trim it. This is an inference from Vocke's "exactly that - but nothing more."

## Q3. What should E2E/UI tests verify, and what should they avoid? (incl. Playwright docs)

### Takeaway
E2E/UI tests against real parts should cover a small number of high-value user journeys and the wiring and configuration between real components. They should assert user-visible outcomes and server-side postconditions. They should not enumerate edge cases or UI branches that lower layers cover, and they should not test third-party systems the team does not control. Playwright's docs focus on how to write such tests (user-visible behavior, isolation, controlled data, mocking only what you don't control). They do not say how many to write or which branches to put there.

### Cited Findings
- Vocke on journeys: "Think about the high-value interactions users will have with your application. Try to come up with user journeys that define the core value of your product and translate the most important steps of these user journeys into automated end-to-end tests." His e-commerce example is search, basket, checkout, "That's it… Maybe you'll find one or two more crucial user journeys… Everything more than that will likely be more painful than helpful." — [Vocke, End-to-End Tests](https://martinfowler.com/articles/practical-test-pyramid.html)
- On cost, Vocke says E2E tests "are notoriously flaky… Quite often their failure is a false positive", "require a lot of maintenance and run pretty slowly", so "aim to reduce the number of end-to-end tests to a bare minimum." — [Vocke](https://martinfowler.com/articles/practical-test-pyramid.html)
- Fowler: E2E is "only a final smoke test with a very limited range of paths tested" when narrow integration tests exist. — [Fowler, IntegrationTest](https://martinfowler.com/bliki/IntegrationTest.html)
- Google ch. 14: larger tests are for fidelity, configuration and emergent behavior, and "to ensure the overall behavior for specific user journeys is as intended". Browser tests that drive the frontend "as a third party… provides an extra layer of coverage." Still "a handful of large tests is preferable to an enormous one." — [SWE at Google ch. 14](https://abseil.io/resources/swe-book/html/ch14.html)
- Wacker lists E2E costs: "Finding the root cause for a failing end-to-end test is painful", "Many smaller bugs were hidden behind bigger bugs", "End-to-end tests were flaky at times". His sketch of a shared sign-in step adds: "Signing in to the service is broken. Almost all tests sign in a user, so almost all tests failed." — [Google Testing Blog](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html)
- Playwright: "Automated tests should verify that the application code works for the end users", meaning user-visible behavior rather than implementation details. — [Playwright Best Practices](https://playwright.dev/docs/best-practices)
- Playwright on isolation: "Each test should be completely isolated from another test" (own storage, data, cookies). Some duplication in setup is acceptable. — [Playwright Best Practices](https://playwright.dev/docs/best-practices)
- Playwright on third parties: "Only test what you control"; mock external services with the Network API. — [Playwright Best Practices](https://playwright.dev/docs/best-practices)
- Playwright on databases: "If working with a database then make sure you control the data." — [Playwright Best Practices](https://playwright.dev/docs/best-practices). This matters for a single shared DB, where data must be controlled per test.
- Playwright on API use: "Prepare server side state before visiting the web application in a test" and "Validate server side post-conditions after running some actions in the browser." — [Playwright API testing](https://playwright.dev/docs/api-testing)
- Playwright: "Locators come with auto waiting and retry-ability". Web-first assertions wait for the condition. — [Playwright Best Practices](https://playwright.dev/docs/best-practices)
- Playwright route mocking: with a fully mocked route, "No requests to the API will be made." — [Playwright Mock APIs](https://playwright.dev/docs/mock). Inference from this example, not a statement in the docs: a Playwright test that mocks one's own server is screen-logic coverage of the same kind as the Vitest faked-response tests, not real-contract coverage.
- On layout and look, Vocke says screenshot-comparison tools exist, and for usability and "looks good" you "leave the realms of automated testing." — [Vocke, UI Tests](https://martinfowler.com/articles/practical-test-pyramid.html)

**Disagreement**
- Vocke's "one or two more crucial user journeys" is far stricter than Google's 5–10% share of the suite. Dodds wants E2E with minimal mocking but sets no count. LMAX (linked by Fowler) is a counterexample with heavy E2E use.
- Playwright says to mock what you don't control. Dodds and Google say to mock as little as possible. These agree for one's own server: Playwright's advice is about third parties, so one's own server should stay real in the E2E layer.

### Inferences
- Positive list for a Playwright test against the real server and DB: (1) a journey step a user actually takes; (2) at least one assertion that depends on a real boundary, such as real authorization or role, real persistence (checked via UI or API postcondition), real serialization or error mapping, or real configuration; (3) data the test controls. Negative list: per-branch text and button-presence checks that a faked-response web test can produce, and edge-case enumeration.
- Role- and permission-dependent behavior is a strong E2E candidate because authorization is real only on the server. A faked response that says "allowed" proves nothing about whether the real server allows it.
- A useful per-test question follows from Google ch. 13–14: name the double or fake in the lower layer whose infidelity this test would expose. If none can be named, the test duplicates a lower layer.

### Gaps
- Playwright's docs say nothing about the number of E2E tests or which branches to cover. They give no layer-allocation guidance.
- I did not fetch Cypress's or Testing Library's docs on component testing vs E2E. They may hold more explicit component-vs-E2E rules.

## Q4. How to decide, when removing or moving a test, what unique coverage it holds

### Takeaway
The sources give one practitioner rule and some research evidence. The rule (Vocke) is to delete or replace a higher-level test only if lower tests cover "all conditions confidently" and it provides no "extra value". If a high-level failure has no matching lower failure, a lower test is missing. The research says code-coverage overlap is an unreliable redundancy signal. Removal should be judged by fault detection, with mutation analysis as the standard measure. Neither source gives a ready procedure for UI-vs-unit layers, so one has to be derived.

### Cited Findings
- Vocke: "I delete high-level tests that are already covered on a lower level (given they don't provide extra value). I replace higher-level tests with lower-level tests if possible… Beware of the sunk cost fallacy and hit the delete key." — [Vocke, Avoid Test Duplication](https://martinfowler.com/articles/practical-test-pyramid.html)
- Fowler's diagnostic: a failure in a high-level test means "you also have a missing or incorrect unit test". So the test is to replicate the bug lower first. — [Fowler, TestPyramid](https://martinfowler.com/bliki/TestPyramid.html)
- Google ch. 14 says a test strategy "identifies risks and larger tests that mitigate them". This implies large tests are judged by the risk they mitigate, not by overlapping lines. — [SWE at Google ch. 14](https://abseil.io/resources/swe-book/html/ch14.html)
- Research (test-suite reduction) finds that test redundancy detection based on coverage information can produce false positives that hurt fault detection. Reduction is judged by mutation-score loss. For permanent removal, reductions based on killed mutants preserve fault detection better than coverage-based ones. — summary of search results pointing to [Gyori et al., FSE 2014 (PDF)](https://mir.cs.illinois.edu/gyori/pubs/fse14reduction.pdf), [Teamscale 2020 test suite minimization (PDF)](https://teamscale.com/hubfs/26978363/Publications/2020-test-suite-minimization-swqd.pdf?hsLang=en), [Analyzing the reduction of test suite redundancy](https://silicon-austria-labs.elsevierpure.com/en/publications/analyzing-the-reduction-of-test-suite-redundancy). I did not read these papers directly. The claims come from search snippets and should be verified before quoting.
- Contract tests let some real-boundary coverage move down. They check a double against the real service, and when one fails the doubles and dependent code should be brought back in line. — [Fowler, ContractTest](https://martinfowler.com/bliki/ContractTest.html); [SWE at Google ch. 13](https://abseil.io/resources/swe-book/html/ch13.html)

### Inferences
These are derived procedures for the guideline. The sources support them, but none states them in this form.
- Unique-coverage check before removing or moving a UI test. For each assertion, (1) name the defect it would catch, such as a server permission rule change, a response-shape change, a route or config miswire, or a screen-branch logic error. (2) Ask whether some lower test fails on that defect **with the real component, not its fake**. Faked-response web tests cannot fail on server-side defects. (3) If no lower test fails, the assertion is unique. Keep it, or move it only after adding a lower test that catches the same defect (e.g., a contract or API test against the real server). (4) If the assertion is a screen-branch check whose defect a faked-response test already catches, remove that assertion only. Keep the journey and real-boundary assertions in the test.
- This turns the user's instruction ("make overlapping tests non-overlapping, don't delete them") into a rule. The unit of removal is the duplicated **assertion**, not the test. The test is removed only when every assertion in it is duplicated at a layer that runs the same real parts.
- Mutation-style check, consistent with the existing SKILL.md signal: introduce a plausible server-side mutation (drop a permission check, rename a response field) and see which tests fail. If only the UI test fails, it holds unique coverage.

### Gaps
- I found no practitioner source (Fowler, Google, Dodds, Playwright) that gives a step-by-step procedure for auditing cross-layer duplication. The procedure above is a synthesis.
- I did not read the mutation-based reduction papers in full. I relied on search summaries.
