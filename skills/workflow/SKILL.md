# workflow

사용자가 이 일에 qef를 지정했다. 이 일이 끝날 때까지 아래 표를 따라 단계 스킬을 `qef:<이름>`으로 부른다. 표대로 부르는 것은 사용자가 지정한 입구의 지시를 따르는 것이다. 사용자의 말이 이 스킬과 다르면 사용자의 말을 따른다.

## 단계 → 스킬

조건이 맞을 때 부르고, 이 세션에서 이미 불렀으면 다시 부르지 않는다. compaction 뒤에는 스킬의 앞부분만 남으니 지금 일에 쓰는 스킬을 다시 부른다. 맞는 조건이 없는 단계는 건너뛴다.

| 지금 눈앞의 일 | 부를 스킬 |
|---|---|
| 요청을 막 받았고, 범위를 적은 파일이나 말이 아직 없다 | `intake` |
| 새 타입·개념·저장 필드를 정하거나, 있는 것을 클래스·값·데이터 중 어디에 둘지 정한다 | `model` |
| 패키지·디렉터리·모듈 경계, 의존 방향, 데이터 흐름, 화면 경로를 정한다 | `layout` |
| 큰 일의 구조 목표를 쓴다 | `model`, `layout` |
| 사람이 쓰는 화면의 흐름, 경로, 보일 것, 순서, 입력, 문구를 정하거나 고치거나 리뷰한다 | `ux` |
| 화면의 모양(정렬, overflow, 강조, 상태, 디자인 토큰)을 정하거나 고치거나 리뷰한다 | `ux`, `ui` |
| 여러 부분에 걸친 변경을 시작하기 전이고 계획 파일이 없거나, 사용자가 계획을 시켰다 | `plan` |
| 정해진 부분을 맡기거나 여러 부분을 나란히 돌린다 | `execute` |
| 코드를 읽거나 쓴다 | `dev` |
| 테스트를 쓰거나 고치거나, 테스트가 실패했다 | `testing` |
| 오류, 예상 밖 동작의 원인을 찾는다 | `investigate` |
| 이미 있는 코드의 이름·위치·구조를 바꾸거나 옛 것을 새 것으로 바꾼다 | `refactor` |
| 사용자가 구조 평가를 시켰거나, 재작성 여부를 사용자에게 물어야 한다 | `structure-review` |
| 완료를 말하려 하거나, 사용자가 커밋·merge·PR을 시켰다 | `finish` |
| 웹 백엔드 API나 브라우저 프론트엔드의 구조를 정하거나 바꾼다 | `web` |
| 저장소에 `package.json`이나 `tsconfig.json`이 있다 | `js-ts` |

## 결정권

| 결정 | 누가 |
|---|---|
| 환경의 성격(스테이징·운영), 프로젝트의 수명(일회용 여부) | 사용자가 정한다 |
| 사용자가 정한 언어·프레임워크·버전과 그 변경 | 사용자가 정한다 |
| 새 외부 의존성(코드가 쓸 라이브러리·패키지, 작업 도구) | 사용자가 정한다. 후보와 이유를 보이고 설치할지 묻는다. 이미 설치된 것과 프로젝트의 공유 패키지는 묻지 않고 쓴다 |
| 정책(역할별 권한처럼 나중에 바꿀 수 있는 설정) | 정해야 할 때만 사용자가 정한다 |
| 기존 구조를 재작성할지 | 사용자가 정한다. 구조 평가를 보인다 |
| 큰 일의 성격(재작성 / 본궤도), 고정 목표, 구조 목표 | 사용자가 정한다. 승인 관문에서 보인다 |
| 큰 일을 닫을지 | 사용자가 `/qef:close`로 정한다 |

나머지는 전역 `CLAUDE.md`의 결정권 표를 따른다.

## 진행

- 시킨 일은 계획을 다시 묻지 않고 한다. 단계나 작업 사이에 "계속할까요?"를 묻지 않는다. 큰 일의 승인 관문은 예외다.
- 계획 문서, 커밋, worktree, reviewer는 사용자가 시켰거나 표의 조건일 때만 쓴다. 기본값으로 걸지 않는다.

## 테스트 시점과 무거운 명령

- 테스트는 한 부분을 끝냈을 때 그 부분에 해당하는 것만 돌린다. 부분을 바꾸는 동안 실패하는 테스트는 예상된 것이니, 그 실패를 없애려고 중간에 다시 돌리거나 구현을 맞추지 않는다. 자주 돌려도 시간과 token만 들고 구조는 나아지지 않기 때문이다.
- 빌드와 전체 테스트처럼 무거운 명령은 조율하는 세션 하나만, 통합하는 시점에 한 번 돌린다. 그 뒤 들어오는 수정(통합 리뷰의 지적을 반영한 수정 포함)은 그 수정이 바꾼 부분의 테스트만 돌린다. 맡긴 쪽은 자기가 바꾼 부분만 확인한다.

## 의존성

- 일에 필요한 도구나 라이브러리·패키지가 없으면, 다른 수단으로 조용히 대신하거나 직접 구현하지 않고 후보와 이유를 보여 설치할지 묻는다. 사용자가 명시적으로 쓰지 말라고 했으면 묻지 않는다.
- 직접 구현하기로 할 때는 이유와 이번에 검색한 출처를 밝힌다.
- 무엇을 쓸지 판단하는 질문은 `dev`에 있다.

## 기록과 보고

한 부분 크기의 일은 일 폴더를 열지 않고, 정한 것을 끝낼 때의 보고에 적는다.

큰 일이나 사용자가 지정한 일은 `.qef/<일 이름>/`에 파일을 역할별로 둔다.

- 열기: `${CLAUDE_PLUGIN_ROOT}/scripts/job.sh open ${CLAUDE_SESSION_ID} <일 이름>`
- 잇기: 새 세션은 `qef:workflow`를 일 이름을 인자로 불러 그 일에 묶인다. 회차 지시문에 일 이름을 적는다.
- 자료 더하기: `${CLAUDE_PLUGIN_ROOT}/scripts/job.sh add ${CLAUDE_SESSION_ID} <경로>...`. 사용자가 준 자료와 인계 문서를 넣는다. 256KB를 넘는 자료는 일 전체에 걸치는 줄을 출처와 함께 뽑아 `goal.md`로 승인받는다.

| 파일 | 담는 것 | 쓰는 법 |
|---|---|---|
| `goal.md` | 일의 이유, 일의 성격, 사용자 원문, 금지와 전제, 줄마다 출처가 달린 요구사항, 지금 동작, 후보 줄 | 사용자에게 보인 글 그대로만. 승인 뒤 더하거나 고칠 줄은 그 글을 보이고 답을 받는다 |
| `structure.md` | 승인된 타입 모델과 경계 중 아직 코드에 없는 것. 지금 구조는 적지 않는다 | 사용자에게 보인 글 그대로만. 승인 뒤 더하거나 고칠 줄은 그 글을 보이고 답을 받는다. 부분이 끝나 코드에 고정된 항목은 지운다 |
| `progress.md` | 끝난 부분, 다음 부분, 맨 끝의 `스냅샷: <tree>`, 보고 경로 | 덮어쓴다 |
| `reasoning.md` | 정한 것, 버린 안, 고치지 않은 지적 | 추가만 한다 |
| `sources.txt` | 끝까지 읽을 자료 목록 | 추가는 `job.sh add`, 빼기는 사용자 확인 |

자료는 일마다 한 번 끝까지 읽고, 내용이 바뀐 파일만 다시 읽는다. 다음 세션은 `goal.md`와 `structure.md`로 이어 가고, 다른 자료는 필요할 때 읽는다. 그래서 자료에서 일 전체에 걸치는 줄은 `goal.md`로 옮겨야 다음 세션에 닿는다.

사용자의 말이 일 전체에 걸치면(금지, 기준, 전제) 사용자 승인을 받아 `goal.md`로 올린다. 항목 줄로만 두면 다음 세션에 닿지 않는다.

옛 코드와 지금 동작의 지위는 일의 성격으로 갈린다.

| 일의 성격 | 옛 코드와 지금 동작 |
|---|---|
| 재작성 | 요구사항의 근거가 아니다. 옛 코드에서 본 줄은 `후보`로 적어 승인 관문에서 보이고, 승인 전에 만들지 않는다 |
| 본궤도 | 사용자가 정한 지금 동작과 구조를 지키는 것이 기본 요구사항이다. 에이전트 문서에 적힌 결정은 `qef:intake`의 출처 규칙을 따른다 |

정한 것과 스냅샷은 다음과 같이 적는다.

- 정한 것은 한 줄에 `무엇을 — 왜 — 틀렸을 때 드는 비용`으로 적고, 일을 끝낼 때 빠짐없이 사용자에게 보인다.
- 타입·소속·저장 필드를 정한 줄에는 `model`의 어느 질문에 어떻게 답했는지를, 경계·의존 방향을 정한 줄에는 `layout`의 질문과 답을 함께 적는다. 설계 문서에 이미 있는 것이나 옛 코드에서 옮기는 것을 쓰기로 한 것도 정한 것이다.
- 여러 부분에 걸친 일은 시작할 때와 부분을 끝낼 때 스냅샷을 찍어 적는다. 아래 명령은 커밋과 스테이징을 건드리지 않고, 추적되지 않은 새 파일까지 담은 tree를 출력한다. 부분의 diff는 `git diff <앞 스냅샷> <뒤 스냅샷>`으로 본다. 커밋이 아니라서 오래 두면 `git gc`가 지운다.

  ```sh
  idx=$(mktemp); cp "$(git rev-parse --git-path index)" "$idx" 2>/dev/null; GIT_INDEX_FILE=$idx git add -A; GIT_INDEX_FILE=$idx git write-tree; rm -f "$idx"
  ```

- compaction 뒤에는 기억보다 일 파일, 스냅샷, `git log`를 믿는다.

## 승인 관문

큰 일은 구현 전에 사용자가 고정 목표와 구조 목표를 확정한다. 타입을 보고 찾는 결함은 사용자가 먼저 찾아 왔고, 구현을 쌓은 뒤에는 버릴 양이 크기 때문이다.

1. 자료를 끝까지 읽고 `goal.md`를 쓴다. 쓰기 전에 일의 이유, 요구사항과 그 출처, 후보 줄을 본문에 보인다.
2. `model`과 `layout`을 불러 `structure.md`를 쓴다. 쓰기 전에 타입 트리를 `model`의 「타입 트리 표기」로 본문에 보인다. 디렉터리 트리로 대신하지 않는다. 구조 결정이 없는 일은 `구조 결정 없음` 한 줄로 승인받는다.
3. 승인된 구조를 먼저 타입 계약과 의존 규칙으로 코드에 넣고, 구현은 그 안에서 한다.
4. 다음 구조를 승인받기 전까지 구현을 이어 쌓지 않는다. 틀렸을 때 버리는 양을 줄이기 위해서다.
5. 사람이 쓰는 화면이 있는 일은 화면을 구현하기 전에 UX·UI 설계를 승인받는다(`ux`의 「근거 없는 추가를 막는다」).
