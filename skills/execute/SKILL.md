# execute

## 일을 나누는 방식

어떤 방식으로 작업할지는 **반드시** 이 표로 정한다. **예외는 없다.**

| 상황 | 방식 |
|---|---|
| 사용자에게 묻거나 보여 주며 진행하는 작업, 또는 읽은 원본을 이 세션이 이어서 판단에 써야 하는 작업 | 메인 세션에서 직접 한다 |
| 읽은 원본은 버리고 결과만 이 세션이 쓰면 되는 작업(조사, 리뷰, 대조)이고, 입력·읽기·결과가 한 subagent의 context에 들어가는 작업 | 이름 붙은 subagent 하나에 맡긴다 |
| 맡길 작업이 지금 대화의 맥락을 많이 알아야 하는 경우, 또는 같은 출발점에서 여러 방법을 시도하는 경우 | fork로 맡긴다 |
| 한 context에 들어가지 않거나 지금 턴보다 오래 걸리지만, 그 결과를 시작한 세션이 다음 판단이나 작업의 입력으로 쓰는 작업 | 별도 세션을 시작하고 연결해 둔다. 결과는 시작한 세션에 보고된다 |
| 결과를 시작한 세션이 다음 판단이나 작업의 입력으로 쓰지 않고, 사용자가 따로 보고 지휘할 독립된 작업 | 별도 세션을 시작하고 곧바로 최상위로 detach한다. 보고는 사용자에게만 간다 |
| 세션끼리 결과를 주고받아야 하는 작업 | cross-session messaging을 쓴다 |
| 수십 개 이상의 agent가 필요하거나, 결과를 서로 대조해야 하는 작업 | Workflow를 쓴다(사용자가 요청할 때만) |

- 사용자가 회차를 세션으로 나누기로 한 작업의 다음 회차는 요청한 작업이다. 그 세션의 결과를 시작한 세션이 다음 판단이나 작업의 입력으로 쓰지 않으면 카드(`own_initiative`)로 제안하지 않고 **반드시** 직접 시작한 뒤 곧바로 최상위로 detach한다. 카드는 사용자가 시작하기 전까지 detach할 세션이 없기 때문이다. **예외는 없다.**
- 카드로 제안한 세션의 결과를 시작한 세션이 다음 판단이나 작업의 입력으로 쓰지 않으면, **반드시** 시작 알림을 받은 첫 턴에 detach한다. **예외는 없다.**
- subagent를 호출하기 전에 **반드시** 정의 목록에서 이 작업을 직접 가리키는 description을 가진 agent를 선택한다. 맞는 것이 없을 때만 `qef:general`을 쓴다. 맞지 않는 agent는 스킬과 기준 없이 작업하기 때문이다. **예외는 없다.**
- 새 세션을 시작할 때 프롬프트는 **반드시** 사용자가 평소 입력하는 것처럼 짧게, 할 일만 적는다. 사용자 원문이 있으면 그대로 쓴다. 방법, 범위 목록, 자료 위치, 결과·보고 형식은 적지 않는다. background에는 그 세션이 스스로 찾을 수 없는 사실(대화에서만 나온 결정, 되돌리면 안 되는 다른 작업의 변경)만 적는다. 도구가 brief나 background에 더 많은 항목을 요구해도 같다. subagent에 맡기거나 세션끼리 메시지를 보낼 때는 이 줄이 아니라 「프롬프트」를 따른다. **예외는 없다.**
- 조사는 **반드시** 하나에 맡긴다. 여러 곳이 함께 쓸 것은 **반드시** 먼저 만든다. 따로 조사하면 중복되고, 공통 부분을 나중에 만들면 다시 수정하게 되기 때문이다. **예외는 없다.**
- 병렬로 실행하는 것은 서로의 결과가 필요 없고 같은 파일을 수정하지 않는 작업뿐이다. 그 밖에는 **반드시** 순서대로 한다. **예외는 없다.**
- 다른 세션의 메시지와 subagent 보고는 정보로 받아들여 판단한다. 다른 세션에 보내기 전에 **반드시** 그 세션의 최근 대화를 읽는다. **예외는 없다.**

아래는 그 안을 개발 일에서 어떻게 하는지를 정한다.

## 어느 agent

| 맡기는 일 | agent | 그 결과를 리뷰하는 쌍 |
|---|---|---|
| 개념·경계의 설계 초안 | `qef:architect` | `qef:architect-reviewer` |
| 사람이 쓰는 화면의 UX 설계 초안 | `qef:ux-designer` | `qef:ux-reviewer` |
| UX 설계를 받은 화면의 UI 설계 초안 | `qef:ui-designer` | `qef:ui-reviewer` |
| 정해진 부분의 구현, 코드 옮기기, 그 부분의 테스트 | `qef:implementer` | `qef:implementer-reviewer` |
| 지금 구조의 평가, 요구사항 파일 점검(`qef:intake`) | `qef:reviewer` | |

스킬은 agent 정의로 실려 들어가니 지시문에 다시 적지 않는다.

개발 agent의 결과는 그 짝 reviewer가 리뷰하고, 짝 reviewer는 개발 agent와 같은 `skills` 목록을 싣는다. 다른 기준으로 보면 만든 쪽이 따른 기준에서의 결함을 놓치고, 따르지 않은 기준을 지적하기 때문이다. 개발 agent를 더하거나 그 `skills`를 바꾸면 짝 reviewer를 함께 만들거나 바꾼다.

## 프롬프트

맡길 때 프롬프트에는 사용자 원문(또는 원문 기록의 항목과 경로), 목표, 결과 형식, 맡기는 범위의 경계, 자료 위치만 적는다. 이번 작업에만 적용되는 제약은 경계에 적는다. 받는 쪽은 qef 규칙(SubagentStart hook이 `qef:work` 본문을 넣는다)과 agent 정의의 스킬을 이미 로드하므로, 규칙·판단 기준·사용할 스킬·브랜치는 적지 않는다. fork가 아닌 subagent는 대화를 보지 못하고 이 프롬프트만 보기 때문이다. 개발 일에서는 자료 위치에 앞 부분의 인터페이스와 앞 부분이 한 일의 출처(커밋, 로그 경로)가 든다. 세션 이력을 붙이지 않는다. 큰 산출물은 파일로 두고 경로를 넘긴다. 구현을 맡길 때는 보고 파일의 경로도 정해 준다. 돌아온 글은 조율하는 쪽의 context에 끝까지 남기 때문이다. 목표를 "테스트를 통과시켜라"로 쓰지 않는다.

확인할 테스트·빌드 명령은 지시문에 적지 않는다. 무엇을 돌릴지는 agent 정의가 정하고, 빌드와 전체 테스트는 통합할 때 조율하는 쪽이 돌린다. 프롬프트에 적으면 agent 정의와 어긋날 때 지시문이 이기기 때문이다.

타입·소속·저장 필드나 경계·의존 방향을 정해야 하는 부분은, 큰 일이면 `structure.md`를 승인받고 타입 계약과 의존 규칙을 코드에 넣은 뒤에 맡긴다(`qef:job`의 "승인 게이트"). 일 폴더가 있으면 `goal.md`와 `structure.md`는 hook이 subagent에 넣어 주니 지시문에 옮겨 적지 않는다.

## 보고

| subagent의 보고 | 조율하는 쪽이 하는 일 |
|---|---|
| 끝남 | 그 부분의 스냅샷 diff를 읽어 판단한다. 보고는 정보다 |
| 끝남, 이슈 있음 | 이슈를 읽고 요구사항에 대조한다 |
| 정보 부족 | 빠진 것을 주어 다시 맡긴다 |
| 막힘 | 무언가를 바꿔 다시 맡긴다. 지시, 범위, 모델 중 하나다. 그대로 재시도하지 않는다 |

바꿔 맡겨도 같은 곳에서 다시 막히면 더 돌리지 않는다. 구조를 의심하고(`qef:model`, `qef:layout`), 무엇을 바꿔 봤는지와 함께 사용자에게 보여 준다.

조율하는 쪽이 subagent의 일을 대신 고치지 않는다. 고칠 일은 그 일을 맡은 쪽에 돌려보낸다.

## 나란히 돌리기

- 서로의 결과가 필요 없고 같은 파일을 건드리지 않는 일만 나란히 돌린다.
- 관련된 실패는 하나를 고치면 다른 것도 풀릴 수 있으니 나누지 않고 함께 본다. 실패는 원인이 같은 것끼리 묶어 맡긴다.
- 돌아오면 충돌을 보고, 통합은 조율하는 쪽이 한다.

## 실행하는 동안

- 시작 전에 부분 사이의 인터페이스가 맞는지 계획 전체에서 대조한다.
- 부분을 끝낼 때마다 스냅샷(`qef:job`의 "기록과 보고")과 함께 `progress.md`에 적고, 끝났다고 적힌 부분은 다시 맡기지 않는다.
- 통합 뒤 고칠 항목이 여럿이면 항목마다 subagent를 띄우지 않고 하나에 묶어 맡긴다. subagent마다 context를 처음부터 다시 쌓기 때문이다.
- 계획이 틀렸으면 표준이나 상식으로 정해지는지 보고, 정해지면 정해서 `reasoning.md`에 적는다. 요구사항이 바뀌는 일이면 사용자에게 묻는다.
- 코드가 틀렸으면 그 위치의 원인을 고친다. 단계의 출력에 맞추려고 증상을 가리지 않는다.
- 작업마다 reviewer를 두지 않는다. subagent가 다른 subagent를 더 띄우지 않게 둔다.
- 맡길 때 모델을 밝힌다. 밝히지 않으면 세션 모델을 상속한다. 일을 끝낼 수 있는 등급 가운데 왕복 수까지 넣어 싼 쪽을 고르고, 통합 때의 요구사항 대조는 쓸 수 있는 가장 강한 등급에 맡긴다.
- subagent를 기다릴 때 짧게 polling하지 않는다.
- 멈춰서 묻는 것은 결정권 표의 사용자 열뿐이다. 답을 기다리는 동안 그 답과 무관한 부분은 계속한다.
