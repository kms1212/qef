# finish

## 완료

완료는 요구사항과 구조 기준을 함께 만족한 상태다. 테스트 통과와 동작 확인은 완료의 근거에서 뺀다. 통과했다는 것만으로 끝났다고 말하지 않고, 실패했다고 끝나지 않은 것도 아니다(`qef:testing`).

- 요구사항 항목마다 바뀐 코드의 어디가 맡는지 댄다.
- 구조는 트리를 보고 `qef:dev`의 판정 뿌리로 본다.
- 맡긴 일의 "끝났다"는 보고가 아니라 diff로 본다.
- 주장마다 맞는 근거가 따로 있다. lint 통과는 컴파일 통과가 아니다.
- 구조 기준에 어긋난 곳이 남아 있으면 끝났다고 말하지 않고, 남은 일로 보고한다.

## 요구사항 대조 리뷰

여러 부분에 걸친 일을 통합할 때 `qef:reviewer`에 한 번 맡긴다. 만든 쪽은 자기 판단의 맹점을 보지 못하기 때문이다. 한 부분 크기의 일에는 두지 않는다.

- 지시문: 요구사항 파일, 계획, `progress.md`, 시작 스냅샷부터의 diff를 뜬 파일의 경로를 준다. 판단이나 "이것은 지적하지 말라"를 적지 않는다.
- 보는 것: 빠진 요구사항, 요청에 없는 추가, 잘못 이해한 요구사항, 계획의 "요구사항이 말하지 않은 입력"에서의 동작, `progress.md`에 정한 것의 근거.
- 이번에 정한 구조도 본다: 이번 변경에서 새로 정하거나 바꾼 타입·소속·저장 칸은 `qef:model`의 질문으로, 경계·의존 방향은 `qef:layout`의 질문으로 본다. `progress.md`에서 그 질문의 답이 없는 줄부터 지적한다. 에이전트가 쓴 설계 문서는 근거로 치지 않는다. 옛 코드의 동작은 요구사항의 근거일 수 있어도 구조의 근거는 아니다.
- 보지 않는 것: 문체와 취향. 저장소 전체 구조는 사용자가 시켰을 때 `qef:structure-review`로 본다.
- 형식: 지적마다 `파일:줄`, 무엇이 어긋나는지, 사용자가 무엇을 겪는지. 지적 개수 목표를 두지 않고, 없으면 없다고 쓴다. diff만으로 판정하지 못한 요구사항은 이유와 함께 따로 적는다.
- 받은 뒤: 코드에서 확인해 판단하고(판정하지 못했다고 적힌 요구사항도), 고칠 것은 subagent 하나에 묶어 맡긴다. 그 뒤에는 고친 diff만 한 번 더 보고, 전체 리뷰를 되풀이하지 않는다. 고치지 않기로 한 지적과 그때도 남은 지적은 더 돌리지 않고 `지적 — 판단 — 틀렸을 때 드는 비용`으로 `progress.md`에 적어, 끝낼 때 사용자에게 보인다.

## 커밋

커밋은 사용자가 시킬 때만 한다. 시켰으면 이 절차를 거친 뒤 한다.

1. `git status`와 `git diff`로 들어갈 것을 본다. 시크릿이 없는지, 시킨 범위의 파일만인지 본다.
2. 프로젝트의 포매터와 lint를 커밋할 파일에 돌린다.
3. 바꾼 부분의 테스트만 돌린다. 이미 그 부분을 끝낼 때 돌렸고 그 뒤로 바꾸지 않았으면 다시 돌리지 않는다.
4. 파일을 이름으로 스테이징하고, 왜 바꿨는지를 적어 커밋한다.

사용자가 단위마다 커밋하라고 했으면 그 단위를 따른다.

## 커밋 관문

qef의 hook은 `git commit` 앞에서 저장소 루트의 `.qef/commit-check`를 실행하고, 실패하면 커밋을 막는다. 판단이 필요한 것은 넣지 않고, lint와 바꾼 부분의 테스트처럼 결정론적인 것만 넣는다.

- 실행 파일로 두고, 커밋될 파일 목록을 표준 입력으로 줄마다 받는다. 0이 아닌 코드로 끝나면 막힌다.
- 프로젝트가 이미 git pre-commit hook을 쓰면 만들지 않는다.
- 이 파일이 없으면, 프로젝트의 lint와 테스트 명령으로 만들지 사용자에게 한 번 묻는다.
- 막히면 원인을 고친다. `--no-verify`로 넘기지 않는다.

## 브랜치 마무리

사용자가 시켰을 때만 한다.

- base 브랜치는 짐작하지 않고 확인한다.
- 통합 방식(로컬 merge, push와 PR, 그대로 두기)을 정해 주지 않았으면 선택지를 보이고 기다린다.
- 통합하는 시점에 조율하는 세션이 빌드와 전체 테스트를 한 번 돌린다. 실패가 있으면 `qef:testing`대로 가른다. 지우기 전에 merge 결과를 먼저 본다.
- 버리기는 사용자가 먼저 말했을 때만 한다. 사라지는 것(브랜치, 커밋 목록, worktree)을 적어 확인받는다.
- 자기가 만들지 않은 worktree는 건드리지 않는다. 지우기가 거부되면 `--force`를 쓰지 않고 남은 파일을 보여 묻는다.
- push가 거부되면 force-push하지 않고 원인을 찾는다.

## 끝낼 때의 보고

- 바뀐 것: 요구사항 항목별 결과
- 정한 것: `progress.md`의 줄 전부
- 바뀐 타입: 이번에 새로 정하거나 바꾼 타입의 트리(믹스인과 소속을 포함한다)
- 통합 테스트에서 실패한 것: 테스트 이름과 이번 일 때문인지
- 확인하지 못한 것
- 남긴 것과 이유
