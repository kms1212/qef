# finish

## 완료

완료는 요구사항과 구조 기준을 함께 만족한 상태다. 테스트 통과와 동작 확인은 완료의 근거에서 뺀다. 통과했다는 것만으로 끝났다고 말하지 않고, 실패했다고 끝나지 않은 것도 아니다(`qef:testing`).

- 요구사항 항목마다 바뀐 코드의 어디가 맡는지 댄다.
- 구조는 트리를 보고 `qef:dev`의 검증 기준으로 본다.
- 맡긴 일의 "끝났다"는 보고가 아니라 diff로 본다.
- 주장마다 맞는 근거가 따로 있다. lint 통과는 컴파일 통과가 아니다.
- 구조 기준에 어긋난 곳이 남아 있으면 끝났다고 말하지 않고, 남은 일로 보고한다.

## 요구사항 대조 리뷰

여러 부분에 걸친 일을 통합할 때, 그 일을 만든 개발 agent의 짝 reviewer(`qef:execute`)에 한 번씩 맡긴다. 요구사항 부분은 `qef:implementer-reviewer`, 구조 부분은 `qef:architect-reviewer`가 본다. 사람이 쓰는 화면이 바뀐 일이면 UX 부분은 `qef:ux-reviewer`, UI 부분은 `qef:ui-reviewer`도 본다. 모두 파일을 고치지 않으니 나란히 돌린다. 만든 쪽은 자기 판단의 맹점을 보지 못하기 때문이다. 한 부분 크기의 일에는 두지 않는다.

- 프롬프트: `goal.md`, 계획, `reasoning.md`, 시작 스냅샷부터의 diff를 뜬 파일의 경로를 준다. 화면 부분에는 화면 목록과, 바꾸기 전에 떠 둔 이전 버전 기준(`qef:ux`)의 경로도 준다. 판단이나 "이것은 지적하지 말라"를 적지 않는다.
- 요구사항 부분: 빠진 요구사항, 요청에 없는 추가, 잘못 이해한 요구사항, 계획의 "요구사항에 명시되지 않은 입력"에서의 동작, `reasoning.md`에 정한 것의 근거.
- 구조 부분: 이번 변경에서 새로 정하거나 바꾼 타입·소속·저장 필드는 `qef:model`의 질문으로, 경계·의존 방향은 `qef:layout`의 질문으로 본다. `reasoning.md`에서 그 질문의 답이 없는 줄부터 지적한다. 에이전트가 쓴 설계 문서는 근거로 치지 않는다. 옛 코드의 역할은 `qef:workflow`의 작업 유형 표를 따르고, 어느 쪽이든 구조의 근거는 아니다.
- 보지 않는 것: 문체와 취향. 저장소 전체 구조는 사용자가 시켰을 때 `qef:structure-review`로 본다.
- 형식: 지적마다 `파일:줄`, 무엇이 어긋나는지, 사용자가 무엇을 겪는지. 지적 개수 목표를 두지 않고, 없으면 없다고 쓴다. diff만으로 검증하지 못한 요구사항은 이유와 함께 따로 적는다.
- 받은 뒤: 코드에서 확인해 판단하고(검증하지 못했다고 적힌 요구사항도), 고칠 것은 subagent 하나에 묶어 맡긴다. 그 뒤에는 고친 diff만 한 번 더 보고, 전체 리뷰를 반복하지 않는다. 고치지 않기로 한 지적과 그때도 남은 지적은 더 돌리지 않고 `지적 — 판단 — 틀렸을 때 드는 비용`으로 `reasoning.md`에 적어, 끝낼 때 사용자에게 보여 준다.

## 브랜치 마무리

사용자가 시켰을 때만 한다.

- base 브랜치는 짐작하지 않고 확인한다.
- 통합 방식(로컬 merge, push와 PR, 그대로 두기)을 정해 주지 않았으면 선택지를 표시하고 기다린다.
- 빌드와 전체 테스트의 시점은 `qef:workflow`를 따른다. 실패가 있으면 `qef:testing`대로 구분한다. 지우기 전에 merge 결과를 먼저 확인한다.
- 버리기는 사용자가 먼저 말했을 때만 한다. 사라지는 것(브랜치, 커밋 목록, worktree)을 적어 확인받는다.
- 자기가 만들지 않은 worktree는 건드리지 않는다. 지우기가 거부되면 `--force`를 쓰지 않고 남은 파일을 표시해 묻는다.
- push가 거부되면 force-push하지 않고 원인을 찾는다.

## 끝낼 때의 보고

- 구조: `qef:dev`의 「보고」대로
- 변경 사항: 요구사항 항목별 결과
- 결정 사항: `reasoning.md`의 이번 줄 전부. 일 폴더가 없으면 일하며 정한 것 전부
- 바뀐 타입: 이번에 새로 정하거나 바꾼 타입의 트리(믹스인과 소속을 포함한다)
- 통합 테스트에서 실패한 것: 테스트 이름과 이번 일 때문인지
- 확인하지 못한 것
- 사람이 검토할 것: 기준으로 검증하지 못한 화면 판단(`qef:ux`)
- 남긴 것과 이유
- 큰 일 전체가 끝났으면 `/qef:close <일 이름>`으로 닫을 수 있다는 것
