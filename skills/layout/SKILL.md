# layout

원칙마다 의도, 규칙, 확인할 것을 둔다. 규칙은 경계를 정하는 그 순간에 답하고, 답을 설계에 남긴다. 다 만든 뒤 표로 대조하는 목록이 아니다. 규칙에 없는 상황은 그 원칙의 의도로 판단하고, 답이 갈리면 `qef:dev`의 「판단의 기준」으로 정한다.

사례는 두 파일에 있다. [references/examples.md](references/examples.md)는 판단을 보이려고 지은 도메인의 사례이고, [references/cases.md](references/cases.md)는 사용자가 실제 프로젝트에서 짚은 장면이다.

## 정하는 순서

1. 개념에서 출발한다. `qef:model`로 정한 개념(이미 코드에 있으면 그 개념)을 먼저 늘어놓는다. 파일과 디렉터리는 개념을 담는 자리이고, 개념보다 먼저 정하지 않는다.
2. 선례를 찾는다. 같은 스택, 같은 종류의 프로젝트가 이 위치를 어떻게 나눴는지 그 스택의 공식 문서와 GitHits(`githits-mcp`)에서 찾고, 출처와 함께 적는다. 스택이 구조를 정한 위치는 그 관례를 따른다. 「나누는 기준은 그 자리를 여는 사람이 찾는 것이다」의 표는 웹 서비스 예시이므로, 다른 종류의 프로젝트는 이 선례로 기준을 정한다.
3. 큰 경계에서 작은 경계로 내려간다. 저장소 루트, 패키지, 패키지 안의 디렉터리, 파일 순서다. 단계마다 「나누는 기준은 그 자리를 여는 사람이 찾는 것이다」과 「패키지는 함께 바뀌고 함께 쓰이는 큰 묶음이다」로 나누고, 위 단계가 정해지기 전에 아래를 정하지 않는다.
4. 코드를 쓰기 전에 「구조 트리 표기」로 보여 준다.
5. 정한 의존 규칙을 「의존 규칙은 검사로 둔다」대로 검사 도구 설정으로 만든다.
6. 어디까지 정하고 만들기를 시작할지 정한다. 계획을 고쳐 쓰는 일만 반복되면 더 고치지 않고 만들기를 시작한다.

## 구조 트리 표기

디렉터리마다 그 자리를 여는 사람이 찾는 것, 그 디렉터리가 바뀌는 이유, 의존해도 되는 곳을 적는다. 셋 중 하나를 적을 수 없으면 그 디렉터리의 경계가 아직 정해지지 않은 것이다. 구조는 글이나 그림이 아니라 이 트리로 보여 준다.

```text
apps/warehouse-api/src/
├── fulfillment/      찾는 것: 출고 개념 | 바뀌는 이유: 출고 비즈니스 규칙 | 의존: inventory, packages/order-contract
├── inventory/        찾는 것: 재고 개념 | 바뀌는 이유: 재고 계산 규칙 | 의존: 없음
└── routes/           찾는 것: 이 경로는 어디서 처리하나 | 바뀌는 이유: API 경로 | 의존: fulfillment, inventory
```

## 의존 규칙은 검사로 둔다

의존 방향, 금지 의존, 순환 금지는 판단이 필요 없는 규칙이라 글로 두지 않고 그 스택의 검사 도구 설정으로 둔다. 「구조 트리 표기」의 의존 칸이 그 설정의 출처다.

| 스택 | 도구 |
|---|---|
| JavaScript, TypeScript | dependency-cruiser, eslint-plugin-boundaries |
| Java | ArchUnit |
| Python | import-linter |

- 프로젝트에 이미 있는 것을 먼저 쓴다. 없으면 `qef:dev`의 「쓰기 전에 이미 있는 것을 찾는다」의 새 의존성 문단대로 한다. 그 스택에 맞는 도구가 없으면 그 사실을 보고한다.
- 규칙을 만들면 걸려야 할 의존을 하나씩 일부러 만들어 실제로 걸리는지 본다. 막을 의존만 막고, 막을 이유가 없는 의존까지 막지 않는다.
- 나누는 기준과 이름처럼 판단이 필요한 것은 검사로 만들지 않는다.

## 나누는 기준은 그 자리를 여는 사람이 찾는 것이다

**의도.** 사람은 무엇을 찾으려고 디렉터리를 연다. 나누는 기준이 그 찾는 것과 다르면 트리를 봐도 어디에 무엇이 있는지 알 수 없다. 한 자리의 기준을 다른 자리에 그대로 대면 그 자리를 여는 사람의 질문에 답하지 못한다.

**규칙**
- 이 위치를 여는 사람은 무엇으로 찾는가? 그 기준으로 나눈다. 다른 위치의 기준을 그대로 대지 않는다. 스택이 구조를 정한 위치는 그 스택의 관례를 따른다. 크기나 개수로 나누지 않는다.

  | 위치(웹 서비스 예시) | 여는 사람이 찾는 것 | 나누는 기준 |
  |---|---|---|
  | 웹서비스 모노레포 루트 | 어디에 배포되나 | 저장소 설정 + 배포 대상 |
  | 패키지의 위치(앱 안, 공용) | 누가 쓰나 | 쓰이는 곳 |
  | 공용 foundation 패키지 사이 | 왜 바뀌나 | 바뀌는 이유 |
  | 템플릿·양식 | 어떤 종류의 양식인가 | 템플릿끼리의 범주 |
  | 패키지 안의 도메인 코드 | 이 개념은 어디 있나 | 개념과 상속 관계 |
  | API 엔드포인트 선언 | 이 경로는 어디서 처리하나 | API 경로와 같은 구조 |

- 트리와 경로만 보고 무엇을 하는 파일인지, 어떤 타입이 어떤 타입을 상속·구현하는지 대략 알 수 있게 한다. 추상 타입은 위에, 구현체는 그 아래 디렉터리에 둔다.
- 한 파일이 여러 책임을 지거나 한 디렉터리에 여러 개념이 평평하게 섞이지 않게 한다. 정의를 관계없는 개념의 파일 안에 두지 않는다.
- 상위 경로가 말한 단어를 파일 이름에 반복하지 않는다. 타입 이름에 맞추려고 다시 적지 않는다. 공통점은 이름 접두사가 아니라 공통 상위 디렉터리로 묶는다.
- 사용처가 넓게 퍼져 도메인을 정하기 어려운 것과 전역 설정은 공통 위치에 둔다. 공통 위치 안에서도 그것이 다루는 개념 이름으로 나눈다.

**확인할 것**
- [ ] 트리의 디렉터리마다 「여는 사람이 찾는 것」이 적혀 있다.
- [ ] 경로만 보고 상속·구현 관계가 보인다.

근거: Robert C. Martin, "Screaming Architecture"(구조는 프레임워크가 아니라 시스템을 말해야 한다) (https://blog.cleancoder.com/uncle-bob/2011/09/30/Screaming-Architecture.html).

## 패키지는 함께 바뀌고 함께 쓰이는 큰 묶음이다

**의도.** 패키지를 작게 쪼개면 수가 늘고 평평해져, 하나를 바꿀 때 여러 패키지를 오가야 한다. 반대로 바뀌는 이유가 다른 것을 쓰는 쪽이 같다고 묶으면, 한쪽이 바뀔 때 상관없는 쪽까지 흔들린다.

**규칙**
- 쪼개지 않는다: 바뀌는 이유가 같은 것을 여러 패키지로 나누지 않는다. 새 패키지 대신 하위 디렉터리로 풀 수 있으면 그렇게 한다. 지금 분할이 맞다고 전제하지 않는다. 패키지는 거의 대부분 함께 쓰이는 큰 범위로 잡고, 그 하위 개념은 하위 디렉터리로, 거기서 다시 코드 모양(상속 관계 등)으로 나눈다.
- 붙이지 않는다: 사용처는 프로세스가 아니라 배포 쪽으로 센다. 백엔드의 여러 프로세스만 쓰는 것은 백엔드 안에 두고, 프론트엔드도 쓰는 계약만 공용에 둔다. 지금 앱 경계 때문에 공용이 필요해 보이면 그 경계부터 의심한다. 바뀌는 이유가 다른 것을 쓰는 쪽이 같다고 묶지 않는다. 모든 곳이 쓰는 것(오류 foundation)은 공통 위치로 뺀다. 인터페이스와 구현이 섞여 이름이 둘 중 하나를 가리지 않는지 본다.
- 공용 로직은 밖으로 뺀다. 공용으로 빼는 것을 범위 밖 일이나 위험으로 보지 않는다. 같이 쓰라고 만든 패키지가 있으면 그것을 쓴다.
- "그리고"로 이어지는 문장인지는 나누는 기준으로 쓰지 않는다. 어느 쪽으로든 말을 맞출 수 있기 때문이다.

**확인할 것**
- [ ] 패키지마다 그것을 쓰는 배포 대상이 둘 이상이거나, 그것만 따로 바뀌는 이유가 있다.
- [ ] 같이 쓰라고 만든 패키지를 두고 같은 것을 다시 만든 곳이 없다.

## 책임은 그것을 알아야 하는 모듈 하나가 진다

**의도.** 모듈이 알 필요 없는 것을 알면 그것이 바뀔 때 함께 바뀌어야 한다. 외부 조건에 맞추려고 내부 개념을 바꾸면 내부가 외부의 사정에 끌려다닌다.

**규칙**
- 외부 조건(라이브러리, 저장 방식, API 형태)에 맞추려고 내부 개념을 바꾸지 않는다. 내부 조건에 맞추려면 외부 코드를 바꾼다.
- 이 로직은 어느 모듈의 책임인가? 다른 모듈은 결과만 사용한다. 이 모듈이 알 필요 없는 것을 알게 하지 않는다.
- 비즈니스 로직이 ORM·DB 클라이언트를 직접 호출하지 않는다. API 경로 형태와 내부 구조를 서로 결합하지 않는다. 경로는 리소스 지향 설계 규칙으로, 도메인은 함께 바뀌는 것으로 따로 정한다.
- 코드는 그 실행 위치(서버·클라이언트)에 있어도 되는 곳에 둔다.
- 이 글자나 단위를 읽는 쪽은 어디인가? 화면만 읽는 표시 형식은 value object와 도메인에 두지 않는다. 저장되는 업무 레코드나 로직의 입력인 글자는 표시 형식이 아니다.
- 값 하나가 입력, API, 저장, 표시를 거칠 때 단계마다 받는 형태(타입)를 정한다. 어느 위치를 잡고 넘어갈지는 `qef:dev`의 기준으로 정한다.
- 한 곳에 속한 것은 그것이 쓰이는 곳에 가장 가깝게 둔다(colocation).

**확인할 것**
- [ ] 비즈니스 로직 파일에 ORM·DB 클라이언트 import가 없다.
- [ ] 화면용 표시 형식이 도메인이나 value object에 없다.

근거: Kent C. Dodds, "Colocation" (https://kentcdodds.com/blog/colocation).

## 채널, 메커니즘, 제한, 필드는 이유가 있을 때만 두고, 업무 제약은 구조로 둔다

**의도.** 이유 없는 채널이나 제한은 쓰는 쪽이 지켜야 할 것만 늘린다. 반대로 업무상 반드시 지켜야 하는 제약을 구조에 두지 않으면 사람이 기억해서 지켜야 한다.

**규칙**
- 과하지 않게 한다: 함께 쓰이는 것을 따로 보내는 채널을 두지 않는다. 내부 표현만 통일하면 되는 제한을 두지 않는다. 같은 사실을 두 필드·두 이름으로 나누지 않는다. 대비하는 상황이 실제로 일어나지 않는 메커니즘을 두지 않는다.
- 빼지 않는다: 업무상 지켜야 하는 제약(하나만 있어야 함, 승인 뒤에만 전송)은 구조로 둔다. 파악을 돕는 계층까지 과하다며 빼지 않는다.

**확인할 것**
- [ ] 채널·제한·필드마다 그것이 대비하는 실제 상황이 적혀 있다.

## 결함은 그것이 나온 계층의 결정에서 고친다

**의도.** 객체 설계에서 나온 결함을 이름이나 파일 위치에서 가리면, 같은 원인의 결함이 다른 곳에서 계속 나온다.

**규칙**
- 이 결함은 어느 계층의 결정에서 나왔는가? 이름·파일 계층에서 가리지 말고 그 계층으로 돌아간다. 문제 하나를 커버하는 구조가 아니라 같은 원인의 문제 전부를 커버하는 구조를 만든다.
- 큰 경계(패키지와 바로 아래 디렉터리)를 먼저 정하고 그 아래를 한 부분씩 정한다.

**확인할 것**
- [ ] 고친 결함마다 그것이 나온 계층과, 같은 원인의 다른 곳이 적혀 있다.

## 할 수 있는 작업마다 사용자가 도달할 길이 있다

경로의 구조는 여기서 정하고, 화면에서 무엇을 어떻게 표시할지는 `qef:ux`를 따른다.

**의도.** 권한이 있어도 화면에서 갈 길이 없으면 그 작업은 없는 것과 같다. 선언과 실제 호출이 어긋나면 화면은 있는데 막힌다.

**규칙**
- 할 수 있는 작업마다 화면에서 도달하는 경로가 있게 하고, 그것을 정적으로 확인할 수 있게 둔다.
- 업무 하나를 처음부터 끝까지 할 때 값이 어디서 들어오고 어디서 보이는지 정한다. 입력 형식은 안내 문구가 아니라 동작으로 유도한다.
- 상위 개념 없이 하위 화면이 열리지 않게 한다. 가진 권한보다 할 수 있는 작업이 많은 화면을 두지 않는다. 모듈이 선언한 작업과 실제로 호출하는 작업을 일치시킨다.

**확인할 것**
- [ ] 권한이 있는 작업마다 내비게이션 경로가 있다는 것을 정적으로 확인했다.
- [ ] 이 확인을 검사로 만들었으면, 할 수 있는 일보다 적은 화면과 많은 화면을 하나씩 만들어 둘 다 실패하는지 봤다.
