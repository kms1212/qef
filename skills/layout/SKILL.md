# layout

아래 질문은 경계를 정하는 그 순간에 답하고, 답을 설계에 남긴다. 다 만든 뒤 표로 대조하는 목록이 아니다. 답이 다르면 `qef:dev`의 검증 기준으로 정한다. 사례는 [references/examples.md](references/examples.md)에 있다.

코드를 쓰기 전에 디렉터리 scaffold를 먼저 보여 준다.

## 나누는 기준은 위치마다 다르다

이 위치를 여는 사람은 무엇으로 찾는가? 그 기준으로 나눈다. 다른 위치의 기준을 그대로 대지 않는다. 스택이 구조를 정한 위치는 그 스택의 관례를 따른다. 크기나 개수로 나누지 않는다.

| 위치(예시) | 여는 사람이 찾는 것 | 나누는 기준 |
|---|---|---|
| 웹서비스 모노레포 루트 | 어디에 배포되나 | 저장소 설정 + 배포 대상 |
| 패키지의 위치(앱 안, 공용) | 누가 쓰나 | 쓰이는 곳 |
| 공용 foundation 패키지 사이 | 왜 바뀌나 | 바뀌는 이유 |
| 템플릿·양식 | 어떤 종류의 양식인가 | 템플릿끼리의 범주 |
| 패키지 안의 도메인 코드 | 이 개념은 어디 있나 | 개념과 상속 관계 |
| API 엔드포인트 선언 | 이 경로는 어디서 처리하나 | API 경로와 같은 구조 |

## 패키지

- 쪼개지 않았는가: 바뀌는 이유가 같은 것을 여러 패키지로 나눴는가? 새 패키지 대신 하위 디렉터리로 풀 수 있는가? 지금 분할이 맞다고 전제하고 있는가?
- 붙이지 않았는가: 사용처는 프로세스가 아니라 배포 쪽으로 센다. 백엔드의 여러 프로세스만 쓰는 것은 백엔드 안에 두고, 프론트엔드도 쓰는 계약만 공용에 둔다. 지금 앱 경계 때문에 공용이 필요해 보이면 그 경계부터 의심한다. 바뀌는 이유가 다른 것을 쓰는 쪽이 같다고 묶었는가? 모든 곳이 쓰는 것(오류 foundation)은 공통 위치로 제거한다. 인터페이스와 구현이 섞여 이름이 둘 중 하나를 가리지 않는가?
- "그리고"로 이어지는 문장인지는 나누는 기준으로 쓰지 않는다. 어느 쪽으로든 말을 맞출 수 있기 때문이다.

## 경로와 이름

- 트리와 경로만 보고 무엇을 하는 파일인지, 어떤 타입이 어떤 타입을 상속·구현하는지 대략 알 수 있는가? 추상 타입은 위에, 구현체는 그 아래 디렉터리에 둔다.
- 한 파일이 여러 책임을 지거나 한 디렉터리에 여러 개념이 평평하게 섞이지 않았는가? 정의가 관계없는 개념의 파일 안에 있지 않은가?
- 상위 경로가 말한 단어를 파일 이름에 반복하지 않는가? 타입 이름에 맞추려고 다시 적지 않는다. 공통점은 이름 접두어가 아니라 공통 상위 디렉터리로 묶는다.

## 의존성과 책임 배치

- 외부 조건(라이브러리, 저장 방식, API 형태)에 맞추려고 내부 개념을 바꾸지 않는가? 내부 조건에 맞추려면 외부 코드를 바꾼다.
- 이 로직은 어느 모듈의 책임인가? 다른 모듈은 결과만 사용하는가? 이 모듈이 알 필요 없는 것을 알고 있지 않은가?
- 비즈니스 로직이 ORM·DB 클라이언트를 직접 호출하지 않는가? API 경로 형태와 내부 구조가 서로 결합되어 있지 않은가? 경로는 리소스 규칙으로, 도메인은 함께 바뀌는 것으로 따로 정한다.
- 이 코드가 그 실행 위치(서버·클라이언트)에 있어도 되는가?
- 이 글자나 단위를 읽는 쪽은 어디인가? 화면만 읽는 표기는 값 클래스와 도메인에 두지 않는다. 저장되는 업무 레코드나 로직의 입력인 글자는 표기가 아니다.
- 값 하나가 입력, API, 저장, 표시를 거칠 때 단계마다 받는 형태(타입)가 정해져 있는가? 어느 위치를 잡고 넘어갈지는 `qef:dev`의 기준으로 정한다.

## 채널·장치·제한·필드

- 과하지 않은가: 함께 쓰이는 것을 따로 보내는 채널이 있는가? 이 제한은 이유가 있는가, 내부 표현만 통일하면 되는가? 같은 사실을 두 필드·두 이름으로 나누지 않았는가? 이 메커니즘이 대비하는 상황이 실제로 일어나는가?
- 빼지 않았는가: 업무상 지켜야 하는 제약(하나만 있어야 함, 승인 뒤에만 전송)을 구조로 두었는가? 파악을 돕는 계층까지 과하다며 빼지 않았는가?

## 결정 순서와 계층

- 큰 경계(패키지와 바로 아래 디렉터리)를 먼저 정하고 그 아래를 한 부분씩 정한다.
- 이 결함은 어느 계층의 결정에서 나왔는가? 이름·파일 계층에서 가리지 말고 그 계층으로 돌아간다. 문제 하나를 커버하는 구조가 아니라 같은 원인의 문제 전부를 커버하는 구조를 만든다.
- 어디까지 정하고 만들기를 시작할지 정한다. 계획을 고쳐 쓰는 일만 반복되면 더 고치지 않고 만들기를 시작한다.

## 사용자가 도달할 수 있는 경로

경로의 구조는 여기서 정하고, 화면에서 무엇을 어떻게 표시할지는 `qef:ux`를 따른다.

- 할 수 있는 작업마다 화면에서 도달하는 경로가 있는가? 정적으로 확인할 수 있는가?
- 업무 하나를 처음부터 끝까지 할 때 값이 어디서 들어오고 어디서 보이는가? 입력 형식은 안내 문구가 아니라 동작으로 유도한다.
- 상위 개념 없이 하위 화면이 열리지 않는가? 가진 권한보다 할 수 있는 작업이 많은 화면은 없는가? 모듈이 선언한 작업과 실제로 호출하는 작업이 일치하는가?
