# command 사례: 사용자가 짚은 장면

사용자가 실제 작업에서 짚은 장면이다. 원칙마다 틀린 모습(❌)과 사용자가 원한 모습(✅)을 둔다. 괄호 안은 그 말을 한 날이다. 표면이 아니라 판단을 가져간다.

## 실패를 알아볼 수 있게 돌린다

**실패 처리를 제대로 안 함 (2026-11-26)**
- ❌ 백그라운드로 돌린 명령의 절반 넘게가 출력을 `tail`, `grep`, `tee`로 넘기면서 `pipefail`을 걸지 않아, 실패가 성공으로 보인다. CI가 끝나기를 기다리는 명령은 `gh run watch … > /dev/null 2>&1; …; gh release view …`처럼 출력을 버리고 `;`로 이어, 실패했지만 어느 단계가 왜 실패했는지 남지 않았다.
- ✅ 「오래 걸리는 명령 백그라운드로 돌릴 때 실패할 경우의 처리를 제대로」 한다.

**안 끝나는 명령을 기다림 (2026-10-23)**
- ❌ 가끔 끝나지 않는 명령을 실행해 놓고 계속 기다려 시간을 쓴다.
- ✅ 끝나지 않을 수 있는 명령은 시간 제한을 두거나 지켜보는 장치로 돌린다.

## 끝나면 결과를 읽고, 실패면 원인을 찾는다

**돌고 있지 않은 것을 돌고 있다고 함 (2026-11-13)**
- ❌ 리뷰가 돌고 있다고 보고했지만 실제로는 아무것도 돌고 있지 않았다.
- ✅ 「왜 아무것도 안 돌고 있을까」. 돌고 있다고 말하기 전에 실제로 도는지 확인한다.

**결과를 기다리며 멈춤 (2026-11-01)**
- ❌ e2e 결과를 기다리며 멈춰 있어, 사용자가 직접 결과를 챙기게 한다.
- ✅ 「이거까지 내가 해줘야 함?」. 결과를 챙기는 일을 사용자에게 넘기지 않는다.
