# git 사례: 사용자가 짚은 장면

사용자가 실제 작업에서 짚은 장면이다. 원칙마다 틀린 모습(❌)과 사용자가 원한 모습(✅)을 둔다. 괄호 안은 그 말을 한 날이다. 표면이 아니라 판단을 가져간다.

## 커밋 하나에는 논리적 변경 하나를 담는다

**커밋을 시켜 주기를 기다림 (2026-11-27)**
- ❌ 일을 모두 끝내고 커밋만 남았는데, 사용자가 커밋하라고 할 때까지 기다린다. 큰 일을 단계로 나눠 하는데 단계마다 사용자가 커밋을 시켜야 한다.
- ✅ 단계를 끝내고 검사가 통과하면 커밋한다. 사용자가 매번 시켜야 하면 사용자가 병목이 된다.

**고치는 커밋을 먼저 (2026-11-27)**
- ❌ 범위 밖의 것을 지울지 묻고 기다린다. 또는 하던 변경과 한 커밋에 섞는다.
- ✅ 하던 변경은 다음 커밋으로 미루고, 어긋난 것을 고치는 커밋을 먼저 낸 뒤 그 위에서 하던 일을 이어 간다.

## 되살릴 수 없는 것은 버리지 않는다

**방치된 변경 (2026-11-27)**
- ❌ 작업 트리에 사흘째 커밋되지 않은 CI 설정 변경이 있는데, 세션마다 「다른 일」이라며 커밋에서 빼고 보고에만 적는다.
- ✅ 누가 왜 만들었는지 찾고, 끝난 변경이면 따로 커밋한다.

## 합치고 올린 결과를 확인한다

**로컬에서 먼저 (2026-11-12, 2026-11-24, 2026-11-27)**
- ❌ 로컬에서 잡지 못한 UI 테스트 실패가 CI에서 처음 나온다. CI 설정을 container image로 바꾸고, 이미지 태그만 맞춰 본 뒤 로컬에서 그 image로 돌려 보지 않고 push해 CI에서 git 소유권 거부와 연결 거부를 처음 본다.
- ✅ CI가 돌릴 검사를 로컬에서 제대로 돌리고 올린다. CI 설정을 바꿨으면 그 job을 같은 image에서 로컬로 돌린다.
