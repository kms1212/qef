# ux

## 판정의 뿌리

- 사용성은 정해진 사용자가 정해진 맥락에서 정해진 목표를 이루는 정도다. 에이전트는 글로 된 기준에 대조할 수 있는 판단만 정한다. 기준이 사용자의 머릿속에만 있는 판단(이 업무에서 이 순서가 편한가, 이 정보가 첫 화면에 필요한가, 문구가 자연스러운가)은 정하지 않고, 「사람이 볼 것」으로 모아 끝낼 때 보인다.
- 화면을 띄워 써 보고 괜찮다고 말하는 것은 근거가 아니다. 「좋아 보이는가」를 묻지 않고, 무엇에 대조했는지를 적는다.
- UX와 UI를 섞지 않는다. 이 스킬은 업무를 끝까지 할 수 있는가, 무엇을 어디에 보이는가, 무슨 말로 보이는가를 다룬다. 모양(정렬, overflow, 강조, 같은 종류의 요소가 같은 모양인가)은 `qef:ui`가 다룬다. 이 절과 「근거 없는 추가를 막는다」, 「이전 버전과 결함」은 UI에도 그대로 적용한다.
- 기준은 이 차례로 찾는다: 사용자의 말과 요구사항, 이 스킬, 프로젝트의 규칙 문서와 열린 이슈, Carbon Design System(표, 목록, 폼 같은 업무 화면), GOV.UK Design System(흐름, 이동, 오류, 문구), Nielsen Norman Group. 쓴 근거를 `reasoning.md`에 적는다. 이 차례로도 정해지지 않으면 묻는다.
- `references/`는 관례를 모은 점검 목록이다. 이 스킬과 충돌하면 이 스킬을 따른다. 형식을 안내하는 placeholder(`wondelai-nielsen-heuristics.md` 220행, `owl-form-design.md` 17행)가 그런 예다.

## 근거 없는 추가를 막는다

1. 만드는 동안: 화면, 메뉴 항목, 표의 열, 폼 필드, 버튼, 안내 문구, API 응답 속성마다 「이것을 보고 사용자가 무엇을 하거나 정하나」에 답한다. 「데이터가 있다」, 「요구사항에 그 개념이 있다」, 「API가 준다」는 답이 아니다. 답이 없으면 만들지 않고 `goal.md`의 후보로 올린다.
2. 리뷰: 짝 reviewer가 설계 초안에서, 구현한 뒤에는 diff에서 새로 생긴 화면 요소와 API 응답 속성을 늘어놓고, 1의 답이 없거나 약한 것을 지적한다.
3. 승인: 두 번 거른 UX·UI 설계를 프로토타입으로 보여 사용자에게 승인받는다. 승인은 거르기의 맨 마지막이고, 화면을 구현하기 전이다. 승인받기 전에는 화면을 구현하지 않는다.

## 설계

- 화면은 요구사항과 이 스킬에서 설계한다. 옛 화면을 따라 그리지 않는다. 재작성 일에서 옛 화면에서 본 것은 후보다(`qef:workflow`의 일의 성격).
- 사람이 쓰는 화면은 API나 선언에서 파생하지 않고 업무 흐름에서 설계한다. 기계가 쓰는 채널(MCP)은 선언에서 파생해도 된다.
- 설계는 글이 아니라 화면(프로토타입)으로 보인다. 화면마다 보이는 것과 그것으로 하는 일을 함께 적는다.

## 경로와 흐름

- 권한이 있는 일마다 화면에 정상 경로가 있다. 버튼과 실제로 할 수 있는 일은 양쪽으로 맞는다. 버튼은 있는데 실행하면 막히는 것도, 할 수 있는데 버튼이 없는 것도 결함이다. 일은 API 메소드가 아니라 사용자가 하는 작업 단위로 센다. 경로가 있는지는 `qef:layout`의 「사용자가 닿는 경로」대로 정적으로 확인한다.
- 화면에 보이는 권한과 설정할 수 있는 권한이 같다. 관리 화면은 그 권한이 있는 계정에만 보인다.
- 만든 기록과 연결은 화면에서 고치고 지울 수 있다.
- 하위 화면으로 들어가면 상위 화면 위에 쌓인다. 화면 스택을 통째로 갈아 끼우지 않는다. 뒤로 가기가 어디로 갈지는 위의 기준 차례로 정한다.
- 반드시 상위에 속하는 것은 상위를 먼저 고른 뒤 만든다.
- UX 확인은 역할마다 그 권한만큼의 업무가 처음부터 끝까지 이어지는지를 업무 흐름, 화면 목록, 코드에서 읽어 판정한다. 화면을 조작하거나 둘러보거나 캡처해서 확인하지 않는다. 실제로 쓸 수 있는지는 그 여정을 밟는 테스트(`qef:testing`)가 본다.

## 순서와 보일 것

- 메뉴와 입력 필드의 순서는 개념의 위계와 사용자가 정하는 순서를 따른다. 홈은 메뉴의 맨 앞에 둔다.
- 요구사항의 범위어(맨 앞, 모두, 만)는 관례와 충돌하지 않게 읽는다. 관례로도 갈리면 묻는다.
- 로그인 직후 화면은 그 계정이 할 일을 보인다. 권한이 없다는 표시만 있는 첫 화면을 두지 않는다.
- 기록을 열면 가장 필요한 것이 추가 조작 없이 보인다. 반드시 하나씩 짝지어진 것은 따로 탭을 두지 않고 기본 정보에 둔다.
- 다른 화면에서 이미 다 보이는 것을 따로 목록 화면으로 만들지 않는다.
- 내부 장치의 존재와 상태는 사용자가 그것으로 무엇을 하거나 정할 때만 보인다. 그렇지 않으면 화면에도 API에도 내지 않는다. API는 화면이 쓰는 속성만 낸다.

## 입력

- 형식이 정해진 값은 입력하는 동안 형식을 맞춰 준다(input mask). 형식을 글로 안내하지 않는다. 사람의 입력은 넓게 받고, API와 저장은 엄격하게 받는다.
- 정해진 값 가운데 고르는 필드는 자유 입력으로 받지 않는다. 서버가 매기는 값에는 입력 필드를 두지 않는다.
- 검증 규칙은 서버의 것을 기준으로 하고, 화면은 그것을 가져다 쓴다. 검증 오류는 틀린 입력 곁에 보이고, 화면 위쪽에 그 오류들로 가는 요약을 둔다.

## 문구

- 화면 문구는 `design:ux-copy`와 `korean-humanizer`로 쓰고 리뷰한다.
- 출처·경위·동작을 설명하는 주석식 문장과 em dash를 화면에 넣지 않는다.
- 용어는 그 개념을 정의한 쪽의 공식 이름을 쓴다. 지어낸 말과 기술 용어의 번역어를 쓰지 않는다. 검색, 생성, 수정, 삭제, 제외 같은 한자어 표준 용어를 우리말 풀이로 바꾸지 않는다. 한 개념은 한 말로 부른다.
- 화면 이름은 그 화면에서 하는 일을 가리킨다.
- 검색 필드는 「검색」으로 둔다. 무엇을 찾는지 필드 이름을 늘어놓지 않는다.
- 오류의 종류는 서버가, 오류 문장은 화면이 갖는다. 내부 문자열, 코드, 예외 메시지를 화면에 내지 않는다. 실패는 삼키지 않고, 원인(권한 없음, 없음, 연결 실패)에 따라 다르게 보인다.
- 서버의 enum은 그대로 내지 않고 표시 문자열로 바꾼다. 바꾸는 표는 한 곳에 둔다.

## 이전 버전과 결함

- 본궤도 일에서 화면을 바꾸기 전에 이전 버전의 화면 목록, accessibility tree(Playwright ARIA snapshot), screenshot을 떠 둔다. 바꾼 뒤 차이마다 요구사항 줄을 대고, 댈 줄이 없는 차이(사라진 요소, 바뀐 순서)는 사용자에게 보인다. 이 기록은 대조용이고 테스트가 아니다.
- UX 결함은 하나씩 고치지 않는다. 그 결함이 나온 결정과 빠진 기준을 찾아, 같은 원인의 결함을 함께 커버한다.
