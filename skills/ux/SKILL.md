# ux

이 스킬은 업무를 끝까지 할 수 있는가, 무엇을 어디에 표시하는가, 무슨 말로 표시하는가를 다룬다. UX와 UI를 섞지 않는다. 모양(정렬, overflow, 강조, 같은 종류의 요소가 같은 모양인가)은 `qef:ui`가 다룬다. 「판단의 근거」, 「설계 순서」, 「보이는 것은 모두 사용자가 무엇을 하거나 정하는 데 쓰인다」, 「이전 버전과 결함」은 UI에도 그대로 적용한다.

원칙마다 의도, 규칙, 확인할 것을 둔다. 규칙에 없는 상황은 그 원칙의 의도로 판단한다. 원칙마다 실제로 틀렸던 장면과 바르게 고친 모습은 [references/cases.md](references/cases.md)에 있다.

## 판단의 근거

- 사용성은 정해진 사용자가 정해진 맥락에서 정해진 목표를 이루는 정도다. 에이전트는 글로 된 기준에 대조할 수 있는 판단만 정한다. 기준이 사용자의 머릿속에만 있는 판단(이 업무에서 이 순서가 편한가, 이 정보가 첫 화면에 필요한가, 문구가 자연스러운가)은 정하지 않고, 「수동 확인 항목」으로 모아 끝낼 때 보여 준다.
- 화면을 띄워 써 보고 괜찮다고 말하는 것은 근거가 아니다. 「좋아 보이는가」를 묻지 않고, 무엇에 대조했는지를 적는다.
- 기준은 이 차례로 찾는다: 사용자의 말과 요구사항, 이 스킬, 프로젝트의 규칙 문서와 열린 이슈, Carbon Design System(표, 목록, 폼 같은 업무 화면), GOV.UK Design System(흐름, 이동, 오류, 문구), Nielsen Norman Group. 쓴 근거를 설계 문서(OpenSpec 변경이면 `design.md`의 Decisions)에 적는다. 이 차례로도 정해지지 않으면 묻는다.
- `references/`는 관례를 모은 점검 목록이다. 이 스킬과 충돌하면 이 스킬을 따른다. 형식을 안내하는 placeholder(`wondelai-nielsen-heuristics.md` 220행, `owl-form-design.md` 17행)가 그런 예다.
- 요구사항의 범위어(맨 앞, 모두, 만)는 관례와 충돌하지 않게 읽는다. 관례로도 달라지면 묻는다.

## 설계 순서

1. 화면은 요구사항과 이 스킬에서 설계한다. 옛 화면을 따라 렌더링하지 않는다. 재작성 일에서 옛 화면에서 본 것은 요구사항이 아니라 후보다.
2. 요구사항에서 역할을 늘어놓고, 역할마다 그 권한으로 하는 업무를 처음부터 끝까지 적는다. 사람이 쓰는 화면은 API나 선언에서 파생하지 않고 이 업무 흐름에서 설계한다. 기계가 쓰는 채널(MCP)은 선언에서 파생해도 된다.
3. 업무 흐름에서 메뉴 구조와 화면 목록을 낸다. 화면마다 보이는 것과 그것으로 하는 일을 적는다(「화면은 사용자가 일하고 생각하는 순서를 따른다」, 「할 수 있는 일과 화면에 보이는 일은 양쪽으로 맞는다」).
4. 화면 요소마다 「보이는 것은 모두 사용자가 무엇을 하거나 정하는 데 쓰인다」의 질문에 답하고 근거를 적는다. 답이 없으면 만들지 않고 후보로 적어 사용자에게 보여 준다.
5. 글이 아니라 클릭할 수 있는 low-fidelity 프로토타입으로 보여 준다. 기준이 사용자 머릿속에만 있는 판단은 「수동 확인 항목」으로 모은다.
6. 만든 쪽이 아닌 새 맥락(subagent)에서, 설계 초안과 구현한 뒤의 diff에 새로 생긴 화면 요소와 API 응답 속성을 나열하고 「보이는 것은 모두 사용자가 무엇을 하거나 정하는 데 쓰인다」의 답이 없거나 약한 것을 지적한다.
7. 두 번 걸러 낸 UX·UI 설계를 프로토타입으로 보여 줘 사용자에게 승인받는다. 승인받기 전에는 화면을 구현하지 않는다.

## 화면은 사용자가 일하고 생각하는 순서를 따른다

**의도.** 화면의 순서가 일의 순서와 어긋나면, 사용자는 화면을 오가며 머릿속으로 순서를 다시 맞춰야 한다. 앞에서 고른 것이 뒤의 선택을 바꾸면 이미 채운 값을 다시 고쳐야 한다.

**규칙**
- 사용자는 화면을 위에서 아래로, 왼쪽에서 오른쪽으로 읽는다고 본다. 먼저 정할 것을 위와 왼쪽에, 그 결과를 아래와 오른쪽에 둔다.
- 폼은 사용자가 정하는 순서대로, 큰 범위에서 작은 범위로 채운다. 같은 단계 안에서는 중요한 정보 묶음을 덜 중요한 묶음보다 먼저 둔다.
- 입력할 것이 종류에 따라 달라지면 종류를 먼저 고르게 하고, 그 종류에 필요한 입력만 보인다.
- 반드시 상위에 속하는 것은 상위를 먼저 고른 뒤 만든다. 상위가 없으면 하위 화면이 열리지 않는다.
- 사용자가 이미 채운 값을 사용자 몰래 지우거나 되돌리지 않는다.
- 메뉴는 홈이 맨 앞이고, 그룹과 그룹 안의 순서는 개념의 위계와 사용자가 정하는 순서를 따른다. 그룹 안에서 앞에 두라는 요구를 그룹 밖까지 끌어내지 않는다.
- 하위 화면으로 들어가면 상위 화면 위에 쌓인다. 화면 스택을 통째로 갈아 끼우지 않는다. 뒤로 가기가 어디로 갈지는 「판단의 근거」의 기준 차례로 정한다.

**확인할 것**
- [ ] 폼의 필드를 위에서부터 읽을 때 범위가 다시 커지는 곳이 없다.
- [ ] 뒤의 선택이나 키 입력이 앞에서 채운 값을 지우거나 무효로 만들지 않는다.
- [ ] 고른 종류에 쓰이지 않는 칸이 보이지 않는다.
- [ ] 하위 화면에서 뒤로 가면 그 상위 화면으로 돌아간다.

근거: NN/g, "F-Shaped Pattern For Reading Web Content" (https://www.nngroup.com/articles/f-shaped-pattern-reading-web-content/); Laws of UX, "Serial Position Effect" (https://lawsofux.com/serial-position-effect/); GOV.UK Service Manual, "Structuring forms"(관련 있는 질문만 보이는 branching) (https://www.gov.uk/service-manual/design/form-structure).

## 보이는 것은 모두 사용자가 무엇을 하거나 정하는 데 쓰인다

**의도.** 쓰이지 않는 요소는 찾는 시간과 판단할 거리만 늘린다. 「데이터가 있으니 보인다」로 쌓인 화면은 사용자가 필요한 것을 찾지 못하게 만든다.

**규칙**
- 화면, 메뉴 항목, 표의 열, 폼 필드, 버튼, 안내 문구, API 응답 속성마다 「이것을 보고 사용자가 무엇을 하거나 정하나」에 답한다. 「데이터가 있다」, 「요구사항에 그 개념이 있다」, 「API가 준다」는 답이 아니다.
- 내부 메커니즘(중간 테이블, 키, 동기화 상태)의 존재와 상태는 사용자가 그것으로 무엇을 하거나 정할 때만 보인다. 그렇지 않으면 화면에도 API에도 내지 않는다. API는 화면이 쓰는 속성만 반환한다.
- 레코드를 열면 가장 필요한 것이 추가 조작 없이 보인다. 그 레코드의 기본 정보에 속하는 것과 1:1 관계인 것은 따로 탭을 두지 않고 기본 정보에 묶는다. 다른 탭이 다루는 것을 요약해 보이는 섹션은 그 탭으로 가는 길을 둔다.
- 다른 화면에서 이미 다 보이는 것을 따로 목록 화면이나 탭으로 만들지 않는다.
- 정렬과 필터는 사용자가 그 열로 찾거나 고를 때만 둔다.
- 로그인 직후 화면은 그 계정이 할 일을 표시한다. 권한이 없다는 표시만 있는 첫 화면을 두지 않는다.

**확인할 것**
- [ ] 새로 생긴 화면 요소와 API 응답 속성마다 「무엇을 하거나 정하나」의 답이 적혀 있다.
- [ ] 저장 구조(중간 테이블, 내부 키)가 그대로 화면이나 메뉴가 된 곳이 없다.
- [ ] 1:1 관계나 기본 정보에 속하는 것이 별도 탭에 있지 않다.

근거: NN/g, "Progressive Disclosure" (https://www.nngroup.com/articles/progressive-disclosure/).

## 사용자가 해석하고 기억할 일은 화면이 맡는다

**의도.** 사람이 형식과 규칙을 외워 맞추면 틀리고, 틀린 값은 저장에 남는다. 사람이 읽고 해석해야 하는 표시는 잘못 읽힌다.

**규칙**
- 형식이 정해진 값은 입력하는 동안 형식을 맞춰 준다(input mask). 형식을 텍스트로 안내하지 않는다. 사람의 입력은 넓게 받고 화면에서 정제해 형식에 맞추며, API와 저장은 엄격하게 받는다.
- 정해진 값 가운데 고르는 필드는 자유 입력으로 받지 않는다. 서버가 매기는 값에는 입력 필드를 두지 않는다.
- 칸을 비워 두면 특정 값으로 제출되는 필드(예: 날짜를 비우면 「미정」으로 저장되는 업무)는, 비어 있을 때 placeholder로 그 값을 보인다. 그 글자를 칸마다 써 넣게 하지 않는다. 빈 값이 그런 뜻을 갖지 않는 필드(필수 값, 정해지지 않은 상태가 없는 업무)에는 두지 않는다. 빈 값의 뜻을 몇 가지로 나눌지(예: 「모름」과 「미정」)는 업무 규칙이 정한다.
- 목록마다 그 특성에 맞는 기본 순서를 정하고, 같은 값이면 순서를 정하는 마지막 기준(아이디 등)을 둔다.
- 검증 규칙은 서버의 것을 기준으로 하고, 화면은 그것을 가져다 쓴다. 검증 오류는 해당 입력 필드 옆에 표시하고, 화면 위쪽에 그 오류들로 가는 요약을 둔다.
- 오류 타입(코드)은 서버가, 오류 메시지는 화면이 정한다. 내부 문자열, 코드, 예외 메시지를 화면에 내지 않는다. 실패는 삼키지 않고, 원인(권한 없음, 대상 없음, 연결 실패)에 따라 다르게 표시한다.
- 서버의 enum은 그대로 내지 않고 표시 문자열로 바꾼다. 매핑 테이블은 한 곳에 둔다.

**확인할 것**
- [ ] 형식을 텍스트로 안내하는 곳이 없고, 형식이 정해진 값은 입력 중에 맞춰진다.
- [ ] 서버가 매기는 값(번호, 상태)을 사람이 입력할 수 있는 칸이 없다.
- [ ] 화면에 내부 문자열, 코드, enum 원문이 보이는 곳이 없다.

근거: GOV.UK Design System, "Text input" (https://design-system.service.gov.uk/components/text-input/); NN/g, "Placeholders in Form Fields Are Harmful"(placeholder로 label을 대신하지 않는다) (https://www.nngroup.com/articles/form-design-placeholders/).

## 한 개념은 한 이름으로, 이름은 하는 일을 가리킨다

**의도.** 이름이 흔들리면 사용자는 같은 것을 다른 것으로, 다른 것을 같은 것으로 읽는다. 이름이 하는 일을 가리키지 않으면 화면을 열어 봐야 무엇을 하는 곳인지 안다.

**규칙**
- 화면 이름과 버튼 이름은 그 화면에서, 그 버튼으로 하는 일을 가리킨다.
- 용어는 그 개념을 정의한 쪽의 공식 이름을 쓴다. 지어낸 용어와 기술 용어의 번역어를 쓰지 않는다. 검색, 생성, 수정, 삭제, 제외 같은 한자어 표준 용어를 우리말 풀이로 바꾸지 않는다. 한 개념은 한 용어로 부른다.
- 검색 필드는 「검색」으로 둔다. 무엇을 찾는지 필드 이름을 나열하지 않는다.
- 출처, 경위, 동작을 설명하는 주석식 문장과 em dash를 화면에 넣지 않는다.
- 화면 문구는 `design:ux-copy`와 `korean-humanizer`로 쓰고 리뷰한다.

**확인할 것**
- [ ] 화면과 버튼 이름만 보고 그곳에서 하는 일을 말할 수 있다.
- [ ] 같은 개념이 화면마다 다른 이름으로 불리지 않는다.

## 할 수 있는 일과 화면에 보이는 일은 양쪽으로 맞는다

**의도.** 버튼은 있는데 누르면 막히거나, 할 수 있는데 갈 길이 없으면 둘 다 사용자가 일을 끝내지 못한다.

**규칙**
- 권한이 있는 작업마다 화면에 정상 경로가 있다. 버튼과 실제로 할 수 있는 작업은 양쪽으로 맞는다. 일은 API 메소드가 아니라 사용자가 하는 작업 단위로 센다. 경로가 있는지는 `qef:layout`의 「할 수 있는 작업마다 사용자가 도달할 길이 있다」대로 정적으로 확인한다.
- 화면에 보이는 권한과 설정할 수 있는 권한이 같다. 사용자는 자기가 가진 역할과 권한을 볼 수 있다. 관리 화면은 그 권한이 있는 계정에만 보인다.
- 만든 레코드와 연결은 화면에서 고치고 지울 수 있다.

**확인할 것**
- [ ] 역할마다 그 권한만큼의 업무가 처음부터 끝까지 이어지는지를 업무 흐름, 화면 목록, 코드에서 읽어 확인했다. 화면을 조작하거나 둘러보거나 캡처해서 확인하지 않는다. 실제로 쓸 수 있는지는 그 흐름을 밟는 테스트(`qef:testing`)가 본다.
- [ ] 이 대조를 검사로 만들었으면, 할 수 있는 일보다 적은 화면과 많은 화면을 하나씩 만들어 둘 다 실패하는지 봤다.

## 이전 버전과 결함

- 본궤도 일에서 화면을 바꾸기 전에 이전 버전의 화면 목록, accessibility tree(Playwright ARIA snapshot), screenshot을 떠 둔다. 바꾼 뒤 차이마다 요구사항 줄을 대고, 댈 줄이 없는 차이(사라진 요소, 바뀐 순서)는 사용자에게 보여 준다. 이 레코드는 대조용이고 테스트가 아니다.
- UX 결함은 하나씩 고치지 않는다. 그 결함이 어느 원칙에서 어긋난 결정에서 나왔는지 찾아, 같은 원인의 결함을 함께 고친다.
