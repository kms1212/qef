# doc

이 스킬은 형식과 상관없이 독자가 읽는 문서를 다룬다. 글(무엇을 어떤 순서로, 무슨 말로 쓰는가)과 문서의 모양(제목, 표, 그림, 캡션, 상호참조)이 대상이다. 그 형식으로 만드는 방법(빌드, 검사, 결과 비교)은 형식 스킬에 있다(LaTeX는 `qef:latex`). 화면 문구는 `qef:ux`가 다룬다. 사용자에게 하는 대화 응답은 다루지 않는다.

원칙마다 의도, 규칙, 확인할 것을 둔다. 규칙에 없는 상황은 그 원칙의 의도로 판단한다. 사용자가 실제 프로젝트에서 짚은 장면은 [references/cases.md](references/cases.md)에 있다.

## 판단의 근거

- 기준은 이 차례로 찾는다: 사용자의 말과 프로젝트의 글쓰기 규칙, 이 스킬, 같은 종류의 다른 문서(선례), Google developer documentation style guide, Microsoft Writing Style Guide, Diátaxis.
- 읽기 편한가, 문장이 자연스러운가처럼 기준이 사용자의 머릿속에만 있는 판단은 정하지 않고, 사용자가 직접 확인할 항목으로 모아 끝낼 때 보여 준다.

## 문서의 종류가 쓸 문장을 정한다

**의도.** 무슨 문서인지 잊으면 명세에 홍보 문구, 설계 이유, 표에서 관찰한 경향이 들어간다. 독자는 그 문장이 규칙인지 의견인지 가를 수 없다.

**규칙**
- 쓰기 전에 문서의 종류(명세 같은 reference, how-to guide, explanation, tutorial)와 독자를 정한다.
- 명세와 reference 문서의 문장은 넷 중 하나다: 문서가 정하는 규칙, 용어의 정의, 표·그림을 읽는 방법, 규칙을 실제 값에 적용해 보이는 예시. 설계 의도, 이유, 표에서 관찰한 경향, 앞 문장의 반복, 홍보 문구는 쓰지 않는다. 설계 이유가 필요한 독자가 있으면 explanation 문서(설계 문서, ADR)에 따로 둔다.
- 다른 곳(코드, 형식 명세, 스키마, 생성되는 표)이 source of truth인 내용은 문서가 설명하기만 하고 다시 정의하지 않는다.
- 정해지지 않았다는 표시(TBD)는 초안에만 둔다. 공개하는 버전에 남기지 않는다.
- 지우라고 한 문장은 같은 취지의 문장까지 모두 지운다. 남은 문장이 번지지 않게 막는 문장을 더하지 않는다.

**확인할 것**
- [ ] 명세와 reference 문서에서 문장마다 넷 중 어느 것인지 대조했고, 넷이 아닌 문장은 지웠다.

근거: Diátaxis, "Reference"(「Describe and only describe」) (https://diataxis.fr/reference/).

## 규칙을 먼저 쓰고 예시는 그 뒤에 둔다

**의도.** 예시만 있으면 독자도 에이전트도 예시에 나온 경우에만 규칙을 적용한다.

**규칙**
- 예시는 그것이 보이는 규칙을 일반형으로 먼저 쓴 뒤에만 둔다.
- 규칙은 그 규칙이 다루는 모든 경우에 적용되게 쓴다. 예시의 값, 크기, 형식으로 범위를 좁히지 않는다.
- 예시만 있고 일반 규칙이 없는 곳은 결함으로 보고 고친다.

**확인할 것**
- [ ] 예시마다 바로 앞에 그 예시가 보이는 일반 규칙이 있다.

## 내용의 모양이 요소를 정한다

**의도.** 복잡한 개념을 표 하나로 대신하면 독자가 관계와 순서를 혼자 다시 짜야 한다. 조건과 예외로 이어진 문장을 불릿으로 쪼개면 항목 사이의 관계가 사라진다. 같은 내용이 여러 곳에 있으면 어느 쪽이 맞는지 알 수 없고, 하나만 고쳐져 어긋난다.

**규칙**

| 내용의 모양 | 요소 |
|---|---|
| 개념, 조건과 예외가 얽힌 규칙, 앞뒤가 논리로 이어지는 설명 | 산문 |
| 공간 배치(비트 필드, 메모리 레이아웃), 흐름, 상태 전이, 구성 요소 사이의 관계 | 다이어그램. 같은 내용을 산문에도 쓴다 |
| 여러 항목을 같은 속성 셋 이상으로 찾아보는 값 | 표 |
| 순서가 없는 같은 종류의 항목, 항목마다 값이 하나이거나 짝인 것 | 불릿 리스트 |
| 순서가 뜻을 갖는 절차, 단계, 우선순위 | 번호 리스트 |
| 용어와 그 정의 | 설명 목록(`<dl>`) |
| 독자가 그대로 입력하거나 복사하는 것 | 코드 블록 |

- 표는 값을 찾아보는 데만 쓴다. 개념을 표로 대신하지 않는다.
- 다이어그램은 글로 나타내기 어려운 것을 보일 때만 둔다. 그 다이어그램이 보이는 읽기나 동작이 실제로 일어나지 않으면 두지 않는다. 불필요하다고 한 다이어그램은 이름이나 표시만 바꾸지 않고 지운다.
- 조건과 예외로 이어진 문장을 불릿으로 쪼개지 않는다. 항목이 하나뿐이면 리스트로 두지 않는다. 열이 하나뿐인 표는 리스트로 바꾼다.
- 같은 값을 여러 요소에 되풀이하지 않는다. 생성되는 표·다이어그램에 있는 값은 산문에 다시 적지 않는다. 다이어그램과 같은 내용을 산문에 쓰는 것은 값을 되풀이하는 것이 아니라, 다이어그램이 보이는 구조를 글로 말하는 것이다.
- 표, 다이어그램, 리스트는 본문에서 그 목적을 말하는 완전한 문장으로 소개한다. 요소의 항목이 앞 문장을 완성하게 쓰지 않는다. 위치(「위 그림」)가 아니라 참조로 가리킨다.
- 요소를 바꿀 때(표를 산문으로, 산문을 리스트로) 내용을 빼지 않는다. 바꾸기 전과 값, 조건, 이름을 대조한다.

**확인할 것**
- [ ] 표마다 독자가 찾아보는 값이 무엇인지 말할 수 있다.
- [ ] 다이어그램마다 그것이 보이는 것이 실제 규칙이나 동작이다.
- [ ] 불릿 리스트의 항목 사이에 「그래서」, 「단」, 「그 경우」 같은 관계가 숨어 있지 않다.

근거: Google developer documentation style guide, "Tables" (https://developers.google.com/style/tables), "Images" (https://developers.google.com/style/images), "Lists" (https://developers.google.com/style/lists); Microsoft Writing Style Guide, "Tables" (https://learn.microsoft.com/en-us/style-guide/scannable-content/tables), "Lists" (https://learn.microsoft.com/en-us/style-guide/scannable-content/lists).

## 표는 칸 하나가 혼자 읽히게 만든다

**의도.** 독자는 표를 위에서부터 읽지 않고, 한 행이나 한 칸을 찾아 읽는다. 스크린 리더도 칸 하나를 머리글과 함께 읽는다. 칸의 뜻이 위 행이나 다른 칸에 기대면, 찾아 읽은 칸이 무엇인지 알 수 없다. 행을 정렬하거나 끼워 넣거나 표가 쪽을 넘어가면 그 뜻이 바뀐다.

**규칙**
- 첫 열에는 그 행을 가리키는 것(이름, 값)을 둔다.
- 행은 논리적 순서(비트 위치, 인코딩 값, 문서의 다른 곳과 같은 순서)로 놓는다. 그런 순서가 없으면 이름순으로 놓는다.
- 열 머리글은 짧고 정확하게 쓴다. 단위는 칸이 아니라 머리글에 둔다.
- 칸을 병합하지 않는다. 같은 값은 칸마다 되풀이해 쓴다. 「〃」 같은 반복 표시나 「위와 같음」을 뜻하는 빈 칸을 쓰지 않는다. 되풀이가 너무 많으면 그 값으로 표를 나누거나 묶음 행을 둘 신호로 본다.
- 값이 없는 칸은 빈 칸으로 두지 않고 그 상태(없음, 해당 없음)를 쓴다.
- 같은 열의 칸은 같은 꼴로, 짧게 쓴다. 긴 설명이 필요한 칸은 표 밖의 산문으로 옮긴다.
- 표의 열끼리, 표끼리 같은 내용을 되풀이하지 않는다.
- 열이 넘치거나 왼쪽과 오른쪽의 성격이 달라 세로줄로 가르고 싶으면 표를 둘로 나눈다.
- 기호나 색만으로 정보를 나타내지 않는다.
- 각주는 표 바로 뒤에 둔다.
- 같은 종류의 표는 같은 열 구성으로, 한 곳에 정의한 같은 명령이나 템플릿으로 그린다.

**확인할 것**
- [ ] 아무 칸이나 골라 그 행의 첫 열과 그 열의 머리글만 보고 뜻을 말할 수 있다.
- [ ] 병합한 칸, 반복 표시, 뜻이 정해지지 않은 빈 칸이 없다.
- [ ] 두 열이나 두 표가 같은 내용을 되풀이하지 않는다.

근거: Google developer documentation style guide, "Tables" (https://developers.google.com/style/tables); Microsoft Writing Style Guide, "Tables" (https://learn.microsoft.com/en-us/style-guide/scannable-content/tables); Simon Fear, booktabs 매뉴얼 「The layout of formal tables」(`texdoc booktabs`); W3C WAI, "Tables Tutorial"(「Screen readers speak one cell at a time and reference the associated header cells」) (https://www.w3.org/WAI/tutorials/tables/).

## 다이어그램은 본문과 같은 이름과 같은 표기로 그린다

**의도.** 다이어그램의 이름이 본문과 다르면 독자는 둘을 맞춰 보느라 다이어그램을 읽지 못한다. 같은 종류의 다이어그램이 매번 다른 방향과 모양으로 그려지면 독자는 표기부터 다시 읽는다. 손으로 옮겨 그린 값은 원본이 바뀔 때 어긋난다.

**규칙**
- 다이어그램 하나는 한 가지를 보인다. 캡션은 그 다이어그램의 종류와 범위를 말한다.
- 다이어그램 안의 이름은 본문, 표와 같은 이름을 쓴다(「독자가 찾을 수 있는 이름만 쓴다」). 새 약어를 만들지 않는다.
- 같은 종류의 다이어그램은 같은 표기(방향, 비트 번호 순서, 모양, 선, 색)로 그린다. 표기가 자명하지 않으면 범례를 둔다.
- 화살표 하나는 한 방향의 관계 하나이고, 무슨 관계인지 이름을 붙인다.
- 색만으로 구분하지 않는다. 흑백으로 인쇄해도 읽혀야 한다.
- 설명 문장과 캡션은 다이어그램 안이 아니라 본문과 캡션에 둔다. 다이어그램이 보이는 정보는 본문에도 쓰고, 새 정보를 다이어그램에만 두지 않는다.
- 코드나 글을 이미지로 넣지 않는다. 다이어그램은 벡터로 만든다.
- 값(비트 위치, 필드 폭, 주소, 순서)이 데이터나 선언에 있으면 손으로 그리지 않고 그것에서 생성한다. 같은 종류의 다이어그램은 한 곳에 정의한 같은 명령으로 그린다.

**확인할 것**
- [ ] 다이어그램 안의 이름이 모두 본문이나 표에 같은 글자로 나온다.
- [ ] 같은 종류의 다이어그램이 같은 방향과 같은 모양으로 그려졌다.
- [ ] 다이어그램의 값이 원본에서 생성되었거나, 원본과 대조했다.

근거: C4 model, "Notation"(제목, 범례, 일관된 표기, 선마다 한 방향의 이름 붙은 관계) (https://c4model.com/diagrams/notation); Google developer documentation style guide, "Images" (https://developers.google.com/style/images); W3C, WCAG 2.2 "Understanding SC 1.4.1 Use of Color" (https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html).

## 독자가 찾을 수 있는 이름만 쓴다

**의도.** 내부 ID와 지어낸 용어는 독자가 찾아볼 곳이 없다. 같은 개념의 이름이 바뀌면 독자는 다른 개념으로 읽는다.

**규칙**
- 엔진의 내부 문자열, 선언의 내부 ID, 내부에서 만든 용어를 독자에게 보이지 않는다. 그 선언의 표시 이름을 쓴다.
- 독자가 글자 그대로 쓰는 이름(코드 식별자, 명령, 파일 이름, 설정 키, 레지스터, 필드)은 고정폭 글꼴로 그대로 쓴다. 번역하거나 활용하지 않는다.
- 기술 용어는 그 개념을 정의한 쪽의 공식 이름과 표준 의미로 쓴다. 번역어를 지어내지 않는다. 번역어인지는 그 분야에서 그 말을 쓰는지로 정한다. 사용자가 그 말을 썼는지로 정하지 않는다.
- 한 개념은 한 용어로 부른다. 같은 개념을 문장마다 다른 말로 바꿔 부르지 않고, 이미 있는 용어가 있으면 새로 만들지 않는다.
- 외부 독자에게 가는 문서에는 작업 경위, 내부 문서 참조, 내부 번호를 남기지 않는다.

**확인할 것**
- [ ] 문서에 나오는 이름마다 독자가 문서 안이나 공식 출처에서 찾을 수 있다.
- [ ] 같은 개념이 문서 안에서 다른 용어로 불리지 않는다.

근거: Microsoft Writing Style Guide, "Use technical terms carefully"(「Aim for one term, one concept」) (https://learn.microsoft.com/en-us/style-guide/word-choice/use-technical-terms-carefully); Google developer documentation style guide, "Code in text" (https://developers.google.com/style/code-in-text).

## 제목과 참조는 독자가 찾아가는 길이다

**의도.** 글자로 쓴 참조는 아무것도 검사하지 않아, 제목이 바뀌면 틀린 채로 빌드를 통과한다. 의미 없는 번호는 읽는 비용만 늘린다.

**규칙**
- 제목은 그 절의 내용을 가리키는 말로 쓴다. 제목 위계를 건너뛰지 않는다.
- 다른 장, 절, 표, 그림은 형식이 주는 참조 기능(LaTeX의 `\ref`·`\nameref`, Markdown의 링크)으로 가리킨다. 이름이나 번호를 글자로 쓰지 않는다.
- 링크 텍스트는 앞뒤 문장 없이도 가는 곳을 말한다. 「여기」, 「이 문서」로 쓰지 않는다.
- 텍스트 파일(Markdown, 에이전트 지시문)의 절에 번호를 붙이지 않고 제목으로 가리킨다. 번호는 형식이 자동으로 매길 때와, 순서가 뜻을 갖는 절차에만 쓴다.

**확인할 것**
- [ ] 문서 안의 참조가 모두 참조 기능으로 되어 있고, 빌드나 링크 검사에서 깨진 참조가 없다.

근거: Google developer documentation style guide, "Headings and titles" (https://developers.google.com/style/headings), "Cross-references and linking" (https://developers.google.com/style/cross-references).

## 보강과 재작성은 선례와 이전 버전에 대 본다

**의도.** 목록이나 개수로 대조하면 항목마다의 내용이 빠진다. 이전 버전을 보지 않으면 있던 그림과 설명이 사라진다. 다른 에이전트에게 특성만 뽑아 오게 하면 조사 항목이 적용 범위를 제한한다.

**규칙**
- 보강하거나 다른 문서를 참고하라는 요청에는, 같은 종류의 다른 문서에서 같은 주제를 다룬 절을 끝까지 직접 읽는다. 그 절이 적은 규칙, 정의, 동작마다 지금 문서에 있는지, 이 문서에 해당하지 않는지, 다른 장이 맡는지(그 장 이름을 적는다)를 정하고, 없고 해당하는 것은 넣는다.
- 이 대조를 절 제목이나 주제 목록으로 하지 않는다. 충실한지를 쪽 수나 표·그림의 수로 판단하지 않는다.
- subagent에게 특성만 뽑아 오게 하지 않는다. 작성까지 맡기는 것은 된다.
- 선례는 다룰 내용과 충실함의 기준이다. 문장과 구성을 그대로 옮기지 않고 이 문서에 맞게 다시 쓴다.
- 재작성하면 재작성 전 마지막 결과물(PDF, 렌더링된 문서)을 떠 두고 대조한다. 그 문서의 그림은 살린다(`qef:refactor`의 「구조가 이미 무너졌으면」).
- 여러 장이나 여러 페이지에 걸치는 새 모양(표기, 페이지 구성, 그림·표 방식)은 대표 몇 곳에 만들어 사용자에게 확정받은 뒤에만 나머지로 넓힌다.

**확인할 것**
- [ ] 참고한 절의 항목마다 있음, 해당 없음, 다른 장 중 무엇인지 적었다.
- [ ] 재작성 전 결과물과 대조해 빠진 것과 새로 생긴 것을 적었다.

## 문장 다듬기 skill은 독자와 언어로 고른다

**의도.** 독자에게 가는 글은 AI 흔적과 읽기 힘든 구조가 남으면 신뢰를 잃는다. 대화에서 보여 달라는 것을 다듬느라 미루면 사용자는 기다리기만 한다.

**규칙**

| 상황 | 쓰는 skill |
|---|---|
| 독자에게 가는 영어 산문(명세, 문서, README, 이메일, 게시물) | `ste80-humanizer`, Humanize 모드 |
| 영어 절차, 경고, 유지보수 지시 | `ste80-humanizer`, Strict 모드 |
| 영어 커밋 메시지, PR 설명, 이슈 | `ste80-humanizer`, Light 모드 |
| 독자에게 가는 한국어 산문(문서, README, 보고서, 이메일) | `korean-humanizer`. 원문의 격식과 장르를 지킨다 |
| 한국어 명세, 절차 | `korean-humanizer`로 고친 뒤, `ste80-humanizer`의 Pass 2 구조 규칙(한 문장에 한 생각, 능동, 숨은 주체 없음)으로 다시 본다 |
| 화면 문구 | `qef:ux`의 「한 개념은 한 이름으로, 이름은 하는 일을 가리킨다」 |
| 글자 수가 정해진 한국어 글(양식, 자기소개서) | 길이는 `korean-character-count`로 센다. 맞출 때는 `korean-humanizer`의 길이 맞추기 |
| 공개할 한국어 글의 맞춤법 | `korean-spell-check`. 원문을 외부 웹 서비스로 보내므로, 공개하지 않을 글, 민감한 글, 코드와 로그는 보내지 않는다 |
| 사용자가 유행어를 넣은 가벼운 글을 요청할 때 | `korean-slang-writing`. 문서와 화면 문구에는 쓰지 않는다 |

- 다음에는 문장 다듬기 skill을 쓰지 않는다: 사용자에게 하는 대화 응답과 보고(출력 스타일을 따른다), 정리해 보여 달라는 요청, subagent와 세션에 주는 지시, 코드 식별자, 명령, 로그.
- 프로젝트가 정한 글쓰기 규칙이 있으면 그것이 먼저다.
- 이 스킬의 「독자가 찾을 수 있는 이름만 쓴다」가 skill의 단어 규칙보다 먼저다. skill이 기술 용어를 번역어나 풀이로 바꾸면 되돌린다.
- 다듬은 뒤 사실(규칙, 값, 조건, 이름)이 더해지거나 빠지지 않았는지 다듬기 전 글과 대조한다.

**확인할 것**
- [ ] 독자에게 가는 산문을 위 표의 skill로 다듬었고, 다듬기 전과 사실이 같다.
