# testing

테스트는 맞는지를 확인하는 도구이고 구조를 정하지 않는다. 언제 돌리는지는 `qef:workflow`에 있고, 완료의 정의는 `qef:finish`에 있다.

## 실패를 만났을 때

테스트가 실패하면 테스트가 틀렸을 수도 있다고 본다. 통과시키려고 구현이나 테스트를 맞추지 않는다. 먼저 어느 쪽이 요구사항과 어긋나는지 판단한다.

- 테스트가 틀렸으면 그 사실을 보고하고 고친다.
- 구현이 틀렸으면 원인을 찾는다(`qef:investigate`).
- 바꾸는 중인 부분의 실패는 예상된 것이다. 쫓지 않는다.
- 통합 때의 실패가 이번 일 때문인지 모르면, 시작 스냅샷을 `git archive <스냅샷> | tar -x -C <임시 폴더>`로 풀어 그 테스트만 돌려 가른다.

## 쓰는 순서

- 수정이나 새 동작의 테스트는 고치기 전 코드, 또는 수정을 되돌린 코드에서 실패하는 것을 직접 본다. 그래도 통과하면 그 테스트는 아무것도 지키지 않으므로 다시 쓰거나 지운다.
- 그 테스트만 돌린다. 전체를 돌리지 않는다. 이미 쓴 코드를 테스트가 없다는 이유로 지우지 않는다.

## 무엇을 쓰는가

- 쓰기 전에, 어떤 제품 코드 변경이 이 테스트를 실패시키는지와 그것이 버그인지 결정인지를 말할 수 있어야 한다. 말할 수 없으면 쓰지 않는다. 절차를 채우려고 쓴 테스트는 유지 비용만 남긴다.
- 기대값은 요구사항이나 명세에서 손으로 정한다. 대상 코드를 돌려 나온 값을 기대값으로 옮기지 않고, 대상 코드의 계산을 테스트에 되풀이하지 않는다.
- 사용자가 부르는 공개 경로로 부르고, 호출보다 결과 상태를 본다. 상수 값, 문구, 내부 구조가 아니라 그것에 기대는 동작을 본다.
- 동작 하나에 테스트 하나를 둔다. 실패하면 어느 동작이 깨졌는지 바로 알 수 있어야 한다. 단언이 없거나 약한 테스트를 쓰지 않는다.
- 스크립트·설정·스킬에 어떤 줄이 들어 있는지 grep하는 테스트를 쓰지 않는다.
- 자기 코드의 경계 약속을 본다. 프레임워크 동작을 다시 보지 않는다.
- 꼬인 지금 동작을 새 테스트로 고정하지 않는다. 구조가 꼬였으면 동작도 꼬였을 수 있다.

## 층

- 층은 이름이 아니라 그 테스트에서 무엇이 실제이고 무엇이 test double인지로 가른다. 단위·통합·E2E의 뜻은 출처마다 다르다.
- 검사마다, 그 결함에서 실패할 수 있는 가장 싼 층에 둔다. test double 뒤에서 생기는 결함(권한, 저장, 직렬화, 오류 매핑, 설정)은 그 test double을 쓴 테스트에서 실패할 수 없다.
- 실제 컴포넌트를 모두 쓰는 테스트는 사용자가 밟는 여정과, 그 여정에서 실제 경계에 기대는 결과만 본다. 분기마다의 문구와 버튼은 하위 층이 본다.
- 상위 층에서만 실패가 나면 그 결함을 재현하는 하위 층 테스트를 먼저 더한다.
- 층 사이 겹침을 정리할 때 단위는 테스트가 아니라 단언이다. 단언마다 잡는 결함을 이름 붙이고, 실제 컴포넌트를 쓰는 하위 층 테스트 가운데 그 결함에서 실패하는 것이 있을 때만 그 단언을 뺀다. 겹친 테스트는 지우지 않고 겹치지 않게 좁힌다.

## 격리

- 테스트는 다른 테스트가 만든 데이터나 실행 순서에 기대지 않는다. 혼자 돌려도, 순서를 바꿔도 결과가 같아야 한다.
- 테스트가 바꾸거나, 있다고·몇 개라고 단언하는 데이터는 그 테스트가 겹치지 않는 이름과 키로 만든다. 여러 테스트가 함께 쓰는 준비 데이터는 읽기만 한다.
- 준비는 화면이 아니라 API나 fixture로 한다. 화면으로 만드는 흐름은 그 흐름의 테스트에서 한 번 본다.
- 새로 쓴 테스트는 혼자, 여러 번 돌려 본다.

## test double

- 실제 구현, fake, stub, 호출 검증(mock) 순서로 고른다. 앱이 혼자 쓰는 의존(자기 DB, 같은 저장소의 서버)은 할 수 있으면 실제로 쓰고, 다른 시스템이 관찰하는 바깥 의존만 test double로 바꾼다.
- 외부 라이브러리 타입이 아니라 그것을 감싼 자기 경계를 test double로 바꾼다.
- test double이 실제와 같은 계약인지는 검사로 확인한다. test double의 요청과 응답을 실제 쪽이 쓰는 스키마로 검사하고, 실제 쪽도 그 스키마를 지키는지 테스트한다. 스키마가 없으면 fake와 실제에 같은 테스트를 돌리거나 contract test를 둔다. 형식 밖의 동작(이 권한이면 거절된다 같은 것)은 실제를 쓰는 테스트가 본다.
- test double 자체에 단언하지 않는다.
- test double을 두기 전에 실제 메서드의 부작용을 확인하고, 테스트가 기대는 부작용은 실제로 둔다.
- 인자, 호출 횟수, 순서가 약속이면 단언한다. 성공·오류·잘못된 형식은 따로 준비해 틀린 분기가 기대를 채우지 못하게 한다.
- test double 준비가 테스트 본문보다 커지면 실제 구성 요소로 통합 테스트를 쓴다.
- 테스트만 쓰는 메서드는 제품 클래스가 아니라 테스트 utility에 둔다.

## 신호와 확인

- 테스트 쓰기가 어렵거나 전부 test double로 바꿔야 하면 설계를 의심한다(`qef:model`, `qef:layout`).
- 바뀐 줄에서 그럴듯한 코드 변형(틀린 상수·인자, 틀린 분기, 빠진 상태 변경, 빈 값 반환, 빠진 검증)을 몇 개 떠올리고, 그 변형에서 실패하는 테스트가 있는지 본다.
- 기다림은 임의의 시간이 아니라 조건을 기다린다. 시간 자체를 볼 때만 근거를 적고 timeout을 쓴다.
- 검사 장치를 만들었으면 걸려야 할 양쪽 실패 사례를 하나씩 만들어 둘 다 걸리는지 본다.
