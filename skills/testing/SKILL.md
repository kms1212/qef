# testing

테스트는 맞는지를 확인하는 도구이고 구조를 정하지 않는다. 언제 돌리는지는 `qef:workflow`에 있고, 완료의 정의는 `qef:finish`에 있다.

## 실패를 만났을 때

테스트가 실패하면 테스트가 틀렸을 수도 있다고 본다. 통과시키려고 구현이나 테스트를 맞추지 않는다. 먼저 어느 쪽이 요구사항과 어긋나는지 판단한다.

- 테스트가 틀렸으면 그 사실을 보고하고 고친다.
- 구현이 틀렸으면 원인을 찾는다(`qef:investigate`).
- 바꾸는 중인 부분의 실패는 예상된 것이다. 쫓지 않는다.
- 통합 때의 실패가 이번 일 때문인지 모르면, 시작 스냅샷을 `git archive <스냅샷> | tar -x -C <임시 폴더>`로 풀어 그 테스트만 돌려 가른다.

## 쓰는 순서

코드 전에 테스트를 먼저 써도 되고, 그 테스트만 돌려 실패를 보는 것도 좋다. 전체를 돌리지 않는다. 이미 쓴 코드를 테스트가 없다는 이유로 지우지 않는다.

## 무엇을 쓰는가

- 쓰기 전에, 어떤 제품 코드 변경이 이 테스트를 실패시키는지와 그것이 버그인지 결정인지를 말할 수 있어야 한다. 말할 수 없으면 쓰지 않는다. 절차를 채우려고 쓴 테스트는 유지 비용만 남긴다.
- 기대값은 대상 코드 없이 손으로 정한다. 대상 코드의 계산을 테스트에 되풀이하지 않는다.
- 상수 값, 문구, 내부 구조가 아니라 그것에 기대는 동작을 본다.
- 스크립트·설정·스킬에 어떤 줄이 들어 있는지 grep하는 테스트를 쓰지 않는다.
- 자기 코드의 경계 약속을 본다. 프레임워크 동작을 다시 보지 않는다.
- 꼬인 지금 동작을 새 테스트로 고정하지 않는다. 구조가 꼬였으면 동작도 꼬였을 수 있다.

## mock

- mock 자체에 단언하지 않는다.
- mock은 느리거나 바깥에 있는 층에서만 쓰고, 실제 구조를 빠짐없이 흉내 낸다.
- mock을 두기 전에 실제 메서드의 부작용을 확인하고, 테스트가 기대는 부작용은 실제로 둔다.
- 인자, 호출 횟수, 순서가 약속이면 단언한다. 성공·오류·잘못된 형식은 따로 준비해 틀린 분기가 기대를 채우지 못하게 한다.
- mock 준비가 테스트 본문보다 커지면 실제 구성 요소로 통합 테스트를 쓴다.
- 테스트만 쓰는 메서드는 제품 클래스가 아니라 테스트 utility에 둔다.

## 신호와 확인

- 테스트 쓰기가 어렵거나 전부 mock해야 하면 설계를 의심한다(`qef:model`, `qef:layout`).
- 그럴듯한 코드 변형(틀린 상수·인자, 틀린 분기, 빠진 상태 변경, 빈 값 반환, 빠진 검증)을 떠올리고, 그 변형에서 실패하는 테스트가 있는지 본다.
- 기다림은 임의의 시간이 아니라 조건을 기다린다. 시간 자체를 볼 때만 근거를 적고 timeout을 쓴다.
- 검사 장치를 만들었으면 걸려야 할 양쪽 실패 사례를 하나씩 만들어 둘 다 걸리는지 본다.
