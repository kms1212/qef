# plan

spec에는 무엇과 왜를, 계획에는 어떻게를 쓰고 서로 옮겨 적지 않는다. 계획은 값을 옮겨 적는 대신 spec의 위치를 가리킨다.

계획은 구현하는 쪽이 혼자 정할 수 없는 결정의 집합이다. 파일, 이름과 시그니처, 부분 사이의 인터페이스를 적는다. 코드보다 길어지면 코드를 대신 쓴 것이다.

## 나누기

- 각 부분은 끝났을 때 동작하고 merge할 수 있어야 한다. 부분을 바꾸는 동안은 동작하지 않아도 된다.
- 여러 부분이 쓸 것을 먼저 만든다. 나중에 합치면 다시 고치게 되기 때문이다.
- 다른 부분이 의존하는 부분을 앞에 둔다.
- 함께 바뀌는 파일은 함께 둔다. 기술 계층이 아니라 책임으로 나눈다. 경계의 기준은 `qef:layout`에 있다.

## 형식

```markdown
# <일 이름> 계획

요구사항: <goal.md 경로>
구조: <structure.md 경로>

## 요구사항에 명시되지 않은 입력
- <실제로 들어올 입력이나 실패> — <사용자가 받을 동작> — <맡는 부분>

## 부분 1: <이름>
- 파일: <만들고 고치는 파일과 각각 하는 일>
- 의존하는 것: <앞 부분에서 받는 이름과 타입>
- 제공하는 것: <뒤 부분이 쓸 이름과 타입>
- 단계: <한 단계에서 구현자가 쓸 수 있는 합당한 것이 하나뿐이도록>
- 완료 기준: <이 부분의 테스트 또는 확인 방법>
```

단계에 커밋, 전체 테스트, reviewer를 넣지 않는다. 커밋은 사용자가 시킬 때 `qef:commit`으로 하고, 테스트 시점은 `qef:testing`에 있다.

## 쓰고 나서

- 결정하지 않은 줄을 찾아 정한다. "TBD", "예외를 적절히 처리", "알맞은 검증 추가"는 빈칸이다. 정해지지 않는 것은 왜 그런지와 함께 적는다.
- 같은 함수가 부분마다 다른 이름으로 불리지 않는지, 내놓는 것과 쓰는 것이 맞는지 본다.
- spec 항목마다 맡는 부분이 있는지 본다.
- 요구사항이 말하지 않았어도 실제로 들어올 입력과 실패 가운데 사용자가 겪을 만한 것을 적고, 맡는 부분의 "완료 기준"에 넣는다. 말이 없다고 깨져도 되는 것은 아니다. 일어날 수 없는 경우는 적지 않고, 사용자가 받을 동작이 달라지면 요구사항이니 묻는다.

계획 파일의 위치는 `qef:job`의 "기록과 보고"를 따른다. 시킨 일이면 쓴 뒤 다시 묻지 않고 실행한다.
