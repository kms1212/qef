# dev

## 원칙

큰 틀을 먼저 정하고, 그 아래를 한 부분씩 정해 가며 만든다. 사람이 큰 재작성을 할 때처럼 한다.

- **위층부터 정한다.** 위층은 패키지·모듈 경계와 개념의 자리다. 위층을 정한 뒤에 그 아래의 파일 구성과 코드를 정한다. 파일 전부를 미리 정하지 않는다.
- **아래층은 그 부분을 맡을 때 정한다.** 이미 만든 것을 보고 다음 부분을 정한다.
- **어느 정도의 오류는 감수한다.** 아래층에서 생긴 문제는 그 자리에서 고친다. 그것 때문에 위층을 다시 열지 않는다. 위층을 다시 여는 것은 위층 결정이 성립 조건을 통과하지 못한다는 것이 드러났을 때뿐이다.
- **멈추지 않는다.** 사람을 부르는 것은 아래 "사람을 부르는 경우"뿐이다. 그 밖의 판단은 기준으로 정하고, 기록하고, 계속한다. 기록은 끝에 한 번 모아 보인다.
- **기준은 `criteria/`에 있다.** 구조는 `structure.md`, 동작 확인은 `verification.md`, 점검은 `review-lenses.md`, 재사용은 `reuse.md`를 따른다. 웹 프로젝트(HTTP API 백엔드, 웹 프론트엔드)면 `qef:web` 스킬의 기준도 따른다.
- **사용자에게 하는 말은 사용자가 쓴 언어로 쓴다.** 도구 결과, 알림, 하위 에이전트 보고가 다른 언어여도 바꾸지 않는다.

## 시작

1. 요청을 읽고, 관련 코드와 프로젝트 문서를 읽는다. 범위가 넓으면 읽기 전용 하위 에이전트 하나에게 맡긴다.
2. 모드를 정한다(아래 "모드"). 요청만으로 정해지지 않으면 묻지 않고 아래 기준으로 정한다.
3. 실행 폴더를 정한다(아래 "실행 기록"). 같은 일의 끝나지 않은 폴더가 있으면 그 `run.md`와 `ledger.md`를 읽고 이어서 한다. 없으면 새로 만들고 `run.md`에 요청 원문, 모드, 언어를 쓴다.
4. 기준선을 남긴다. 빌드와 시험을 지금 상태에서 한 번 돌려 결과를 `run.md`에 적는다. 이미 실패하는 것도 그대로 적는다.

## 모드

| 모드 | 언제 | 끝났다는 뜻 |
|---|---|---|
| `build` | 기존 코드가 없는 새 프로젝트 | 할 수 있게 되는 것이 관찰 가능한 결과로 확인된다 |
| `extend` | 기존 프로젝트에 기능 추가·수정·버그 수정 | 위와 같고, 건드리지 않은 동작은 기준선과 같다 |
| `refactor` | 외부 동작은 그대로 두고 구조만 바꿈 | 성립 조건(구조 기준)을 통과하고, 외부 동작이 기준선과 같다 |

모드를 정하는 기준: 요청의 표준 뜻이 외부 동작을 바꾸는가. "정리해줘", "구조 바꿔줘"는 동작을 바꾸지 않으므로 refactor다. "고쳐줘", "추가해줘"는 extend다. 기능도 바꾸고 구조도 바꾸는 요청이면 둘로 나눠, 동작 변경을 먼저 한다. 사용자가 구조를 다시 짜면서 외부 동작이 바뀌는 것도 허용하면 refactor로 다룬다. 허용된 외부 동작이 바뀐 곳은 기준선 비교에서 의도한 변경으로 따로 적는다.

**외부 동작**:

| 포함 (바뀌면 extend) | 포함 안 함 (refactor에서 바뀌어도 됨) |
|---|---|
| 공개 인터페이스: API 경로·시그니처, CLI 인자, 설정 키 | 응답 지연, 처리량, 메모리·CPU 사용량 |
| 출력: 값, 형식, 순서, 개수, 오류 응답 | 내부 구조, 내부 함수·모듈 경계 |
| 부수효과: 저장되는 데이터, 외부 호출, 이벤트·메시지 | 내부 로그 |
| 결과 신선도: 결과가 어느 시점의 데이터를 반영하는지 | |
| 실행 방식: 동기↔비동기, 재시도·타임아웃 정책, 트랜잭션 경계 | |

지연·자원 사용량이라도 계약(SLA, 문서화된 타임아웃)에 걸려 있으면 포함한다.

## 흐름

### 1. 조사와 큰 틀

대상 전체를 보고 위층만 정한다. `run.md`의 "큰 틀"에 쓴다.

- 감사(refactor는 대상 전체, extend는 이번에 손대는 부분): 큰 틀을 정하기 전에, 적용되는 기준 파일의 모든 절을 대상의 모든 부분(최상위 패키지·앱·DB)에 대어 `run.md`의 "감사" 표를 채운다. 칸마다 맞음 / 어긋남(근거 파일) / 해당 없음 중 하나를 적는다. 빈칸이 있으면 큰 틀로 넘어가지 않는다. 큰 틀은 어긋난 칸을 모두 덮어야 한다.
- 무엇이 성립해야 끝인지: build·extend는 관찰 가능한 결과로, refactor는 `structure.md`의 규칙에 대어 쓴다. 지금 구조를 적은 문서(패키지 표, 의존 그림)는 기준이 아니라 함께 고칠 대상이다.
- 목표 구조: 패키지·모듈마다 그 큰 개념과 주요 하위 개념, 개념마다 그 자리, 의존 방향.
- 타입 모델: 패키지·모듈마다 주요 타입과 그 책임, 상위 타입과 그 하위 타입(is-a), 무엇이 무엇을 갖는지(has-a). `structure.md`의 도메인 개념 모델링 규칙으로 정한다. 디렉터리는 이 모델에서 나온다. 파일 목록은 쓰지 않는다.
- 다른 안: 가장 적게 바꾸는 안을 포함해 둘 이상을 견주고, 고른 이유를 한두 줄로 쓴다.
- 이미 있는 것: `reuse.md`대로 찾는다.
- 읽다가 찾은 결함: 고치지 않고 "남긴 결함"에 적는다. refactor에서는 결함도 지금 동작이다.

### 2. 할 일 목록

큰 틀을 작은 단위로 나눠 `ledger.md`에 순서대로 적는다. 단위 하나는 한 번에 끝내고 검증할 수 있는 크기다.

| 칸 | 내용 |
|---|---|
| 번호 | L1, L2 … |
| 할 일 | 무엇을 어디로 바꾸는지 한 문장 |
| 지킬 동작 | 이 단위가 바꾸면 안 되는 것 |
| 검증 | 끝났는지 보는 명령과 기대 결과 |
| 상태 | 할 일 / 진행 / 끝 / 보류(이유) / 의도된 것(고치지 않음) |

refactor에서는 지울 것(쓰이지 않는 코드) → 합칠 것(중복) → 옮길 것과 나눌 것 → 이름과 문서 순으로 둔다. 어느 모드든 다른 단위가 기대는 단위를 먼저 둔다.

### 3. 단위마다

`ledger.md`의 다음 단위를 하나씩 끝낸다.

1. 이 단위의 아래층을 정한다: 만들고 옮길 파일과 각 파일이 하는 일. `structure.md`의 파일 규칙을 따른다.
2. 바꾼다.
3. 검증 칸의 명령을 돌린다. 기준선보다 나빠진 것이 없어야 한다.
4. `review-lenses.md`로 스스로 점검하고, 걸린 것을 이 단위 안에서 고친다.
5. 커밋하고 상태를 "끝"으로 바꾼다.

도중에 찾은 일은 이 단위의 몫이면 함께 하고, 아니면 `ledger.md`에 새 줄로 더한다. 쓰기 범위·순서·방법은 이 단위 안에서 판단한다. 판단한 것은 `run.md`의 "판단 기록"에 한 줄씩 남긴다.

### 4. 마무리

1. 모든 단위가 끝나면 바뀐 코드 전체를 `review-lenses.md`로 한 번 더 점검한다. 범위가 크면 읽기 전용 하위 에이전트 하나에게 맡긴다.
2. 기준선과 같은 명령을 돌려 비교한다(`verification.md`의 "끝낼 때").
3. `run.md`에 "마무리" 절을 쓰고, 사용자에게 같은 내용을 보인다.
   - 바뀐 것: 큰 틀과 단위별 결과, 커밋
   - 동작 확인: 기준선과 비교한 결과, 확인하지 못한 것
   - 판단 기록: 혼자 정한 것과 감수한 것
   - 남긴 결함과 보류한 단위

## 사람을 부르는 경우

아래일 때만 멈추고 묻는다. 물을 때는 기본값과 그 이유를 붙이고, 답을 기다리는 동안 그 결정과 무관한 단위는 계속한다.

- 사용자가 허용하지 않은 외부 동작을 바꿔야만 할 수 있는 결정. refactor에서 이런 것이 나오면 그 단위를 보류하고 묻는다.
- 되돌리기 어려운 결정: 다른 사람이 최근에 만든 작업을 지우는 것, 저장된 데이터의 모양을 바꾸는 것, 새 외부 의존성을 들이는 것.
- 요청의 의도를 기준으로도 정할 수 없을 때. 질문은 하나만 한다.
- 큰 틀이 패키지나 최상위 모듈의 경계를 바꿀 때. 큰 틀을 정한 뒤, 할 일 목록에 들어가기 전에 한 번 보이고 기다린다. 보일 것: 감사 표에서 어긋난 칸의 요약, 목표 구조(패키지·모듈마다 그 큰 개념과 주요 하위 개념, 개념의 자리, 의존 방향), 타입 모델, 견준 안과 고른 이유. 위층이 틀리면 가장 비싼 실수가 되기 때문이다. 경계를 바꾸지 않는 작업은 보이지 않고 계속한다.

## 실행 기록

위치: `~/.qef/runs/<저장소 경로의 /를 -로 바꾼 것>/<작업 이름>/`. 저장소 경로는 git 작업 트리 안에서도 원래 저장소의 경로다(`git rev-parse --path-format=absolute --git-common-dir`의 상위 폴더). 그래야 작업 트리가 바뀌어도 같은 폴더를 찾는다. 작업 이름은 요청을 줄인 짧은 영어 소문자·하이픈 이름이다(예: `common-cleanup`). 프로젝트 밖이라 저장소를 더럽히지 않고, 여러 세션에 걸친 일도 같은 폴더에서 이어 한다.

| 파일 | 내용 |
|---|---|
| `run.md` | 요청 원문, 모드, 언어, 기준선, 감사, 큰 틀, 판단 기록, 남긴 결함, 마무리 |
| `ledger.md` | 할 일 목록 |

`run.md`에 "마무리" 절이 있으면 끝난 작업이다. 없으면 끝나지 않은 작업이다.

컨텍스트가 압축됐거나 어디까지 했는지 모르겠으면 `run.md`와 `ledger.md`부터 다시 읽는다.
