# dev

원칙마다 의도, 규칙, 확인할 것을 둔다. 규칙에 없는 상황은 그 원칙의 의도와 「판단의 기준」으로 판단한다. 사용자가 실제 프로젝트에서 짚은 장면은 [references/cases.md](references/cases.md)에 있다.

## 판단의 기준

이 질문은 코드를 다루는 동안 내내 적용한다. 다른 기준의 답이 갈리면 여기로 정한다.

**구조가 동작과 테스트보다 먼저다.** 테스트가 통과하고 기능이 작동해도 구조가 나쁘면 끝난 것이 아니다. 고쳐졌는지가 아니라 구조가 고쳐졌는지를 본다.

**사람이 읽고 바로 파악할 수 있는가.** 더할지 뺄지는 모두 이 질문으로 달라진다. 팩토리를 둘지, 추상화를 둘지, 계층을 뺄지를 줄 수나 반복 여부로 정하지 않는다. 트리를 보고, 파일을 열고, 무엇을 하는지 바로 알 수 있는 쪽을 고른다. 어느 쪽이 더 읽기 쉬운지가 검증이다.

**기준은 휴리스틱이다.** 숫자(줄 수, 개수)로 두지 않고 한 방향의 금지로 읽지 않는다. 특정 프로젝트의 규칙으로 좁히지 않는다.

## 요청이 가리키는 것만 바꾸되, 그 원인까지 바꾼다

**의도.** 요청하지 않은 것을 더하면 유지할 코드와 사용자가 확인할 것만 늘고, 그것이 다음 일의 전제처럼 굳는다. 반대로 증상이 난 곳만 고치면 같은 원인이 다른 곳에서 다시 나온다. 요청은 글자가 아니라 그것이 가리키는 대상 전체다.

**규칙**
- 코드를 쓰기 전에 [references/ms-yagni.md](references/ms-yagni.md)를 끝까지 읽고 따른다. 이 스킬이나 사용자의 말과 충돌하면 이 스킬과 사용자의 말을 따른다. 27행 "Change only what is necessary. Clean up only the problems that your changes cause."와 28행 "Do not improve adjacent code … Do not refactor code that is not broken."은 원인이 생긴 계층과 같은 원인의 다른 곳을 고치는 것을 막지 않는다. 그곳은 「판단의 기준」, 「같은 지식은 한 곳에 두되, 변경 이유가 다르면 합치지 않는다」, 「결함은 같은 원인 전부를, 그 원인이 생긴 계층에서 고친다」을 따른다. 테스트가 통과하고 동작해도 이 스킬과 `qef:model`, `qef:layout`의 규칙에 어긋나면 고장 난 코드다.
- 요청을 이루는 데 표준과 상식으로 당연히 필요한 처리는 요청이 가리키는 것에 들어가므로, 묻지 않고 처음부터 갖춘다. 올리는 파일의 크기 제한이나 올리기 전 이미지 크기 줄이기 같은 것이다.
- 사용자가 시키지 않은 예외(특정 경우만 다르게 처리하는 조건, 우회)를 코드에도 문서와 생성기 같은 산출물에도 두지 않는다. 예외 하나가 생기면 에이전트는 그 선례를 따라 예외를 늘려, 제품이 예외로 채워진다. 구조가 그 경우를 담지 못하면 구조를 고치거나 묻는다. 종류마다 달라야 하는 동작은 예외가 아니다.
- 요청하지 않은 기능, abstraction, 설정, error handling, 파일은 만들지 않는다. 정말 필요해 보이는 것도 만들기 전에 사용자에게 아래를 자세히 말하고 허가를 받는다. 허가를 받기 전에는 만들지 않고, 만든 뒤에 알리는 것으로 대신하지 않는다.
  - 무엇을 만들려는가
  - 왜 필요한가: 없으면 무엇이 깨지거나 사용자가 무엇을 하지 못하는가
  - 그 근거: `파일:줄`, 명령 출력, 요구사항 줄
  - 만들면 드는 비용: 늘어나는 코드, 유지보수, 다른 곳에 주는 영향
- 바꾸는 줄마다 그 줄이 요청이 가리키는 것에 닿는지 댈 수 있어야 한다. 고치라는 요청은 증상이 난 곳만이 아니라 그 원인이 생긴 계층과 같은 원인의 다른 곳까지 가리킨다. 댈 것이 없는 줄은 바꾸지 않는다.
- 요청한 변경의 결과가 나빠 보여도, 기존 동작을 바꿔서 고치지 않는다. 무엇이 왜 나빠 보이는지 알리고 묻는다. 기존 코드가 자기가 정한 동작(요구사항, 주석, 문서)대로 동작해서 나온 결과는 결함이 아니다. 정한 동작과 다르게 동작하거나 이 스킬, `qef:model`, `qef:layout`의 규칙에 어긋나는 것이 결함이고, 결함은 「결함은 같은 원인 전부를, 그 원인이 생긴 계층에서 고친다」대로 원인이 생긴 계층에서 고친다.

**확인할 것**
- [ ] 바꾼 줄마다 요청이나 그 원인에 닿는 근거를 댈 수 있다.
- [ ] 허가 없이 더한 기능, 설정, 파일, error handling이 없다.

근거: Martin Fowler, "Yagni"(앞으로 필요할 것이라 짐작하는 기능은 지금 만들지 않는다) (https://martinfowler.com/bliki/Yagni.html).

## 강하게 잡을지는 틀렸을 때 어떻게 되는지로 정한다

**의도.** 모든 것을 똑같이 엄격하게 잡으면 사람이 그 자리에서 보고 고칠 수 있는 것까지 막혀 쓰기 어려워진다. 반대로 저장과 API에 남는 것을 느슨하게 두면 틀린 값이 퍼지고, 여러 곳이 그 값을 믿고 다시 확인하지 않는다.

**규칙**
- 코드에 강하게 둘지 넘어갈지는 값, 구조, 동작 모두 규칙이 중요해 보이는지가 아니라 틀렸을 때 어떻게 되는지로 정한다.

  | 묻는 것 | 잡는다 | 넘어간다 |
  |---|---|---|
  | 틀린 것을 누가 언제 알아차리는가? | 나중에 다른 사람이 발견한다 | 당사자가 그 위치에서 보고 고친다 |
  | 남거나 퍼지는가? | 저장, API, 이력, 마이그레이션에 남는다 | 그 화면이나 함수에서 끝난다 |
  | 다른 것이 여기에 의존하는가? | 여러 곳이 믿고 다시 확인하지 않는다 | 사용처가 하나이고 쉽게 바꾼다 |
  | 푼 비용이 그 위치에서 끝나는가? | 조회 비용이 데이터 전체로 퍼지거나 결과를 예측하기 어려워진다 | 글자 하나를 읽고 끝난다 |

- 잡는 것은 검사를 늘리는 것이 아니다. 경계 한 곳에서 파싱해 정확한 타입으로 변환하고 내부에서는 다시 검증하지 않는다. 수단은 대체로 타입과 DB 제약 조건, 경계에서의 거부, 정적 분석, 테스트, 규칙 문구 순으로 강하다.
- 넘어가는 것은 방치가 아니다. 사람이 보고 고치게 보여 주거나 나중에 바꾸기 쉽게 둔다. 화면은 사람의 입력을 정제해 형식에 맞추고, 서버는 엄격하게 받는다. 둘 다 판정한다.
- 잡는 것과 하드코딩은 다르다. 값의 형태와 종류는 잡고, 바뀌는 값은 데이터로 둔다(`qef:model`).
- API는 쓰는 쪽이 우리 것뿐이어도 잡는다. 받아 준 값은 저장에 남는다.
- 잡기 전에 이미 있는 데이터가 새 규칙에 막히지 않는지 본다.
- 거꾸로 두지 않는다: 검사하기 쉬운 곳에 검사가 몰린다. 입력 글자의 쉼표 위치는 따지면서 저장되는 형태는 경로마다 다르면 거꾸로다.
- 옮겨 대지 않는다: 한 위치의 규칙을 다른 위치에 같은 강도로 옮기지 않는다. 옮기는 규칙이 버리는 것이 거기서도 뜻이 없는지 본다.

**확인할 것**
- [ ] 저장과 API에 남는 값은 경계 한 곳에서 정확한 타입으로 바뀐다.
- [ ] 같은 검증이 내부에서 되풀이되지 않는다.

사례는 `qef:layout`의 [references/examples.md](../layout/references/examples.md)의 「위치마다 다른 엄격함」에도 있다. 근거: Alexis King, "Parse, don't validate"(경계에서 한 번 파싱하면 다시 검사할 필요가 없다) (https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/).

## 쓰기 전에 이미 있는 것을 찾는다

**의도.** 이미 있는 것을 다시 만들면 같은 일을 하는 코드가 두 벌이 되어 서로 어긋나고, 나중에 합치려면 다시 고쳐야 한다. 찾았다는 근거가 남지 않으면 정말 없었는지, 찾지 않았는지 알 수 없다.

**규칙**
- 쓰기 전에 아래 순서로 찾는다. 찾은 것마다 `경로:줄`이나 URL과, 찾는 데 쓴 명령을 남긴다. 「없다」고 판단할 때도 찾은 명령을 남긴다.
  1. 이 저장소에서 같은 개념, 같은 일을 하는 코드(언어 서버의 심볼 검색, grep)
  2. 프로젝트의 공유 패키지와 이미 도입한 의존성
  3. 표준 라이브러리와 그 스택의 공식 문서
  4. 오픈소스 구현과 라이브러리(GitHits: `githits-mcp`, 패키지는 `githits-package`)
- 찾은 것이 이 기능을 주면 쓴다. 처음부터 그 라이브러리로 개발했어도 무난하게 진행할 수 있었을까? 그렇다면 현재 동작과 조금 달라도 라이브러리를 쓴다. 라이브러리가 정한 규칙은 그 결정을 따른다. 고를 때는 쓰는 사람이 많고 유지보수가 잘 되는 것을 고른다.
- 맞는 라이브러리가 없으면 가까운 라이브러리를 확장해 쓸 수 있는지 본다.
- 과하게 들이지 않는다: 직접 써도 될 만큼 단순한 일에 큰 라이브러리를 들고 오지 않는다.
- 새 외부 의존성(코드가 쓸 라이브러리·패키지, 작업 도구)을 설치할지는 사용자가 정한다. 없으면 다른 수단으로 조용히 대신하거나 직접 구현하지 않고, 후보와 이유를 보여 주고 설치할지 묻는다. 직접 구현하기로 할 때는 이유와 이번에 검색한 출처를 밝힌다.
- 들인 도구가 저장소에 만드는 파일(캐시, 빌드 결과)은 저장소 밖에 두거나 `.gitignore`에 넣는다. 언어를 새로 들이면 그 언어 스킬의 「들일 때」를 따른다.
- 여러 곳이 쓸 공통 부분은 먼저 만들고, 각 부분은 그것을 가져다 쓴다. 만든 뒤에 합치면 다시 고치게 된다.

**확인할 것**
- [ ] 새로 만든 함수·타입·모듈마다 찾은 곳과 찾은 명령이 남아 있다.
- [ ] 쓸 수 있는 의존성이 없을 때 조용히 직접 구현하지 않고 설치를 물었다.

## 같은 지식은 한 곳에 두되, 변경 이유가 다르면 합치지 않는다

**의도.** 같은 지식이 여러 곳에 흩어지면 한 곳만 바뀌어 서로 어긋난다. 반대로 형태만 같고 변경 이유가 다른 것을 억지로 합치면, 한쪽이 바뀔 때마다 그 공용 코드에 조건이 붙어 잘못된 추상화가 된다. 잘못된 추상화는 중복보다 비싸다.

**규칙**
- 흩어 두지 않는다: 같은 타입 별칭·함수·상수·검증이 여러 파일에 따로 있으면 공용으로 뺀다. 새로 쓰는 코드끼리도 같다. 공용 로직을 빼는 것을 범위 밖 일이나 위험으로 보지 않는다.
- 엉뚱하게 묶지 않는다: 중복을 함수 하나로 커버하고 끝내지 않는다. 타입 모델에 들어갈 것은 타입으로 만든다. 형태만 같고 변경 이유가 다른 것은 합치지 않는다.
- 노출을 줄인다: 밖에서 쓰지 않으면 export하지 않는다. 쓰지 않는 import를 남기지 않는다.

**확인할 것**
- [ ] 바꾼 범위에서 같은 상수·검증·타입이 두 곳에 정의되어 있지 않다.
- [ ] 공용으로 뺀 코드에 쓰는 쪽마다 다른 분기가 붙어 있지 않다.

근거: Sandi Metz, "The Wrong Abstraction"(중복은 잘못된 추상화보다 훨씬 싸다) (https://sandimetz.com/blog/2016/1/20/the-wrong-abstraction).

## 판단은 끝까지 읽은 것과 도구가 센 것으로 한다

**의도.** 일부만 읽고 판단하면 읽지 않은 곳에서 틀린다. 판단이 필요 없는 것을 눈으로 세면 빠뜨린다.

**규칙**
- 구조나 동작을 검증하는 데 쓰는 코드와 문서는 일부만 보고 판단하지 않는다. Read 결과가 `PARTIAL view`면 남은 쪽을 마저 읽는다. 긴 출력은 파일로 보내 필요한 곳을 읽는다.
- 아래 일은 도구에 맡긴다. 도구가 설치되어 있지 않으면 「쓰기 전에 이미 있는 것을 찾는다」의 새 의존성 규칙대로 한다.

  | 일 | 의존하는 것 |
  |---|---|
  | 정의, 참조, 구현, 호출 계층 구조 찾기 | 언어 서버(LSP 도구). 글자 찾기가 아니라 심볼로 찾는다 |
  | 포맷 | 프로젝트의 포매터. 손으로 맞추지 않는다 |
  | 이름 바꾸기, 코드 옮기기 | `qef:refactor` |
  | 의존 방향, 순환, 중복, 쓰지 않는 export | 정적 분석 도구. 의존 규칙은 `qef:layout`의 「의존 규칙은 검사로 둔다」 |

**확인할 것**
- [ ] 판단에 쓴 파일을 끝까지 읽었다.

## 결함은 같은 원인 전부를, 그 원인이 생긴 계층에서 고친다

**의도.** 문제를 하나씩 덮으면 같은 원인의 문제가 끝없이 다시 나오고, 덮을 때마다 예외가 쌓여 구조가 누더기가 된다.

**규칙**
- 함께 읽다 찾은 같은 원인의 결함은 이번 일 밖이어도 고치고 보고한다. 안만 표시하고 두지 않는다. 표시만 한 결함은 아무도 고치지 않기 때문이다.
- 고칠 때는 증상이 아니라 그 결정이 잘못된 계층에서 고친다. 이슈가 여럿이면 하나씩 고치지 않고, 공통 원인을 찾아 그것을 덮는 구조를 만든다.
- 규칙대로 하면 막히는 곳에 예외를 남기지 않는다. 그 규칙을 제대로 다시 정한다.
- 바꿀 때는 옛것을 먼저 빼고 새것을 더한다. 바꾸는 동안 잠시 동작하지 않는 상태는 정상이다(`qef:refactor`).

**확인할 것**
- [ ] 고친 결함마다 원인이 생긴 계층과, 같은 원인의 다른 곳을 찾은 결과가 적혀 있다.
- [ ] 이번 수정이 새 예외 경로를 만들지 않았다.

## 보안 결함을 만들지 않는다

**의도.** 기능이 동작해도 보안 결함이 있으면 공격 경로가 된다. 결함의 종류를 몇 가지 예시로만 떠올리면 그 밖의 종류(접근 제어, 인증, 설정)는 보지 않게 된다. 검증을 안쪽 코드마다 덧붙이면 코드만 무거워지고, 정작 입력이 들어오는 경계는 비어 있기 쉽다.

**규칙**
- 코드를 쓰거나 고칠 때 OWASP Top 10의 범주에 드는 취약점을 만들지 않는다. 쓴 코드에서 찾으면 그 자리에서 고친다. 지금 판(2025)의 범주는 아래 열 가지이고, 새 판이 나오면 그 판을 따른다.
  - A01 Broken Access Control
  - A02 Security Misconfiguration
  - A03 Software Supply Chain Failures
  - A04 Cryptographic Failures
  - A05 Injection
  - A06 Insecure Design
  - A07 Authentication Failures
  - A08 Software or Data Integrity Failures
  - A09 Security Logging and Alerting Failures
  - A10 Mishandling of Exceptional Conditions
- 외부 입력(사용자 입력, 요청, 파일, 외부 API 응답)이 셸 명령, SQL, HTML, 파일 경로에 닿으면 그 형식의 안전한 방법으로 넘긴다. 인자 배열, 매개변수화한 질의, 이스케이프하는 템플릿, 정규화한 뒤 허용 범위를 확인한 경로가 그런 방법이다. 문자열을 이어 붙여 만들지 않는다.
- 검증은 외부 입력이 들어오는 경계에서 한다. 안쪽 코드끼리는 서로가 보장한 것을 믿는다.
- 비밀값을 코드, 로그, 오류 메시지, 커밋에 두지 않는다.

**확인할 것**
- [ ] 바꾼 코드를 OWASP Top 10의 범주마다 대 봤고, 해당하는 결함이 없다.
- [ ] 외부 입력이 닿는 명령·질의·화면·경로마다 그 형식의 안전한 방법으로 넘어간다.

근거: OWASP, "OWASP Top 10:2025" (https://top10.owasp.org/2025/).

## OpenSpec이 있는 저장소의 변경은 change 안에서 한다

**의도.** change 없이 바꾸면 무엇을 왜 바꿨는지와 승인받은 설계가 남지 않는다. OpenSpec 포크의 schema가 단계마다 부르는 qef skill과 Done When 대조도 빠진다.

**규칙**
- 저장소에 `openspec/`이 있으면, 그 저장소를 바꾸는 일은 모두 OpenSpec change를 만들고(`openspec-propose`) 그 안에서 한다. 그 일이 속한 change가 이미 있으면 그 change에서 한다.
- change를 어느 세션이 만드는지는 세션의 종류로 정한다(`qef:delegate` 「세션의 종류와 역할」).

**확인할 것**
- [ ] 바꾼 일마다 그 일이 속한 change가 있다.

## 보고

코드를 바꾼 뒤의 보고는 턴 끝 보고까지 모두 구조부터 말한다.

- 바뀐 부분을 이 스킬과 `qef:model`, `qef:layout`의 어느 규칙에 대조했는지, 어디가 맞고 어디가 어긋나는지를 `파일:줄`과 함께 쓴다. 어긋난 곳이 남았으면 남은 일로 쓴다.
- 테스트 통과 수는 고쳐졌다거나 끝났다는 근거로 쓰지 않는다.
- 테스트는 실패한 것과 돌리지 않은 것만 따로 적는다.
