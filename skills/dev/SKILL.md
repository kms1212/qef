# dev

## 검증 기준

이 질문은 코드를 다루는 동안 내내 적용한다. 기준의 답이 다르면 여기로 정한다.

**구조가 동작과 테스트보다 먼저다.** 테스트가 통과하고 기능이 작동해도 구조가 나쁘면 끝난 것이 아니다. 고쳐졌는지가 아니라 구조가 고쳐졌는지를 본다.

**사람이 읽고 바로 파악할 수 있는가.** 더할지 뺄지는 모두 이 질문으로 달라진다. 팩토리를 둘지, 추상을 둘지, 계층을 뺄지를 줄 수나 반복 여부로 정하지 않는다. 트리를 보고, 파일을 열고, 무엇을 하는지 바로 알 수 있는 쪽을 고른다. 어느 쪽이 더 읽기 쉬운지가 검증이다.

**기준은 휴리스틱이다.** 숫자(줄 수, 개수)로 두지 않고 한 방향의 금지로 읽지 않는다. 특정 프로젝트의 규칙으로 좁히지 않는다.

## 요청하지 않은 것

코드를 쓰기 전에 [references/ms-yagni.md](references/ms-yagni.md)를 끝까지 읽고 따른다. 이 스킬이나 사용자의 말과 충돌하면 이 스킬과 사용자의 말을 따른다. 충돌하는 곳은 아래와 같다.

- 27행 "Change only what is necessary. Clean up only the problems that your changes cause."와 28행 "Do not improve adjacent code … Do not refactor code that is not broken."은 원인이 생긴 계층과 같은 원인의 다른 곳을 고치는 것을 막지 않는다. 그곳은 「검증 기준」, 「DRY」, 「시킨 일 안에서」를 따른다. 테스트가 통과하고 동작해도 구조 기준에 어긋나면 고장 난 코드다.

요청하지 않은 기능, abstraction, 설정, error handling, 파일은 만들지 않는다. 정말 필요해 보이는 것도 만들기 전에 사용자에게 아래를 자세히 말하고 허가를 받는다. 허가를 받기 전에는 만들지 않고, 만든 뒤에 알리는 것으로 대신하지 않는다.

- 무엇을 만들려는가
- 왜 필요한가: 없으면 무엇이 깨지거나 사용자가 무엇을 하지 못하는가
- 그 근거: `파일:줄`, 명령 출력, 요구사항 줄
- 만들면 드는 비용: 늘어나는 코드, 유지보수, 다른 곳에 주는 영향

바꾸는 줄마다 그 줄이 요청이 가리키는 것에 닿는지 댈 수 있어야 한다. 고치라는 요청은 증상이 난 곳만이 아니라 그 원인이 생긴 계층과 같은 원인의 다른 곳까지 가리킨다. 댈 것이 없는 줄은 바꾸지 않는다.

요청한 변경의 결과가 나빠 보여도, 기존 동작을 바꿔서 고치지 않는다. 무엇이 왜 나빠 보이는지 알리고 묻는다. 기존 코드가 자기가 정한 동작(요구사항, 주석, 문서)대로 동작해서 나온 결과는 결함이 아니다. 정한 동작과 다르게 동작하거나 이 스킬의 구조 기준에 어긋나는 것이 결함이고, 결함은 「시킨 일 안에서」대로 원인이 생긴 계층에서 고친다.

## 잡을 곳과 넘어갈 곳

코드에 강하게 둘지 넘어갈지는 값, 구조, 동작 모두 규칙이 중요해 보이는지가 아니라 틀렸을 때 어떻게 되는지로 정한다.

| 묻는 것 | 잡는다 | 넘어간다 |
|---|---|---|
| 틀린 것을 누가 언제 알아차리는가? | 나중에 다른 사람이 발견한다 | 당사자가 그 위치에서 보고 고친다 |
| 남거나 퍼지는가? | 저장, API, 이력, 마이그레이션에 남는다 | 그 화면이나 함수에서 끝난다 |
| 다른 것이 여기에 의존하는가? | 여러 곳이 믿고 다시 확인하지 않는다 | 사용처가 하나이고 쉽게 바꾼다 |
| 푼 비용이 그 위치에서 끝나는가? | 조회 비용이 데이터 전체로 퍼지거나 결과를 예측하기 어려워진다 | 글자 하나를 읽고 끝난다 |

- 잡는 것은 검사를 늘리는 것이 아니다. 경계 한 곳에서 파싱해 정확한 타입으로 변환하고 내부에서는 다시 검증하지 않는다. 수단은 대체로 타입과 저장 제약, 경계에서의 거부, 정적 분석, 테스트, 규칙 문구 순으로 강하다.
- 넘어가는 것은 방치가 아니다. 사람이 보고 고치게 보여 주거나 나중에 바꾸기 쉽게 둔다.
- 잡는 것과 박는 것은 다르다. 값의 형태와 종류는 잡고, 바뀌는 값은 데이터로 둔다(`qef:model`).
- API는 쓰는 쪽이 우리 것뿐이어도 잡는다. 받아 준 값은 저장에 남는다.
- 잡기 전에 이미 있는 데이터가 새 규칙에 막히지 않는지 본다.
- 거꾸로 되지 않았는가: 검사하기 쉬운 곳에 검사가 몰린다. 입력 글자의 쉼표 위치는 따지면서 저장되는 형태는 경로마다 다르면 거꾸로다.
- 옮겨 대지 않았는가: 한 위치의 규칙을 다른 위치에 같은 강도로 옮기지 않는다. 옮기는 규칙이 버리는 것이 거기서도 뜻이 없는지 본다.

사례는 `qef:layout`의 [references/examples.md](../layout/references/examples.md)에 있다.

## 기존 코드 재사용

쓰기 전에 공통 부분이 어디 있는지 찾고 찾은 위치를 남긴다. 만든 뒤에 합치면 다시 고치게 된다.

- 직접 만들지 않았는가: 표준 라이브러리, 이미 도입한 의존성, 프로젝트의 공유 패키지, 이미 만든 구조가 이 기능을 주는가? 그러면 쓴다.
- 처음부터 그 라이브러리로 개발했어도 무난하게 진행할 수 있었을까? 그렇다면 현재 동작과 조금 달라도 라이브러리를 쓴다. 라이브러리가 정한 규칙은 그 결정을 따른다.
- 맞는 라이브러리가 없으면 가까운 라이브러리를 확장해 쓸 수 있는지 본다.
- 과하지 않은가: 직접 써도 될 만큼 단순한 일에 큰 라이브러리를 들고 오지 않는가?

새 의존성을 설치할지는 사용자가 정한다(결정권 표). 직접 구현하기로 할 때는 이유와 이번에 검색한 출처를 밝힌다.

## DRY

- 흩어지지 않았는가: 같은 타입 별칭·함수·상수·검증이 여러 파일에 따로 있으면 공용으로 뺀다. 새로 쓰는 코드끼리도 같다. 공용 로직을 빼는 것을 범위 밖 일이나 위험으로 보지 않는다.
- 엉뚱하게 묶지 않았는가: 중복을 함수 하나로 커버하고 끝내지 않는다. 타입 모델에 들어갈 것은 타입으로 만든다. 형태만 같고 변경 이유가 다른 것은 합치지 않는다.
- 노출: 밖에서 쓰지 않으면 export하지 않는다. 쓰지 않는 import를 남기지 않는다.

## 검증 대상은 끝까지 읽는다

- 구조나 동작을 검증하는 데 쓰는 코드와 문서는 일부만 보고 판단하지 않는다. Read 결과가 `PARTIAL view`면 남은 쪽을 마저 읽는다.
- 긴 출력은 파일로 보내 필요한 곳을 읽는다.

## 도구를 쓴다

| 일 | 의존하는 것 |
|---|---|
| 정의, 참조, 구현, 호출 관계 찾기 | 언어 서버(LSP 도구). 글자 찾기가 아니라 심볼로 찾는다 |
| 포맷 | 프로젝트의 포매터. 손으로 맞추지 않는다 |
| 이름 바꾸기, 코드 옮기기 | `qef:refactor` |
| 의존 방향, 순환, 중복, 쓰지 않는 export | 정적 분석 도구. 판단이 필요 없는 것을 눈으로 세지 않는다 |

도구가 설치되어 있지 않으면 조용히 grep으로 대신하지 않고 설치할지 묻는다.

## 시킨 일 안에서

- 함께 읽다 찾은 같은 원인의 결함은 고치고 보고한다. 범위 밖이면 안을 표시한다.
- 고칠 때는 증상이 아니라 그 결정이 잘못된 계층에서 고친다.
- 바꾸는 동안 잠시 동작하지 않는 상태는 정상이다(`qef:refactor`).

## 보고

코드를 바꾼 뒤의 보고는 턴 끝 보고까지 모두 구조부터 말한다.

- 바뀐 부분을 어느 구조 기준(이 스킬, `qef:model`, `qef:layout`의 질문)에 대조했는지, 어디가 맞고 어디가 어긋나는지를 `파일:줄`과 함께 쓴다. 어긋난 곳이 남았으면 남은 일로 쓴다.
- 테스트 통과 수는 고쳐졌다거나 끝났다는 근거로 쓰지 않는다.
- 테스트는 실패한 것과 돌리지 않은 것만 따로 적는다.
