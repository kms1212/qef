# 요구사항 확정 가이드

staged-dev 1단계에서 읽는다. 결과물은 사용자가 승인한 요구사항 표와 작업 모드다.

## 순서

1. **읽기.** 관련 코드와 프로젝트 문서(아키텍처 문서, ADR, CONTRIBUTING 등)를 읽는다. 읽을 범위가 넓으면 읽기 전용 Explore 에이전트에게 맡기고 요약만 받는다.
2. **의도 파악.** 무엇을 해결하려는지, 누가 쓰는지, 무엇을 보면 성공인지 정리한다. 요청·코드·문서로 알 수 있으면 묻지 않는다. 의도를 모르면 **그 질문 하나만** 먼저 하고 답을 기다린다.
3. **범위 확인.** 서로 독립적인 기능 여러 개가 섞여 있으면 먼저 나누자고 제안하고, 한 번에 하나씩 진행한다.
4. **모드 정하기.** 아래 "작업 모드"를 따른다.
5. **표 작성.** 아래 "필드별 기준"을 따른다.
6. **자체 점검.** 아래 체크리스트를 통과할 때까지 고친다. 사용자에게는 고친 결과만 보여준다.
7. **보여주고 질문하기.** 표, 모드와 그 이유를 보여준다. 사용자가 말한 것과 내가 가정한 것을 나눠 보여준다(가정은 `assumptions`에만). 질문은 아래 "질문 규칙"을 따른다.
8. **승인.** SKILL.md의 승인 규칙을 따른다.

## 작업 모드

| 모드 | 언제 | 요구사항에 꼭 들어갈 것 |
|---|---|---|
| `build` | 기존 코드가 없는 새 프로젝트 | 기능 |
| `extend` | 기존 프로젝트에 기능 추가·수정·버그 수정 | 기능 |
| `refactor` | 외부 동작은 그대로 두고 구조만 바꿈 | 대상 범위, 고친 뒤 성립해야 할 것, 그리고 수용 기준에 "외부 동작이 바뀌지 않는다" |

**외부 동작**의 기준:

| 포함 (바뀌면 extend) | 포함 안 함 (refactor에서 바뀌어도 됨) |
|---|---|
| 공개 인터페이스: API 경로·시그니처, CLI 인자, 설정 키 | 응답 지연, 처리량, 메모리·CPU 사용량 |
| 출력: 값, 형식, 순서, 개수, 오류 응답 | 내부 구조, 내부 함수·모듈 경계 |
| 부수효과: 저장되는 데이터, 외부 호출, 이벤트·메시지 | 내부 로그 |
| 결과 신선도: 결과가 어느 시점의 데이터를 반영하는지 (캐시로 이전 결과가 나갈 수 있으면 변경) | |
| 실행 방식: 동기↔비동기, 재시도·타임아웃 정책, 트랜잭션 경계 | |

지연·자원 사용량이라도 계약(SLA, 문서화된 타임아웃)에 걸려 있으면 포함한다.

- 기능도 바꾸고 구조도 바꾸는 요청이면 둘을 나눠 따로 진행할지 묻는다. 기본값은 동작 변경을 먼저, 리팩터링을 나중에 (리팩터링이 버그를 "현재 동작"으로 고정하지 않게).
- 요청만으로 모드가 정해지지 않으면(예: "성능 개선해줘", "정리해줘") 표를 만들기 전에 사용자와 먼저 정한다. 가능한 모드마다 외부 동작이 바뀌는지, 테스트를 어떻게 하는지 짧게 보여주고 고르게 한다. 모드를 추측해서 표를 만들지 않는다.

## 요구사항과 구조 설계의 경계

요구사항 단계에서는 기술 결정을 하지 않는다. 요구사항이 다 정해지기 전에 내린 기술 결정은, 뒤에 요구사항이 추가되면 흔들린다. 기술 결정은 승인된 요구사항 전체를 보고 구조 설계 단계에서 한다.

| 요구사항 (무엇을) | 구조 설계 (어떻게) |
|---|---|
| 사용자나 호출하는 쪽이 관찰하는 동작 | API 경로, 상태 코드, 요청·응답 필드 이름 |
| 정책: 기한, 한도, 권한, 실패했을 때 사용자가 겪는 일, 기존 데이터를 어떻게 다룰지 | 저장 방식, DB 스키마, 토큰 형식·길이 |
| 사용자가 직접 겪는 방식 (예: 링크를 누름 / 코드를 입력함) | 쓸 모듈·라이브러리, 파일 위치 |
| 결과로서의 품질 (예: DB가 유출돼도 링크를 악용할 수 없음, 1만 건에 2초 이내) | 그 품질을 내는 방법 (예: 해시 저장, 인덱스) |
| | 테스트 도구, 테스트 방식 |

수용 기준도 관찰되는 결과로 쓴다. 예: "403을 돌려준다" 대신 "로그인이 거부되고 '이메일 인증 필요' 안내를 받는다". 상태 코드 같은 세부는 설계가 정하고 design 체크포인트에서 사용자가 확인한다.

예외로, 아래는 구현 세부라도 요구사항에 쓴다. 이미 확정된 제약이라 흔들리지 않는다.
- 사용자가 직접 정한 것 (예: "경로는 /verify로 해줘")
- 외부에서 이미 의존하고 있어 지켜야 하는 계약 (예: 다른 서비스가 호출하는 공개 API의 경로·응답 형식)

## 필드별 기준

| 필드 | 기준 |
|---|---|
| `summary` | 무엇을 왜 하는지 한 문장. 구현 방법은 쓰지 않는다. |
| `functional` | 할 수 있게 되는 것을 쓴다. 해결 방법은 쓰지 않는다 ("경계" 참고). 항목 하나에 기능 하나. |
| `nonFunctional` | 수치와 측정 조건으로 쓴다("p95 200ms 이하, 1만 건 기준"). 수치를 모르면 "현재 대비"로 쓰고 현재 값을 적는다. 해당 없으면 비운다. |
| `acceptanceCriteria` | 아래 "수용 기준 쓰는 법". |
| `outOfScope` | 사용자가 함께 기대할 만한 인접 기능을 적고, 항목마다 빼는 이유를 한 줄 붙인다. |
| `userStatements` | 사용자가 한 말 원문. 처음 요청, 대화 중 사용자가 결정하거나 답한 말을 **고치지 않고** 그대로 인용한다. 요구사항 문구로 옮기며 뜻이 달라졌는지 뒤 단계가 확인하는 기준이 된다. 비어 있으면 안 된다. |
| `rationale` | 요구사항·가정 항목마다 왜 그렇게 정했는지: `{ for: "<항목>", reason: "<이유>", source: "user" \| "assumed" }`. 사용자가 밝힌 이유는 `user`, 내가 기본값을 고른 이유는 `assumed`. 표에 없는 상황이 생기면 뒤 단계가 이 이유로 판단한다. |
| `assumptions` | 기본값으로 정한 동작·정책, 그 값, 다른 선택지. 사용자가 말한 것은 넣지 않는다. 다른 필드에 쓴 구체적인 값(기한, 개수, 화면 문구, 실패했을 때 사용자가 겪는 일 등) 중 사용자가 정하지 않은 것도 모두 여기에 적는다. 그래야 사용자가 무엇이 이미 정해졌고 무엇이 내 추측인지 구분할 수 있다. 기술 결정은 가정으로도 넣지 않는다. |

refactor 모드에서 요구사항은 무엇이 문제인지와 고친 뒤 무엇이 성립해야 하는지만 정한다. 어떤 구조로 고칠지(파일·디렉터리·패키지 배치, 타입 모델링)와 얼마나 바꿀지("가져오는 경로만", "이름만", "타입은 그대로" 같은 바뀌는 방식의 한도)는 정하지 않는다. 바뀌면 안 되는 것은 외부 동작뿐이다. 대상 범위는 구조를 판단할 코드를 가리키고, 그 코드를 쓰는 곳은 설계가 고른 구조에 맞춰 필요한 만큼 바뀐다. 설계가 대안을 만들어 비교한다. 구조 대안을 이 단계에서 사용자에게 묻지 않는다.
성립해야 할 것은 관찰 가능하게 쓴다. 예: "수수료 계산식이 코드베이스에 한 곳에만 있다", "대상 패키지가 `criteria/structure.md`의 경계 규칙을 모두 통과한다", "같은 패키지 안에서 한 이름이 두 뜻으로 쓰이지 않는다".
지금의 구조를 적은 문서(아키텍처 문서의 패키지 표, 의존 그림, 코드 위치 설명 등)는 성립 조건의 기준이 아니다. 그 문서는 구조와 함께 고칠 대상이다. 성립 조건은 `criteria/structure.md`의 구조 규칙, 도메인 개념 모델링 규칙, 패키지·모듈 경계 규칙에 대어 쓴다. 문서에 관해서는 "바뀐 구조와 문서가 맞는다"만 조건으로 둔다.
사용자가 구조를 직접 정했으면("X를 Y로 옮겨", "A와 B를 합쳐") userStatements에 원문을 두고, 그 구조를 목표 구조로 적는다. 사용자가 바뀌는 방식의 한도를 직접 정한 경우도 같다.

## 수용 기준 쓰는 법

형식은 둘 중 하나를 쓴다 (EARS 패턴, Given/When/Then).

| 상황 | 형식 |
|---|---|
| 항상 | `<시스템>은 <결과>한다` |
| 사건이 일어나면 | `<사건>일 때 <시스템>은 <결과>한다` |
| 어떤 상태인 동안 | `<상태>인 동안 <시스템>은 <결과>한다` |
| 잘못된 입력·실패 | `<잘못된 상황>이면 <시스템>은 <대응>한다` |
| 조합 | `<상태>인 동안 <사건>일 때 <시스템>은 <결과>한다` |

- 기준 하나에 동작 하나. 테스트 하나로 확인할 수 있어야 한다.
- 입력·조건·결과를 구체적인 값으로 쓴다. 경계가 있으면 경계값을 쓴다.
- 정상 경로, 오류 경로, 경계(빈 값·0·최대·경계±1)를 모두 넣는다.
- 일어나면 안 되는 것도 쓴다("권한 없는 사용자에게는 데이터가 내려가지 않는다").
- `functional` 항목마다 대응하는 수용 기준이 최소 하나 있다.

예:

| 나쁨 | 좋음 |
|---|---|
| CSV 내보내기가 잘 동작한다 | 상태 필터가 `paid`일 때 내보내기를 누르면 `paid` 주문만 담긴 CSV가 내려온다 |
| 대용량도 빠르게 처리한다 | 주문 10만 건을 내보낼 때 30초 안에 다운로드가 시작된다 |
| 오류를 적절히 처리한다 | 로그인하지 않은 상태로 내보내기를 요청하면 거부되고 로그인 안내를 받으며, 파일은 만들어지지 않는다 |

## 피해야 할 표현

| 표현 | 문제 | 고치는 법 |
|---|---|---|
| 빠르게, 쉽게, 적절히, 사용자 친화적, 깔끔하게 | 주관적이라 검증할 수 없다 | 수치나 구체적 동작으로 |
| 등, 기타, 지원한다, 처리한다, 관리한다 | 범위가 열려 있다 | 목록을 닫거나 동작을 구체적으로 |
| 가능하면, 필요시, 가급적, 원칙적으로 | 빠져나갈 구멍이 된다 | 조건을 명시하거나 지운다 |
| 더 빠르게, 개선한다 | 기준점이 없다 | 기준 값 대비 수치로 |
| 그것, 해당 기능, 위의 것 | 무엇을 가리키는지 모호하다 | 이름으로 |

## 사용자에게 보여주고 묻는 말

사용자는 내가 코드를 읽으며 만든 용어와 번호를 모른다. 질문과 표만 읽고도 무엇을 정하는지 알 수 있게 쓴다.

- 내가 붙인 번호(F3, A1, AC7)나 내부 용어(`extend`, `refactor`, 특성 테스트, 공통부 등)만으로 가리키지 않는다. 내용을 문장으로 쓴다.
- 처음 나오는 용어·약어·코드 식별자는 한 줄로 뜻을 풀어 쓴다. 모드는 이름 옆에 뜻을 붙인다. 예: "`extend` (기존 앱에 기능을 추가하는 작업)"
- 선택지는 구현 방법이 아니라 **사용자나 사용자의 사용자에게 무엇이 달라지는지**로 설명한다. 예: "토큰을 해시로 저장" 대신 "DB가 유출돼도 인증 링크를 악용할 수 없음"
- 질문 하나만 따로 읽어도 답할 수 있어야 한다. 표의 특정 칸을 봐야만 이해되는 질문은 다시 쓴다.

## 질문 규칙

- 코드·문서로 답할 수 있는 것은 묻지 않는다.
- 의도를 모르면 의도 질문 하나만 먼저 한다.
- 그 밖에는 동작·정책을 바꾸는 결정만 묻는다. 기술 결정은 묻지 않는다 (설계 단계의 몫). 한 메시지에 최대 3개, 영향이 큰 것부터.
- 질문마다 기본값과 그 이유를 붙인다. 가능하면 선택지로 묻는다.
- 답이 없으면 표를 쓸 수 없는 질문은 표보다 먼저 묻는다. 기본값으로 표를 쓸 수 있으면 표와 함께 묻는다. 어느 쪽이든 승인 전에는 진행하지 않는다.

## 자체 점검

표를 보여주기 전에 확인한다.

- [ ] `functional` 항목마다 대응하는 수용 기준이 있다.
- [ ] 수용 기준마다 동작 하나, 구체적인 입력·조건·결과가 있다.
- [ ] 정상·오류·경계 경로가 모두 있다.
- [ ] "피해야 할 표현"이 없다.
- [ ] 항목끼리, 그리고 `outOfScope`와 모순이 없다.
- [ ] 요청에 없는 기능을 넣지 않았다.
- [ ] 기술 결정이 없다 (사용자가 정한 것, 외부 계약은 예외).
- [ ] 이런 기능에 흔히 필요한 정책이 정해졌거나 질문에 올라 있다: 실패했을 때 사용자가 겪는 일, 권한, 기존 데이터·기존 사용자, 기한·한도, 같은 요청이 겹칠 때.
- [ ] 가정은 `assumptions`에 있다. 다른 필드에 쓴 구체적인 값 중 사용자가 정하지 않은 것도 빠짐없이 있다.
- [ ] 질문과 표에 설명 없는 내부 번호·용어가 없다. 선택지는 사용자에게 무엇이 달라지는지로 설명했다.
- [ ] refactor면 "외부 동작이 바뀌지 않는다"와 관찰 가능한 성립 조건이 있다. 사용자가 정하지 않은 구조 배치나 바뀌는 방식의 한도가 없다.
