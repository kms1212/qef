# 단위 테스트 기준

근거: Kent Beck, Test Desiderata. 테스트 작성, 테스트 보완(이의 판정), 테스트 지적 반영이 모두 이 기준을 쓴다.

## 구현에 묶인 테스트의 신호 (리팩터링만 해도 깨진다)

- private 함수나 내부 상태에 직접 접근한다.
- 같은 코드베이스의 내부 모듈이 몇 번, 어떤 순서로 호출됐는지 검증한다.
- 함수 추출이나 이름 변경만으로 깨진다.

## 검증이 약한 테스트의 신호 (버그가 있어도 통과한다)

- 단언이 없거나 "에러가 안 나면 통과"다.
- 결과의 일부만 확인해서 틀린 값도 통과한다.
- 기대값을 구현과 같은 로직으로 계산한다.
- 내용을 확인하지 않은 스냅샷을 기대값으로 쓴다.

판정 규칙: "이 테스트는 어떤 버그를 잡는가?"에 한 문장으로 답할 수 없으면 쓰지 마라. 기대값은 리터럴로 적어라.

## 케이스 고르기

- 동등 분할: 입력을 같은 처리 경로를 타는 구간으로 나누고 구간마다 대표값 하나를 고른다. 오류 구간도 하나씩 넣는다.
- 경계값: 경계마다 경계값, 경계−1, 경계+1을 넣는다. 예: "1~100 허용"이면 0, 1, 50, 100, 101.
- 같은 구간의 대표값을 여러 개 고르면 중복이다. 하나만 남긴다.

## 테스트 하나에 동작 하나

- 이름은 "<조건>일 때 <결과>" 형식으로 쓴다.
- 준비 → 실행 → 단언 순서로 쓰고, 실행은 한 번만 한다.
- 실패하면 무엇이 기대와 달랐는지 메시지로 보이게 한다.

## 항상 같은 결과

- 현재 시각은 고정하거나 주입하고, 난수는 시드를 고정한다.
- 파일은 임시 디렉터리를 쓰고, 네트워크는 가짜로 대체한다.
- 테스트끼리 상태를 공유하지 않는다. 실행 순서가 바뀌어도 결과가 같아야 한다.

## mock 범위

- 허용: 외부 API, DB, 파일 시스템, 시계, 난수
- 금지: 같은 코드베이스의 내부 모듈 (실제 객체를 쓴다)
- mock 설정이 테스트 본문보다 길면 과하다.

## 수용 기준 추적

수용 기준마다 그것을 검증하는 테스트가 최소 하나 있어야 한다. 테스트 이름이나 주석에 어느 수용 기준인지 표시한다.

## 모드별 목표

- build, extend: 인터페이스대로 동작을 검증한다. 구현은 쓰지 않는다. 테스트는 지금 실패해야 정상이다. TDD 스킬은 "실패하는 테스트 작성·실패 확인"까지만 쓴다.
- refactor: 현재 동작을 고정하는 테스트(특성 테스트)를 쓴다. 지금 코드에서 통과해야 한다. 바뀌지 않는 공개 동작만 검증하고, 목표 구조의 내부를 검증하지 않는다. 구현 코드는 수정하지 않는다. TDD 스킬은 "리팩터 전에 동작을 고정하는 안전망 테스트를 갖춘다"는 관점으로만 쓴다.
