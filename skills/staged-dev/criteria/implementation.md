# 구현 기준

구현, 구조 보완, 테스트 실패 수정, 지적 반영을 맡은 서브에이전트가 읽는다.

## 기준

- 관례(이름 짓기, 오류 처리 방식, 폴더 구조 등)는 전역 관례 문서가 있으면 그것을 따르고, 없으면 주변 코드의 관례를 따른다.
- 테스트를 통과시키는 데 필요한 것만 만든다. 지금 필요 없는 일반화는 하지 않는다.
- 새 의존성은 설계에 적힌 것(컴포넌트 reuse.candidate, adoptedDependencies 포함)만 추가한다.
- 파일은 설계의 fileTree대로 만들고, 파일마다 fileTree에 적힌 책임만 넣는다.

## 모드별 목표

- build, extend: 설계대로 구현한다. 이미 작성된 테스트를 통과시키는 것이 목표다. TDD 스킬은 "최소 구현으로 통과 → 리팩터" 부분만 쓴다.
- refactor: 설계의 목표 구조로 바꾼다. 이미 통과하는 테스트는 계속 통과해야 하고, 외부에서 관찰되는 동작은 바꾸지 않는다. 설계의 steps 순서대로 진행하고 단계마다 설계의 testCommand로 테스트를 돌린다. TDD 스킬은 "리팩터" 부분만 쓴다.

## 테스트는 고치지 않는다

테스트 파일은 수정·건너뛰기·삭제하지 않는다 (mod도 구현 단계에서 테스트 파일 쓰기를 막는다). 테스트가 요구사항과 어긋난다고 판단되면 그 테스트에 맞춰 구현하지 말고 보고의 testDisputes에 적는다. 이의와 무관한 부분은 그대로 진행한다.

- 인터페이스 변경이나 중복 코드 삭제 때문에 테스트를 바꾸거나 지워야 할 때도 testDisputes로 올린다.
- 구현이 어렵다는 것은 이의의 근거가 아니다.

## 설계에 없는 파일

fileTree에 없는 파일이 필요하면 만들지 말고 보고의 missingFiles에 경로·역할·책임·이유를 적는다. 그 부분은 이번에 구현하지 않는다. 메인 세션이 구조 규칙으로 판단해 트리에 더하거나 다른 자리를 알려준다.

## 이전 판단이 넘어온 경우

- 테스트 보완 결과가 넘어오면: 수용된 테스트는 고쳐졌다. 기각된 테스트는 맞으니 그 테스트를 통과하도록 구현한다.
- 파일 요청 결정이 넘어오면: added는 트리에 더해졌으니 만들어도 된다. redirected는 useInstead 자리에 구현한다.

## 보고 형식

```json
{
  "changedFiles": ["바꾼 파일"],
  "notes": "바뀐 인터페이스, 다음 단계가 알아야 할 것",
  "testDisputes": [{ "test": "테스트 이름과 파일:줄", "claim": "테스트가 무엇을 잘못 단정하는가", "requirement": "근거가 되는 요구사항·수용 기준 원문" }],
  "missingFiles": [{ "path": "경로", "role": "test | impl | doc | build", "responsibility": "한 문장", "reason": "설계에 있는 파일로는 왜 안 되는지" }],
  "issuesHandled": [{ "id": "I3", "status": "fixed | rejected", "resolution": "무엇을 바꿨는지, 또는 왜 반영하지 않았는지" }],
  "feedbackDecisions": []
}
```

issuesHandled는 검토 지적을 반영하는 단계에서만, feedbackDecisions는 사용자 지적을 반영할 때만 쓴다 (`feedback.md`).
