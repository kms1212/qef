# 설계 기준

## 파일·디렉터리 구조 규칙

경로와 이름만 보고 무엇을 하는 파일인지, 어떤 타입이 어떤 타입을 구현하는지 알 수 있게 한다. 숫자(줄 수) 기준은 두지 않는다. 숫자가 목표가 되면 억지로 쪼갠 구조가 나온다.

- 우선순위: 기술 스택(언어·프레임워크·생태계)의 관례 > (extend) 이 프로젝트만의 관례 > 아래 규칙. 스택 관례가 정하지 않은 부분에만 아래 규칙을 쓴다. 스택 관례가 정하는 것은 배치, 이름, 도구 쓰는 법(파일 이름 규칙, 디렉터리 관례, 프레임워크의 모듈 체계)이다. 도메인 개념을 어떻게 모델링할지는 스택 관례가 정하지 않는다. "이 스택에서는 보통 함수와 상수로 쓴다"는 아래 모델링 규칙을 건너뛸 이유가 아니다.
- 파일 하나에 주요 타입(클래스·인터페이스·트레이트·합 타입 등) 하나. 파일 이름은 스택 관례에 맞춘 타입 이름이다.
- 추상(인터페이스·기반 타입·트레이트·합 타입)과 그 구현의 관계를 그 언어의 모듈 체계 안에서 포함 관계로 드러낸다. 추상이 있는 디렉터리 아래에 구현을 둔다.
- 구현이 실제로 둘 이상일 때만 그 추상을 위한 디렉터리를 만든다. 추상을 위한 빈 디렉터리를 만들지 않는다. 이 규칙은 추상을 위한 디렉터리에만 적용하고, 아래의 개념 디렉터리에는 적용하지 않는다.
- 한 개념을 이루는 파일이 둘 이상이면 그 개념 이름의 디렉터리로 묶는다. 같은 디렉터리에 서로 다른 개념의 파일이 섞이면 "찾아가기"를 통과하지 못한 것으로 본다.
- 주요 타입이 없는 파일(함수·상수만 있는 파일)은 공개 함수들이 한 문장 설명 하나에 들어가야 한다. 들어가지 않으면 하는 일별로 나눈다.
- 새 파일을 기존 파일 옆에 둘 때 그 둘이 한 개념의 부분이면 개념 디렉터리를 만들어 함께 옮긴다. extend 모드에서는 새 파일만 개념 디렉터리에 넣고, 기존 파일은 refactorCandidates에 적는다.
- utils, helpers, misc, common처럼 아무거나 쌓이는 이름을 쓰지 않는다. 이름만 보고 내용을 짐작할 수 있어야 한다.
- 파일마다 아래 네 가지를 통과해야 한다.
  - 한 문장 설명: 하는 일을 "그리고" 없이 한 문장으로 말할 수 있다.
  - 바뀌는 이유: 서로 다른 이유(요구사항의 다른 항목, 다른 외부 시스템)로 같은 파일을 고칠 일이 없다.
  - 이름으로 예측: 트리와 이름만 보고 내용과 타입 관계를 예측할 수 있다.
  - 찾아가기: "X 동작을 바꾸려면 어디를 열지"를 트리만 보고 찾을 수 있다.

## 도메인 개념 모델링 규칙

- 도메인 개념(이 소프트웨어가 다루는 대상과 그 규칙. 예: 종류, 상태, 금액, 식별자, 권한, 일정)은 그 데이터와, 그 데이터에 대한 규칙(검증, 변환, 판정, 표시)을 함께 가진 타입으로 둔다. 같은 개념의 상수, 함수, 스키마가 서로 다른 파일이나 패키지에 흩어져 있으면 통과하지 못한 것이다.
- 같은 질문에 종류마다 다르게 답하는 코드(종류별 분기, 종류를 키로 한 대응표)가 두 곳 이상 있으면, 공통 인터페이스와 종류마다의 구현으로 바꾼다.
- 규칙을 가진 원시 값(문자열, 숫자)은 값 객체나 브랜드 타입으로 감싼다.
- 한 인터페이스의 구현이 여러 패키지에 걸치면, 아래 층은 인터페이스만 갖고, 구현은 위 층이 갖고, 구현을 모으는 일은 조립 지점에서 한다.
- 스키마 라이브러리(zod 등)는 경계에서 들어오는 값을 검증하는 데 쓴다. 개념의 규칙은 타입이 가진다.

## 패키지·모듈 경계 규칙

패키지: 모노레포의 워크스페이스 패키지. 단일 패키지 프로젝트에서는 `src/` 바로 아래 모듈.

- 한 문장: 패키지가 하는 일을 "그리고" 없이 한 문장으로 말할 수 있고, 이름만 보고 그 문장을 짐작할 수 있다.
- 한 곳: 한 도메인 영역의 규칙(상태 목록, 한도, 판정, 분류)은 그 영역을 맡은 패키지 하나에만 있다.
- 한 방향: 패키지 의존은 순환 없이 한 방향이다. 층을 어떻게 나누고 어떤 순서로 둘지는 설계에서 정해 decisions에 적는다. 아래 층은 위 층의 개념을 모른다.
- 계약의 주인: 다른 패키지가 쓰는 타입·스키마는 그 개념을 맡은 패키지가 내보낸다. 저장 방식이 만든 타입(ORM이 생성한 타입, DB enum)이나 전송 형식을 도메인 개념의 계약으로 쓰지 않는다.
- 함께 바뀜: 늘 함께 바뀌는 패키지들, 한 곳에서만 쓰이는 패키지는 따로 둘 이유가 있어야 한다. 한 패키지가 서로 다른 이유로 바뀌면 나눌 후보다.

## 작업 모드별 설계 기준

기존 관례와 분야 모범 사례가 부딪힐 때 무엇을 따를지가 모드마다 다르다. 설계·검토·설계 결정 재검토는 작업 모드의 절만 읽고 "모든 모드 공통"을 함께 따른다.

### build (기존 코드가 없는 새 프로젝트)

- 근거 우선순위: 프로젝트 문서(있으면) > 분야 모범 사례 > 새 결정.

### extend (기존 프로젝트에 기능 추가·수정)

- 근거 우선순위: 프로젝트 문서 > 기존 코드 > 분야 모범 사례 > 새 결정.
- 이번 변경이 건드리는 결정만 decisions에 넣는다.
- 기존 관례와 분야 모범 사례가 다르면 기존 관례를 따르고, deviation에 모범 사례와 무엇이 다른지와 이유를 적는다.
- 프로젝트만의 배치 관례가 위 구조 규칙과 어긋나면 프로젝트 관례를 따르고, 어긋나는 곳을 refactorCandidates에 적는다.
- 이미 여러 책임을 진 기존 파일에 새 책임을 더하지 않는다. 새 책임은 관례에 맞는 새 파일로 분리하고, 기존 파일의 구조 문제는 고치지 말고 refactorCandidates에 적는다.
- 기존 경계를 따른다. 단, 이번 변경이 경계 규칙을 새로 어기게 하지 않는다 (아래 층에 도메인 규칙을 더하거나, 저장 방식의 타입을 새 계약으로 쓰지 않는다). 기존 경계 문제는 refactorCandidates에 적는다.

### refactor (동작은 그대로, 구조만 바꿈)

- 요구사항의 대상 범위와 성립 조건이 설계 기준이다. 사용자가 구조를 직접 정했으면 그 구조도 기준이다. 기존 관례를 바꾸는 것이 목적이므로 "기존 관례 우선"을 적용하지 않는다.
- 지금의 경계(패키지 분할, 디렉터리 배치)는 근거가 아니다. "옮기면 순환이 생긴다"는 지금 분할을 지킬 이유가 아니라 경계가 틀렸다는 신호다.
- 근거 우선순위: 요구사항(성립 조건, 사용자가 정한 구조) > 프로젝트 문서 > 분야 모범 사례 > 새 결정.
- 구조 대안을 둘 이상 만든다. 패키지를 합치거나 나누거나 옮기는 안만이 아니라, 패키지 안을 디렉터리로 나누는 안, 개념을 타입으로 모델링해 푸는 안, 가장 적게 바꾸는 안을 함께 넣는다. 안마다 성립 조건과 구조·경계 규칙을 어떻게 통과하는지, 바뀌는 파일과 import 수를 적어 overview에서 비교한다. 고른 안과 고른 이유는 decisions에 넣는다. 각 안은 비교표에 따로 한 줄로 둔다. 다른 안 속에 섞어 넣은 것은 그 안을 낸 것으로 치지 않는다. 예: 패키지를 합치면서 안을 디렉터리로 나눈 안은 "패키지 안을 디렉터리로 나누는 안"이 아니다. 이 안은 패키지 경계를 그대로 두고 안만 나누는 안이다.
- 외부 동작은 바뀌면 안 된다. 외부 동작: 공개 인터페이스(API 경로·시그니처, CLI 인자, 설정 키), 출력(값·형식·순서·개수·오류 응답), 부수효과(저장 데이터, 외부 호출, 이벤트), 결과 신선도(캐시로 이전 결과가 나가면 변경), 실행 방식(동기/비동기, 재시도·타임아웃, 트랜잭션 경계). 응답 지연·처리량·자원 사용량·내부 구조·내부 로그는 외부 동작이 아니다. 단, SLA나 문서화된 타임아웃에 걸린 지연은 외부 동작이다.
- 변경을 작은 단계로 나눠 steps에 순서대로 적는다. 각 단계가 끝나도 테스트가 통과해야 한다.

### 모든 모드 공통

- 이 작업이 걸친 분야를 판별해 domains에 적는다 (예: 웹 프론트엔드, 백엔드 API, DB 스키마, CLI, 라이브러리, 임베디드, 데이터 파이프라인). 여러 개일 수 있다.
- 분야마다 이런 작업에서 반드시 정해야 할 것을 기존 해결 방법 조사 결과로 확인하고 decisions에 빠짐없이 넣는다.
- 요구사항은 관찰되는 동작과 정책만 정한다. 인터페이스 세부(API 경로, 상태 코드, 필드 이름), 저장 방식, 모듈·라이브러리, 테스트 도구는 설계에서 정하고 decisions에 넣는다. 요구사항에 이런 세부가 적혀 있으면 사용자가 정했거나 외부 계약이므로 그대로 따른다.
- 결정마다 basis와 source를 적는다. 근거가 없으면 basis=new로 적는다. new는 설계 체크포인트에서 사용자 확인을 받는다.
- deviation은 근거가 있는 결정(basis가 new가 아닌 것)에만 적는다. basis=new인 결정에는 deviation을 적지 않는다. 같은 결정이 두 목록에 나오지 않게 하기 위해서다.
- 새로 만들거나 바꾸는 파일 전부를 fileTree에 경로, 역할, 한 줄 책임으로 적는다. 파일·디렉터리 배치는 위 구조 규칙을 따른다.
- 승인된 요구사항·가정과 다른 동작이 구조적으로 더 낫다고 보면, 그 결정을 decisions나 deviation에 묻지 말고 requirementProposals에 적는다(지금 요구사항, 제안, 이유, 영향받는 수용 기준). 요구사항 문장의 적용 범위를 넓히거나 좁혀 해석한 것, 승인된 가정과 다르게 동작할 수 있는 경우(예: 동시 실행 중 일부만 처리됨)도 여기에 해당한다. 설계 본문은 제안을 반영한 안으로 쓴다. 사용자가 받아들이지 않으면 원래 요구사항대로 다시 맞춘다. 검토 지적을 피하려고 요구사항 문장의 적용 범위를 좁히는 제안은, `review-lenses.md`의 "지적을 반영하지 않을 때"를 거쳐 외부 동작을 지키는 안이 없다고 나온 경우에만 낸다.

## 설계 형식 (실행 폴더의 `design/`)

설계는 부분별 파일로 나눠 쓴다. 검토 관점마다 필요한 파일만 읽게 해서, 같은 큰 파일을 여러 서브에이전트가 통째로 읽지 않게 하기 위해서다.

| 파일 | 내용 |
|---|---|
| `design/overview.json` | `{ overview, interfaces, testCommand, integrationTestCommand, priorArtUsed, domains, steps, adoptedDependencies }` |
| `design/components.json` | `{ common: [<컴포넌트>], rest: [<컴포넌트>] }` |
| `design/decisions.json` | `[<결정>]` |
| `design/file-tree.json` | `[<파일>]` |
| `design/boundaries.json` | `[{ "name": "패키지", "oneSentence": "하는 일 한 문장", "exports": ["내보내는 계약"], "from": ["지금 패키지나 파일"] }]` (경계 조사를 띄운 경우만. 이번 작업이 건드리는 패키지의 목표 경계) |
| `design/requirement-proposals.json` | `[<제안>]` (없으면 `[]`) |
| `design/refactor-candidates.json` | `[{ "target": "파일·모듈", "problem": "고치지 않고 보고만 하는 기존 구조 문제" }]` (없으면 `[]`) |

overview.json의 값:
- overview: 구조 개요와 대안 비교 결과
- interfaces: 공통 타입·함수 시그니처·모듈 경계
- testCommand: 단위 테스트 실행 명령 / integrationTestCommand: 통합 테스트 실행 명령 (없으면 생략)
- priorArtUsed: 참고한 기존 해결 방법 / domains: 이 작업이 걸친 분야
- steps: refactor 모드에서 작은 단계로 나눈 변경 순서
- adoptedDependencies: 사용자가 채택한 외부 라이브러리 (처음에는 `[]`)

components.json의 common은 나머지 컴포넌트 둘 이상이 실제로 쓰는 것, 또는 컴포넌트 사이의 계약(타입, 인터페이스)이다. rest는 공통부 위에 올라가는 나머지로, 의존 순서대로 적는다. 컴포넌트 하나:

```json
{
  "name": "컴포넌트 이름",
  "responsibility": "책임 한 문장",
  "files": ["구현 파일 경로"],
  "testFiles": ["테스트 파일 경로"],
  "dependsOn": ["다른 컴포넌트 이름"],
  "reuse": {
    "decision": "reuse | extend | new",
    "candidate": "reuse/extend일 때 쓰는 후보의 location",
    "reason": "new일 때: 조사된 후보 각각을 왜 못 쓰는지"
  }
}
```

결정 하나:

```json
{
  "id": "D1",
  "decision": "결정 문장",
  "basis": "requirement | project-doc | existing-code | domain-practice | new",
  "source": "요구사항 항목, 문서 경로, 파일:줄, 출처 URL (new면 빈 문자열)",
  "deviation": "분야 모범 사례와 다르게 정했으면 무엇이 다르고 왜 그런지 (basis가 new면 생략)"
}
```

파일 하나:

```json
{
  "path": "프로젝트 루트 기준 경로",
  "role": "test | impl | doc | build",
  "responsibility": "\"그리고\" 없는 한 문장",
  "change": "new | modified | moved | removed",
  "component": "이 파일이 속한 컴포넌트 이름"
}
```

moved는 옮겨 간 새 경로에 붙이고 `"from": "<옛 경로>"`를 함께 적는다. 옛 경로는 change=removed인 항목으로 따로 적는다. removed는 이 작업에서 지우는 파일이다. role은 그 파일의 지금 역할로, responsibility는 "없앤다: <옮겨 가는 곳이나 지우는 이유>"로 적는다.

제안 하나:

```json
{
  "id": "P1",
  "current": "지금 요구사항·가정 문장",
  "proposed": "제안하는 동작",
  "reason": "왜 구조적으로 더 나은지",
  "affectedCriteria": ["영향받는 수용 기준 문장"]
}
```

파일의 role은 mod가 단계별 쓰기를 판정하는 기준이다. 테스트 코드와 테스트 데이터는 test, 제품 코드는 impl, 문서는 doc, 빌드 설정·매니페스트는 build로 적는다. 역할이 둘인 파일은 없게 나눈다.
