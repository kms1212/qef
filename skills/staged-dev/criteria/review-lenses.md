# 검토 관점

관점마다 서브에이전트 하나가 맡는다. 관점 프롬프트는 구호 대신 관찰 가능한 신호와 판정 규칙으로 쓴다. 근거: Google eng-practices 리뷰 가이드, refactoring.guru 코드 스멜, Ousterhout『A Philosophy of Software Design』.

검토자는 자기 관점의 절과 "심각도 기준", "지적 형식"을 읽는다. 보고는 자기 관점에 한정하고, 실제 근거가 있는 문제만 보고한다. 없으면 빈 배열이다.

## 요구사항 충족

수용 기준(acceptanceCriteria)마다 그것을 책임지는 컴포넌트(설계 단계) 또는 테스트(구현 단계)를 짝지어라.

- 짝이 없는 수용 기준은 누락으로 지적한다.
- 어떤 요구사항에도 대응하지 않는 컴포넌트·기능은 과잉 구현으로 지적한다. outOfScope에 적힌 것을 구현한 경우도 과잉이다.
- 요구사항·가정·수용 기준과 다른 동작을 고른 결정이 requirementProposals에 없으면 지적한다. deviation이나 overview 안에만 들어 있는 것도 여기에 해당한다. 요구사항을 바꾸는 것 자체는 문제가 아니고, 제안으로 드러나지 않은 것이 문제다.

## 단순성·결합도

추상화는 많아도 적어도 문제다. 아래 신호로 판단하라.

과한 추상화의 신호:
- 구현체가 하나뿐인 인터페이스·팩토리·전략 객체인데, 요구사항에 두 번째 구현이 필요한 시나리오가 없다 (Speculative Generality).
- 받은 인자를 그대로 넘기기만 하는 계층·메서드 (Middle Man, pass-through method).
- 인터페이스가 구현만큼 복잡해서 호출 쪽이 얻는 것이 없다 (얕은 모듈).

구현이 실제로 둘 이상이거나 요구사항이 정한 종류가 둘 이상이면, 그 인터페이스는 과한 추상화가 아니다.

부족한 추상화의 신호:
- 같은 규칙·지식(포맷, 검증 규칙, 상수의 의미)이 두 곳 이상에 있다 (지식 중복).
- 변경 하나에 여러 파일을 조금씩 고쳐야 한다 (Shotgun Surgery).
- 호출 쪽이 내부의 호출 순서, 데이터 형식, 상태를 알아야 쓸 수 있다 (정보 누출).
- 도메인 개념을 문자열·숫자·딕셔너리 같은 원시 타입으로 주고받는다 (Primitive Obsession).
- 종류별 분기나 대응표가 두 곳 이상에 있다 (Switch Statements → 다형성).
- 개념의 데이터와 그 규칙이 다른 파일이나 패키지에 있다 (Data Class, Feature Envy).
- 구현이 둘 이상인데 공통 인터페이스가 없다.

그 밖에: 순환 의존, 한 모듈이 서로 무관한 이유로 자주 바뀌어야 하는 구조 (Divergent Change), 다른 모듈의 내부 데이터에 기대는 코드 (Feature Envy, Inappropriate Intimacy).

판정 규칙:
- 지적에는 "이런 변경·사용이 오면 이런 이유로 문제가 된다"는 구체적 시나리오를 반드시 적어라. 시나리오가 없으면 지적하지 마라.
- 모양만 비슷한 코드 중복은 세 번째에 추상화한다 (Rule of Three). 같은 지식의 중복은 두 번째부터 지적한다.
- "더 깔끔해 보인다"는 근거가 아니다.

재사용 결정 (설계 단계에서만, 조사 보고 `design-research-*.json`과 함께):
- reuse.decision이 new인 컴포넌트마다, 조사된 reusable 후보로 대체할 수 있는데 reason이 약하거나 틀린 곳을 찾아라.
- reuse/extend로 정했는데 후보가 실제로 요구를 못 채우는 곳도 찾아라.

## 정확성·엣지케이스

아래 범주를 차례로 확인하라.
- 입력 경계: 빈 값, 0개·1개·최대, 경계값 ±1, 잘못된 형식, 매우 큰 입력
- 실패 경로: 외부 입출력 실패, 타임아웃, 처리 도중 실패했을 때 남는 상태
- 동시성: 공유 상태, 같은 작업의 중복 실행, 순서 가정
- 자원: 닫히지 않는 자원, 누수
- 오류 처리: 오류를 삼키고 넘어가는 곳

지적마다 구체적인 입력과 "기대 결과 vs 실제 결과"를 적어라.

## 설계 근거

- 설계 본문에 있는데 decisions에 빠진 결정을 찾아라 (컴포넌트 분할, 데이터 형식, 오류 처리 방식, 의존성 선택 등).
- basis가 실제 근거와 맞는지 확인하라. existing-code라면 그 파일:줄이 정말 그 관례를 보여주는지, domain-practice라면 출처가 그 주장을 뒷받침하는지 직접 확인하라.
- 작업 모드의 근거 우선순위를 어긴 결정을 찾아라 (예: extend인데 기존 관례 대신 모범 사례를 따랐고 deviation이 없음).
- 판별된 분야에서 반드시 정해야 할 결정 중 빠진 것을 찾아라.
- basis=new인데 deviation도 적힌 결정을 찾아라. 같은 결정이 사용자에게 두 번 보이게 된다.
- refactor 모드에서 구조 대안이 둘 이상인지, 패키지 안 디렉터리로 나누는 안과 가장 적게 바꾸는 안이 들어 있는지 보라. 고른 안이 다른 안보다 성립 조건을 더 잘 통과한다는 근거가 없으면 지적하라.

## 파일·디렉터리 구조

설계의 fileTree와 파일별 책임을 `structure.md`의 "파일·디렉터리 구조 규칙"에 비춰 검토하라.

- 파일마다 네 가지 기준(한 문장 설명, 바뀌는 이유, 이름으로 예측, 찾아가기)을 실제로 적용해 보고, 통과하지 못하는 파일을 지적하라.
- 스택 관례를 어긴 배치, 아무거나 쌓이는 이름, 구현이 하나뿐인데 만든 디렉터리, 추상과 구현의 포함 관계가 드러나지 않는 배치를 찾아라.
- 이미 여러 책임을 진 기존 파일에 새 책임을 더하는 설계를 찾아라.
- 설계의 컴포넌트와 interfaces에 `structure.md`의 "도메인 개념 모델링 규칙"을 적용하라.
- `boundaries.json`이 있으면 패키지마다 `structure.md`의 "패키지·모듈 경계 규칙"을 적용하라. 파일이 맡은 개념이 다른 패키지에 있어야 하면 지적하라.
- 이번 변경과 무관한 기존 구조 문제는 refactorCandidate를 true로 적어라. refactor 모드에서 요구사항의 대상 범위 안에 있는 것은 무관한 것이 아니다.

## 심각도 기준

- blocker: 요구사항 위반, 데이터 손상, 보안 문제
- major: 구체적 시나리오에서 버그가 나거나, 변경 하나가 여러 곳 수정을 강요하거나, 테스트가 실제 동작을 검증하지 못함. 또는 이번 작업이 만들거나 고친 파일(refactor 모드에서는 요구사항의 대상 범위 전체)이 `structure.md`의 구조 규칙 네 기준이나 "패키지·모듈 경계 규칙"이나 "도메인 개념 모델링 규칙"을 통과하지 못함. 같은 패키지 안에서 같은 이름이 다른 것을 가리키는 경우도 여기에 든다. refactor 모드에서 `structure.md`가 요구하는 구조 대안 중 하나가 비교표에 따로 없는 경우도 여기에 든다.
- minor: 위에 들지 않는 가독성·취향 문제 (자동 반영하지 않는다)

## 지적을 반영하지 않을 때

기준(요구사항의 성립 조건·수용 기준, `criteria/`의 규칙)에 걸린 지적은 기준을 좁혀 피하지 않는다. 외부 동작을 바꾸지 않고 기준을 통과하는 안이 하나라도 있으면 그 안으로 고친다. 그런 안이 없을 때만 rejected로 둔다. resolution에는 찾아본 안과 각각이 안 되는 이유를 적는다. "기준을 좁히자는 제안을 냈다"는 rejected 이유가 아니다.

지적의 일부만 반영하면 issuesHandled에 둘로 나눠 적는다. 반영한 부분은 원래 id로 fixed, 반영하지 않은 부분은 id 뒤에 `-rest`를 붙여 rejected(이 절대로 이유)로 적는다.

## 지적 형식

```json
{
  "issues": [{
    "severity": "blocker | major | minor",
    "where": "파일:줄 또는 설계의 컴포넌트·결정 id",
    "problem": "무엇이 문제인지와 그 시나리오",
    "fix": "어떻게 고칠지",
    "refactorCandidate": false
  }]
}
```

메인 세션은 검토 보고를 모아 실행 기록의 `issues.json`에 옮기며 지적마다 id를 붙인다 (SKILL.md "실행 기록").
