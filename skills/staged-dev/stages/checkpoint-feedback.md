# 체크포인트와 사용자 지적

체크포인트는 요구사항 확정, 구조 설계·검토, 공통부 테스트 실행, 전체 구조 보완, 전체 통합 테스트 뒤에 있다. 제출하면 mod가 승인 대기로 바꾼다. 승인 대기 중에는 프로젝트 파일을 쓸 수 없다 (셸 포함).

## 승인

- 승인은 사용자가 **패널의 승인 버튼을 누르거나 `/qef-approve`를 직접 입력할 때만** 된다. 모델이 대신할 방법은 없다.
- 사용자가 채팅으로 "좋아", "진행해"라고 하면 승인 버튼이나 `/qef-approve`로 승인해 달라고 안내한다. 승인됐다고 말하지 않는다.
- 승인을 묻는 질문이나 버튼을 내 쪽에서 띄우지 않는다 (턴 끝의 다음 단계 상자, AskUserQuestion 등). 그 버튼은 채팅 메시지를 보낼 뿐 승인이 아니라서, 승인 창이 두 개로 보이게 된다. 승인은 패널에만 있다.
- 승인 말고 내용에 대한 질문(기본값 확인, 선택지)은 물어도 된다. 답과 승인을 나눠서 묻는다. 예: "승인할까요?"가 아니라 "이 기본값이 맞나요? 맞으면 패널에서 승인해 주세요."
- "다르게 원하시면 말씀해 주세요"라고 쓰고 진행하지 않는다. "답이 없으면 기본값으로 진행한다"고 쓰지 않는다. 답이 없으면 기다린다.
- 지금 단계와 승인 여부는 매 턴 시스템 프롬프트의 qef 안내와 `qef_status`로 판단한다. 대화에 들어오는 `[qef] 사용자가 승인했다`는 쉬고 있을 때 깨우는 알림일 뿐이고, 단계가 바뀐 뒤 한 턴 늦게 올 수 있다.
- 승인과 함께 온 사용자 말에 요구사항·설계를 바꾸는 내용이 있으면, 이미 승인된 결과를 고치지 않는다. 그 말은 지적으로 분류해(아래 "지적 분류") `feedback.json`에 pending으로 남기고 다음 체크포인트에서 다룬다.

## 보여주기

필드 이름·내부 용어·id·번호를 그대로 보여주지 않고, 사용자가 알아들을 수 있는 말로 풀어 쓴다 (`../requirements.md`의 "사용자에게 보여주고 묻는 말"). 선택지는 사용자에게 무엇이 달라지는지로 설명한다. 각 목록은 항목마다 보여준다. 비어 있는 목록은 건너뛴다.

체크포인트마다 보여줄 것 (위에서부터 차례로):

- 요구사항: `../requirements.md`의 순서 7. 표, 모드와 그 이유, 사용자가 말한 것과 가정한 것을 나눠서.
- 구조 설계:
  - requirementProposals (설계가 제안하는 요구사항 변경): **맨 먼저**, 제안마다 지금 요구사항·제안·이유·영향받는 수용 기준을 보여주고 받아들일지 묻는다. 요구사항을 바꾸자는 제안 자체는 문제가 아니다.
  - refactor 모드면 구조 대안 비교: 안마다 무엇이 바뀌는지, 기준을 어떻게 통과하는지, 고른 안과 이유
  - fileTree: 경로와 파일별 책임. 경로만 보고 역할을 알 수 있는지 확인받는다.
  - 근거 없는 새 결정 (decisions 중 basis=new)
  - 분야 모범 사례와 다르게 정한 결정과 이유 (deviation이 있는 것)
  - 외부 라이브러리 후보: 무엇을 대체하는지와 근거, 채택 여부를 묻는다.
  - 남은 검토 지적: `issues.json`의 stage=design 중 open·rejected (rejected는 반영하지 않은 이유와 함께)
  - 고치지 않고 보고만 하는 기존 구조 문제 (refactorCandidates, status=reported): 따로 refactor 작업으로 할지 묻는다.
- 공통부 테스트 실행: 테스트 결과, 공통부 검토 지적의 처리 결과(fixed·rejected·open), 구현 중 더하거나 다른 자리로 정한 파일 (`file-tree-changes.json`), 외부 라이브러리 후보, 테스트 이의와 판정 (`test-disputes.json`), 보고만 하는 기존 구조 문제.
- 전체 구조 보완: 공통부와 같은 항목을 전체 검토 기준으로. 단위 테스트 결과.
- 전체 통합 테스트: 수용 기준별 통합 테스트 결과, 남은 minor 지적, 테스트 이의와 판정.
- 지적을 반영한 뒤 다시 제출할 때는 지적마다의 해석·판정·변경 (`feedback.json`의 이번 차수)과, 요구사항 보완 때문에 다시 정한 설계 결정(이전 → 이후, 이유)을 함께 보여준다.

## 지적 분류

지적마다 종류를 정하고, 분류와 그 이유를 사용자에게 확인받는다. 애매하면 묻는다.

| 종류 | 무엇 | 처리 |
|---|---|---|
| 요구사항 변경 | 컴포넌트를 새로 만들거나 없애야 함, 또는 공통부 인터페이스를 바꿔야 함 (승인된 설계가 무효가 됨). 예: 새 내보내기 형식 추가 | 사용자에게 `/qef-reset`으로 작업을 끝내 달라고 하고, 요구사항부터 다시 확정해 새로 시작한다 |
| 요구사항 보완 | 기존 컴포넌트 구성과 공통부 인터페이스 안에서 해결됨. 예: 파일명에 날짜 추가, 버튼 문구 변경 | 고친 요구사항 표를 보여주고 동의받은 뒤 type=requirement |
| 설계·코드·테스트 | 그 밖의 지적 | type=design·code·test |
| 라이브러리 채택 | 외부 라이브러리 후보를 쓰기로 함 | type=adopt, library=패키지@버전, text=무엇을 대체 |

- requirementProposals를 받아들이면 요구사항 보완으로, 받아들이지 않으면 type=design, text="원래 요구사항대로: <제안 내용> 취소"로 넣는다.
- original에는 사용자가 한 말을 고치지 않고 그대로 넣는다. text는 내가 정리한 문장이다.
- 요구사항 보완이면 `requirements.json`을 고치고, userStatements에 이번 원문을, rationale에 이번 이유를 더한다.
- 지적은 `feedback.json`에 체크포인트·차수와 함께 남기고 id(U1, U2…)를 붙인다.

## 반영

이번 차수 지적을 한꺼번에 처리한다. 지시는 `../criteria/brief.md` 틀로 쓰고, 판정 서브에이전트는 `criteria/feedback.md`의 해당 절을 읽는다.

### 요구사항 체크포인트

메인 세션이 표를 고쳐 다시 보여주고 `mcp__qef__qef_submit`으로 다시 제출한다.

### 구조 설계 체크포인트

설계에는 아직 코드·테스트가 없으므로 종류와 상관없이 설계 수정으로 반영한다. 1개. 스킬 `superpowers:receiving-code-review`. 읽을 것: 요구사항, 설계(`design/` 전체), `criteria/structure.md`의 작업 모드 절과 "모든 모드 공통", `criteria/feedback.md` 전체, 이번 지적.

지시: apply로 판정한 지적만 반영해 `design/`의 해당 파일을 고쳐 쓴다. requirement는 설계를 보완된 요구사항에 맞게 고치고, decisions 중 이 보완 때문에 근거가 흔들리는 결정을 다시 정한다. adopt는 대상 컴포넌트의 reuse를 바꾼다.

보고: `design-feedback-<차수>.json` (feedbackDecisions, 다시 정한 결정). 그 뒤 fileTree가 바뀌었으면 artifact.files도 새로 넣어 다시 제출한다.

### 공통부·전체 보완·통합 체크포인트

승인 대기 중에는 프로젝트 파일을 쓸 수 없다. 분류를 사용자에게 확인받은 뒤 `mcp__qef__qef_reopen`(reason: 이번 차수 지적 요약, 사용자 원문 포함)으로 승인 대기를 풀고 같은 단계로 돌아간다. 사용자 지적 없이 부르지 않는다. 풀린 동안에는 그 단계의 쓰기 규칙이 적용되고, 패널에 지적 요약이 보이며, 승인 버튼은 없다. 테스트를 고쳐야 하는데 그 단계가 테스트 파일을 쓸 수 없으면(공통부 테스트 실행, 전체 구조 보완) `qef_test_revision` action=enter로 테스트 보완에 들어가 고치고 exit로 돌아온다.

순서:

- requirement가 있으면 먼저 **설계 결정 재검토** 1개. 스킬 `engineering:architecture` (대안 비교와 트레이드오프 정리에만). 읽을 것: 요구사항(보완 반영됨), 설계(`design/` 전체), `criteria/structure.md`의 작업 모드 절과 "모든 모드 공통", 이번 요구사항 보완. 지시: decisions 중 이 보완 때문에 근거가 흔들리거나 맞지 않게 된 결정을 찾아 다시 정한다. 바뀐 결정만 changed에 적고 before에는 원래 결정 문장을 그대로 적는다. 새로 필요해진 결정은 before를 빈 문자열로 둔다. 다시 정한 결과 컴포넌트를 새로 만들거나 없애야 하거나 공통부 인터페이스를 바꿔야 하면 invalidatesDesign=true와 이유를 적는다. 코드는 고치지 않는다.
  보고: `<체크포인트>-revisit-<차수>.json`, 형식 `{ "changed": [{ "before", "after": <결정>, "reason" }], "invalidatesDesign": false, "reason": "" }`. 메인 세션이 `design/decisions.json`를 갱신한다. invalidatesDesign이면 요구사항 변경으로 다룬다.
- test·requirement 지적 → 테스트 반영 1개 (통합 체크포인트가 아니면 테스트 보완에 들어간 상태에서). 스킬 `superpowers:test-driven-development`, `engineering:testing-strategy` (테스트 수정에만). 읽을 것: 요구사항, 설계(`design/` 전체), `criteria/feedback.md`, `criteria/unit-tests.md` (통합 체크포인트면 `criteria/integration-tests.md`도). 지시: apply로 판정한 지적만 테스트에 반영한다. requirement는 바뀐 수용 기준에 맞게 테스트를 고치거나 더한다. 구현 코드는 고치지 않는다.
- adopt 지적 → `implement.md`의 구현과 같은 방식으로 1개, `criteria/feedback.md`의 "라이브러리 채택" 절로. apply된 라이브러리는 `design/overview.json`의 adoptedDependencies에 더한다.
- design·code·requirement 지적 → `implement.md`의 보완과 같은 방식으로 1개, 스킬 `superpowers:receiving-code-review`, `criteria/feedback.md`의 해당 절로. 인터페이스가 바뀌면 notes에 정확히 적게 한다.
- 어느 판정에서든 reason이 "설계 무효화: "로 시작하는 reject가 나오면 멈추고 요구사항 변경으로 다룬다.
- 반영 뒤 `run-tests.md`대로 테스트를 다시 돌리고 `qef_submit`으로 다시 제출한다. 제출하면 승인 대기로 돌아간다.
- 설계 무효화로 멈출 때는 다시 제출하지 않고 사용자에게 `/qef-reset`을 부탁한다.

### 판정 뒤

- reject(요구사항·승인된 설계와 충돌), unclear(해석이 여럿)는 사용자와 다시 이야기한다. 요구사항 변경이면 위 표대로, 지적을 구체화한 것이면 다음 차수로 넣는다.
- 판정은 `feedback.json`의 해당 지적에 붙인다.

## 단계 도중 내가 찾은 질문

검토나 설계에서 사용자에게 물어야 할 것(요구사항 범위, 가정과 다른 동작 등)을 찾아도 바로 묻지 않는다. `feedback.json`에 pending 질문으로 남기고, 다음 체크포인트에서 보여줄 것과 함께 한꺼번에 묻는다. 진행이 멈추지 않게 하기 위해서다. 예외는 답이 없으면 지금 단계를 끝낼 수 없는 질문뿐이다.

## 진행 중에 들어온 지적

- 진행을 멈추지 않는다. 위 표로 분류해 사용자 원문과 함께 `feedback.json`에 pending으로 남기고, 다음 체크포인트에서 이번 차수로 넣는다. 요구사항 보완도 여기에 해당한다.
- 요구사항 변경(설계 무효화)만 예외: 즉시 멈추고 사용자에게 `/qef-reset`을 부탁한 뒤 요구사항부터 다시 한다.
