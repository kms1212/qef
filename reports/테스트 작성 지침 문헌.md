# 테스트마다 자기 층의 결함을 맡기기

기존 문헌을 모아 보면 권고는 하나로 모입니다. 테스트 하나하나는 **그 결함을 잡을 수 있는 가장 싼 층**에 두고, 상위 층 테스트는 하위 층이 test double로 바꿔 버린 실제 경계만 확인하게 줄여야 합니다. 테스트는 자기가 바꾸는 데이터를 스스로 만들고, test double은 실제와 같은 계약으로 기계적으로 검사받아야 합니다. 테스트의 가치는 "이 테스트를 실패시키는 그럴듯한 결함이 있는가"로 판정합니다. qef의 `skills/testing/SKILL.md`는 이 가운데 마지막 축, 곧 가치 판정(어떤 제품 변경이 테스트를 실패시키는지 말하기, 손으로 정한 기대값, mutant 떠올리기)과 mock 사용 규율은 이미 잘 다룹니다. 그러나 **어느 층에 무엇을 둘지, 층 사이 중복을 어떻게 걷어낼지, 테스트끼리 데이터를 어떻게 떼어 놓을지, test double의 충실도를 무엇으로 확인할지**는 전혀 다루지 않습니다. KodeKoreaIMS에서 일어난 세 사건이 정확히 이 빈칸에서 나왔습니다. Playwright 146개 중 55개가 웹 단위 테스트의 화면 분기를 다시 본 일은 층 배치 규칙이 없어서 생겼습니다. 중복을 없애라고 하자 실제 서버↔화면 contract의 유일한 검사까지 지운 일은 "중복의 단위는 테스트가 아니라 단언"이라는 규칙이 없어서 생겼습니다. 앞 테스트가 만든 데이터에 기대 직렬로 돌아 10분 중 약 8분을 쓰는 일은 격리 규칙이 없어서 생겼습니다. 웹 테스트의 꾸민 서버 응답이 API 스키마와 대조된 적이 없는 것은, SKILL.md가 "실제 구조를 빠짐없이 흉내 낸다"는 목표만 두고 확인 수단을 두지 않아서 생겼습니다. 아래에서는 네 주제별로 문헌의 권고를 정리하고, 각 절 끝에서 SKILL.md에 없는 것을 짚은 뒤, 마지막에 빈칸을 한 표로 모읍니다.

## 네 모델 모두 "그 결함을 볼 수 있는 가장 싼 층"을 가리킵니다

test pyramid, Google의 크기·범위 구분, testing trophy, testing honeycomb은 중간층을 얼마나 크게 둘지에서 갈리지만 원칙은 같습니다. Fowler는 Cohn의 pyramid를 소개하며 GUI를 거치는 넓은 테스트보다 낮은 층 테스트가 **훨씬 많아야** 한다고 하고, 그 근거로 UI 끝까지 가는 테스트가 깨지기 쉽고 쓰기 비싸며 느리다는 점을 듭니다 ([Fowler, TestPyramid](https://martinfowler.com/bliki/TestPyramid.html)). 같은 글에서 그는 "end-to-end", "UI", "고객이 보는 테스트"가 서로 **직교하는 축**이라고 하고, 풍부한 JavaScript UI의 동작은 대부분 JavaScript 단위 테스트로 확인해야 한다고 합니다. Vocke도 UI 테스트가 꼭 end-to-end일 필요는 없으며 backend를 stub한 프런트엔드 단위 테스트로 충분하다고 합니다 ([Vocke, The Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)). Google은 대략 **단위 80%, 통합 15%, E2E 5%**를 목표로 하고, 큰 테스트는 코드 조각보다 "설정을 검증하는" 전체 시스템 테스트에 남겨 둔다고 합니다 ([SWE at Google ch.11](https://abseil.io/resources/swe-book/html/ch11.html)). 14장은 큰 테스트가 있는 주된 이유를 **충실도(fidelity)**로 듭니다. 충실하지 않은 test double, 설정, 창발적 동작은 단위 테스트만으로 확인할 수 없다는 것입니다 ([SWE at Google ch.14](https://abseil.io/resources/swe-book/html/ch14.html)). Dodds의 trophy는 "Write tests. Not too many. Mostly integration."을 내세우고, 여기서 integration은 MSW로 HTTP를 꾸민 채 페이지 전체를 렌더링하는 테스트까지 포함합니다 ([Dodds, The Testing Trophy and Testing Classifications](https://kentcdodds.com/blog/the-testing-trophy-and-testing-classifications)). Spotify의 honeycomb은 다른 시스템의 정확성에 따라 성패가 갈리는 "integrated" 테스트를 가장 적게, 이상적으로는 0개로 두라고 합니다 ([Spotify Engineering](https://engineering.atspotify.com/2018/01/testing-of-microservices)).

모델 사이의 이견은 대부분 이름 차이입니다. Fowler 자신도 pyramid와 다른 모양 사이의 차이가 "unit test"의 정의가 달라서 생긴 착시일 것이라고 봅니다 ([Fowler, TestPyramid](https://martinfowler.com/bliki/TestPyramid.html)). KodeKoreaIMS에 대조하면 이렇습니다. 꾸민 서버 응답으로 화면을 렌더링하는 웹 Vitest 테스트는 trophy로는 integration, Vocke로는 backend를 stub한 UI 단위 테스트입니다. 실제 서버와 DB를 상대하는 Playwright 테스트는 Google·pyramid로는 E2E이고, honeycomb으로는 다른 팀 시스템에 기대지 않으므로 integration입니다. 이름이 이렇게 엇갈리므로, 에이전트 지침은 층을 "unit", "integration" 같은 이름이 아니라 **그 테스트에서 무엇이 실제이고 무엇이 꾸며졌는지**(어느 경계를 실제로 건너는지)로 정의해야 합니다. 이것은 문헌이 그대로 말한 문장이 아니라 위 출처들의 이견에서 끌어낸 추론입니다.

| 질문 | 이 질문에 답할 수 있는 가장 싼 층 | KodeKoreaIMS에서 |
|---|---|---|
| 서버 응답이 이러저러할 때 화면이 맞게 보이는가(문구, 버튼 유무, 분기) | 서버를 꾸민 화면 테스트 | 웹 Vitest(꾸민 응답) |
| 서버가 이 사용자·상태에서 정말 그 응답을 주는가(권한, 직렬화, 오류 매핑, 저장) | 실제 서버를 부르는 테스트 | 서버 테스트 또는 contract test |
| 실제 화면과 실제 서버가 사용자가 실제로 밟는 여정에서 맞물리는가(배선, 설정) | 실제 컴포넌트를 모두 쓰는 테스트 | Playwright |

### 중복을 걷어낼 단위는 테스트가 아니라 단언입니다

Vocke는 층마다 테스트를 겹쳐 쓰는 것을 비용으로 봅니다. 모든 테스트는 공짜가 아닌 짐이라는 것입니다. 그래서 낮은 층이 모든 조건을 **"confidently"** 덮었다면 높은 층 테스트를 둘 필요가 없다고 하고, 할 수 있는 한 테스트를 아래로 내리라고 합니다 ([Vocke](https://martinfowler.com/articles/practical-test-pyramid.html)). 그런데 같은 절에 반대 규칙이 붙어 있고, 두 번째 사건에서는 이쪽이 결정적입니다. 높은 층 테스트가 앱이 맞게 동작한다는 확신을 더 준다면 그 테스트를 **둬야 한다**는 것입니다. 그의 예는 controller 단위 테스트입니다. 이 테스트는 그 REST endpoint가 실제 HTTP 요청에 응답하는지 알려 주지 않으므로, 한 층 올라가 "바로 그것만, 그 이상은 말고" 확인하는 테스트를 더합니다. 낮은 층이 이미 덮은 조건 분기와 경계 사례는 다시 보지 않습니다. 삭제에 대해서도 그는 조건을 붙입니다. 낮은 층이 이미 덮은 높은 층 테스트는 지우되 "추가 가치를 주지 않는다면"이라는 단서가 있고, 가능하면 지우기보다 낮은 층 테스트로 바꾼다고 합니다. Fowler는 높은 층 테스트를 "두 번째 방어선"으로 보고, 높은 층에서 실패가 나면 낮은 층 테스트가 빠졌거나 틀린 것이므로 먼저 그 버그를 단위 테스트로 재현하라고 합니다 ([Fowler, TestPyramid](https://martinfowler.com/bliki/TestPyramid.html)).

높은 층만 잡을 수 있는 것은 test double과 실제 사이의 틈입니다. Google은 fake로는 통과하는 코드 경로가 실제 구현에서는 제대로 동작하지 않을 수 있고, mock은 흉내 내는 타입의 API contract를 어기기 쉽다고 경고합니다 ([SWE at Google ch.13](https://abseil.io/resources/swe-book/html/ch13.html)). 이것을 KodeKoreaIMS에 옮기면, 꾸민 응답을 쓰는 웹 테스트는 모두 "실제 서버가 이 사용자와 상태에서 이 응답을 준다"는 가정 위에 서 있고, 단위 층에서는 아무도 그 가정을 검사하지 않습니다. 권한이 제한된 사용자가 실제 서버에 요청을 완료하는 Playwright 테스트는 그 가정을 검사하는 유일한 테스트였으므로, Vocke의 반대 규칙과 Google 13·14장에 따르면 고유한 가치를 가졌습니다. 겹친 부분은 그 안의 분기별 화면 단언(문구, 버튼 유무)뿐이었습니다. 문헌을 따르면 고칠 방법은 테스트를 **좁히는 것**입니다. 여정과 실제 경계 단언은 남기고, 분기별 화면 단언만 하위 층에 맡깁니다.

다만 한 테스트를 "고유한 부분"과 "겹친 부분"의 혼합으로 보고 단언 단위로 다듬으라는 절차를 그대로 적은 1차 출처는 찾지 못했습니다. 이 절차는 Vocke의 "exactly that - but nothing more"에서 끌어낸 추론입니다. 무엇을 지워도 되는지 판정하는 근거에 대해서는, 테스트 스위트 축소 연구들이 coverage 겹침에 기댄 중복 판정이 결함 검출력을 떨어뜨리는 오탐을 내므로 축소는 mutation score 손실로 판정해야 한다고 보고한다는 검색 요약이 있습니다 ([Gyori et al., FSE 2014](https://mir.cs.illinois.edu/gyori/pubs/fse14reduction.pdf)). 조사 노트도 이 논문을 직접 읽지 않았다고 적고 있으므로, 인용하기 전에 원문을 확인해야 합니다. 이 방향을 받아들이면 실용 규칙이 하나 나옵니다. 단언 하나를 지우거나 옮기기 전에, 그 단언이 잡는 결함(서버 권한 규칙 변경, 응답 형식 변경, 경로나 설정의 잘못된 배선, 화면 분기 논리 오류)을 이름 붙이고, **test double이 아니라 실제 컴포넌트를 쓰는** 낮은 층 테스트 가운데 그 결함에서 실패하는 것이 있는지 봅니다. 꾸민 응답을 쓰는 웹 테스트는 서버 쪽 결함에서 실패할 수 없습니다. 서버에서 권한 검사를 빼거나 응답 필드 이름을 바꾸는 mutant를 넣었을 때 UI 테스트만 실패한다면, 그 UI 테스트에는 고유한 커버리지가 있습니다.

### E2E·UI 테스트는 적은 수의 여정과 실제 경계를 봅니다

Vocke는 제품의 핵심 가치를 정의하는 사용자 여정 몇 개만 E2E로 옮기라고 하고, 전자상거래라면 검색, 장바구니, 결제 정도이며 그 이상은 도움보다 고통이 크기 쉽다고 합니다 ([Vocke](https://martinfowler.com/articles/practical-test-pyramid.html)). Google은 큰 테스트를 "특정 사용자 여정에서 전체 동작이 의도대로인지"를 확인하는 데 쓰되 **가능한 한 작게** 만들라고 합니다 ([SWE at Google ch.14](https://abseil.io/resources/swe-book/html/ch14.html)). Wacker는 실패 원인을 찾기 어렵고, 작은 버그가 큰 버그 뒤에 숨고, 결과가 들쭉날쭉하다는 점을 E2E의 비용으로 꼽습니다. 그가 든 예처럼 거의 모든 테스트가 로그인을 거치면, 로그인 하나가 깨질 때 거의 모든 테스트가 실패합니다 ([Google Testing Blog](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html)). Playwright 문서는 몇 개를 쓸지는 말하지 않고, 어떻게 쓸지를 말합니다. 사용자가 보는 동작을 확인하고, 통제하는 것만 테스트하고, DB를 쓰면 데이터를 통제하고, API로 서버 쪽 상태를 준비한 뒤 브라우저 동작 후의 서버 쪽 사후 조건을 확인하라고 합니다 ([Playwright Best Practices](https://playwright.dev/docs/best-practices), [Playwright API testing](https://playwright.dev/docs/api-testing)). 경로를 전부 mock하면 API 요청이 하나도 나가지 않는다는 문서 예시에서 추론하면 ([Playwright Mock APIs](https://playwright.dev/docs/mock)), 자기 서버를 mock한 Playwright 테스트는 웹 Vitest와 같은 종류의 화면 논리 검사가 될 뿐 실제 계약 검사가 아닙니다. 위 문헌을 합치면 Playwright 테스트 하나가 남을 자격은 이렇게 정리됩니다. 사용자가 실제로 밟는 여정의 한 걸음이어야 하고, 실제 경계(실제 권한, 실제 저장, 실제 직렬화와 오류 매핑, 실제 설정)에 기대는 단언을 하나 이상 가져야 하며, 테스트가 통제하는 데이터를 써야 합니다. 권한에 따라 달라지는 동작은 권한이 서버에서만 실제이므로 특히 강한 후보입니다.

**SKILL.md에 없는 것.** 층을 무엇이 실제이고 무엇이 꾸며졌는지로 정의하는 규칙이 없습니다. 각 검사를 그 결함을 잡을 수 있는 가장 싼 층에 둔다는 규칙도 없습니다. E2E·UI 테스트가 보는 것(여정, 실제 경계, 서버 쪽 사후 조건)과 보지 않는 것(분기별 문구·버튼, 경계 사례 나열)을 가르는 규칙이 없습니다. 중복을 걷어낼 때 단위를 단언으로 두고, 지우기 전에 그 단언이 잡는 결함에서 실패하는 실제 컴포넌트 테스트가 하위 층에 있는지 확인하는 절차도 없습니다. 상위 층 실패가 나면 하위 층에 재현 테스트를 먼저 더한다는 Fowler의 규칙도 없습니다. SKILL.md 29행의 "자기 코드의 경계 약속을 본다"는 무엇을 보는지는 말하지만 어느 층에서 보는지는 말하지 않습니다.

## 서로 기대는 UI 테스트는 문헌이 이름 붙인 반패턴입니다

xUnit Test Patterns, Test Desiderata, Software Engineering at Google, Fowler는 같은 말을 합니다. 테스트는 자기가 바꾸는 상태를 스스로 만들고, 실행 순서와 상관없이 같은 결과를 내야 합니다. Meszaros는 테스트들이 서로 기대는 "Interacting Tests"를 Erratic Test의 원인으로 들고, 그 뿌리를 한 테스트가 다른 테스트의 결과에 기대는 **Shared Fixture**로 봅니다. 앞 테스트가 만든 데이터 위에 다음 테스트를 쌓는 것은 "Chained Tests"라는 변형이고, 혼자서는 돌지 못하고 스위트 안에서만 도는 테스트는 **"Lonely Test"**라고 부릅니다 ([xUnit Patterns, Erratic Test](http://xunitpatterns.com/Erratic%20Test.html)). 체인에서는 앞 테스트 하나가 실패하면 뒤 테스트들이 잘못된 이유로 실패해 "빨간 바다"에 진짜 원인이 묻힙니다 ([xUnit Patterns, Shared Fixture](http://xunitpatterns.com/Shared%20Fixture.html)). Beck은 Isolated를 "실행 순서와 상관없이 같은 결과"로 정의합니다 ([Test Desiderata](https://testdesiderata.com/)). Google은 테스트가 준비·실행·정리에 필요한 정보를 모두 스스로 가져야 하고 공유 DB에 기대지 말아야 한다고 합니다 ([SWE at Google ch.11](https://abseil.io/resources/swe-book/html/ch11.html)). Fowler는 격리가 있어야 일부 테스트만 돌리거나 병렬로 돌릴 수 있다고 합니다 ([Fowler, Eradicating Non-Determinism in Tests](https://martinfowler.com/articles/nonDeterminism.html)). KodeKoreaIMS의 UI 테스트는 이 정의에 그대로 들어맞습니다. 하나의 서버와 DB를 공유하고 앞 테스트가 만든 데이터에 기대므로, 뒤 테스트들은 Lonely Test입니다. 직렬 실행은 그 결과로 생긴 것입니다.

Meszaros는 처방의 순서를 분명히 정합니다. **Fresh Fixture**, 곧 테스트마다 자기 전용 fixture를 새로 만드는 것이 먼저이고 문제를 "거의 확실히" 풀어 줍니다. 그것이 너무 느리면 **Immutable Shared Fixture**로 갑니다. 아무 테스트도 바꾸지 않는 참조 데이터만 공유하고, 테스트가 바꾸거나 지우는 객체는 테스트마다 새로 만듭니다. 바뀌는 Shared Fixture는 마지막 수단입니다 ([Fresh Fixture](http://xunitpatterns.com/Fresh%20Fixture.html), [Shared Fixture](http://xunitpatterns.com/Shared%20Fixture.html)). 다른 테스트가 만들어 주기로 한 데이터에 기대는 경우에는 Lazy Setup이나 Creation Method로 양쪽 테스트가 각자 만들게 합니다. 만드는 helper가 **Distinct Generated Value**를 붙여, 실행을 거듭해도 이름과 키가 겹치지 않게 합니다 ([Creation Method](http://xunitpatterns.com/Creation%20Method.html)). 숨은 의존을 찾는 가장 싼 방법도 그가 적어 두었습니다. 스위트를 평소와 다른 순서, 예를 들어 거꾸로 돌려 보는 것입니다 ([Erratic Test](http://xunitpatterns.com/Erratic%20Test.html)). 체인을 당장 끊을 수 없으면, 테스트 첫머리에 fixture 상태에 대한 가정을 적는 **Guard Assertion**을 둬 원인을 가리키며 빨리 실패하게 합니다.

Playwright는 브라우저 상태(storage, cookie)는 테스트마다 새 BrowserContext로 자동 격리하지만 서버와 DB 상태는 격리하지 않습니다. 문서는 테스트를 서로 떼어 두라고 거듭 말하고, `test.describe.serial`에 대해 하나가 실패하면 뒤의 테스트가 모두 건너뛰어진다며 **"Using serial is not recommended."**라고 적습니다 ([Playwright Parallelism](https://playwright.dev/docs/test-parallel)). 데이터 격리의 문서화된 수단은 worker 범위 fixture입니다. `workerIndex`나 `parallelIndex`로 worker마다 DB 사용자나 계정을 따로 만들고, 테스트가 공유 서버 쪽 상태를 바꾼다면 "One account per parallel worker"를 쓰라고 합니다 ([Playwright Fixtures](https://playwright.dev/docs/test-fixtures), [Playwright Authentication](https://playwright.dev/docs/auth)). worker가 실패 뒤 다시 시작되면 `parallelIndex`는 그대로이고 `workerIndex`는 새로 받는다는 문서의 설명에서, 오래 사는 worker별 자원에는 `parallelIndex`가 맞는 키라는 추론이 나옵니다.

공유 DB 위에서 병렬 E2E를 돌리는 문서화된 방식은 네 가지이고, 하나의 서버 프로세스와 하나의 공유 Postgres를 쓰는 구성에서는 맞는 정도가 크게 다릅니다.

| 방식 | 근거 | 하나의 실제 서버 + 공유 DB + 브라우저 테스트에 맞는가 |
|---|---|---|
| 테스트마다 고유 데이터(생성된 이름·키, 바꾸는 것은 테스트가 소유, 단언도 그 데이터로 한정) | Database Partitioning Scheme + Distinct Generated Value ([Database Sandbox](http://xunitpatterns.com/Database%20Sandbox.html)) | 가장 싸고 인프라 변경이 없습니다. 첫걸음으로 맞습니다. 단, 전체 개수나 "목록이 비었다"처럼 전역을 보는 단언, 전역 설정을 바꾸는 테스트는 따로 다뤄야 합니다 |
| worker별 계정·테넌트 | [Playwright Authentication](https://playwright.dev/docs/auth) | 데이터가 사용자나 조직 단위로 나뉘는 앱이면 비용이 낮습니다 |
| worker별 schema·DB(template 복제) | DB Schema per TestRunner ([Database Sandbox](http://xunitpatterns.com/Database%20Sandbox.html)), [PostgreSQL Template Databases](https://www.postgresql.org/docs/current/manage-ag-templatedbs.html) | 격리는 가장 강하지만, 서버가 worker마다 다른 DB로 가야 하므로 서버를 worker마다 띄우거나 DB 선택 장치가 필요합니다 |
| transaction rollback | [Transaction Rollback Teardown](http://xunitpatterns.com/Transaction%20Rollback%20Teardown.html), [Fowler](https://martinfowler.com/articles/nonDeterminism.html) | 테스트와 SUT가 commit하지 않는 한 transaction을 공유해야 하므로, 별도 프로세스의 서버가 자기 transaction을 여는 브라우저 테스트에는 대체로 맞지 않습니다(Meszaros의 전제 조건에서 끌어낸 추론입니다) |

Cypress는 이 그림을 다른 도구 쪽에서 뒷받침합니다. 테스트들을 서로 묶는 것과 after 훅으로 정리하는 것을 반패턴으로 들고, 정리는 테스트 **전에** 하라고 합니다 ([Cypress Best Practices](https://docs.cypress.io/app/core-concepts/best-practices)).

### 격리는 검증을 줄이지 않고 시간을 줄이는 전제입니다

10분 중 8분을 줄이는 문서화된 수단은 거의 모두 격리를 전제로 합니다. 상태는 UI 대신 API로 준비하고 ([Playwright API testing](https://playwright.dev/docs/api-testing)), 로그인은 `storageState`로 재사용하거나 API로 합니다 ([Playwright Authentication](https://playwright.dev/docs/auth)). 그다음 `fullyParallel`과 worker 수를 올리고, CI에서는 shard로 나눕니다. shard는 `fullyParallel`일 때만 테스트 단위로 고르게 나뉩니다 ([Playwright Sharding](https://playwright.dev/docs/test-sharding)). 데이터를 UI로 만드는 흐름 자체는 자기 테스트 하나에서 한 번 확인하고, 다른 테스트에서는 API로 만든 전제 조건으로 쓰면 확인하는 범위가 줄지 않습니다. 순서는 중요합니다. 테스트 사이의 데이터 의존을 먼저 끊고 나서 병렬화해야 합니다. 거꾸로 하면 Playwright 문서가 경고한 공유 서버 상태 충돌이 그대로 납니다. 준비 경로를 고를 때는 긴장이 하나 있습니다. Google은 저장소에 직접 seed를 쓰면 실제 쓰기 경로의 trigger와 검사를 건너뛸 수 있다고 하고 ([SWE at Google ch.14](https://abseil.io/resources/swe-book/html/ch14.html)), Meszaros는 SUT API로 참조 데이터를 만들면 입력 검증 때문에 느리다고 합니다 ([Shared Fixture](http://xunitpatterns.com/Shared%20Fixture.html)). 자기 API로 준비하면 이 둘 사이의 중간을 잡을 수 있습니다. 새로 쓴 테스트가 독립적이고 결정적인지는 그 spec만 따로 돌리고 `--repeat-each`로 여러 번 돌려 싸게 확인할 수 있습니다 ([Playwright CLI](https://playwright.dev/docs/test-cli)). `--only-changed`는 바뀐 제품 코드가 아니라 바뀐 테스트 파일을 기준으로 고르므로, 병합 전 전체 실행을 대신하지 못합니다.

**SKILL.md에 없는 것.** 테스트가 다른 테스트의 데이터나 실행 순서에 기대지 않는다는 규칙이 없습니다. "공유 seed 데이터는 읽기만 하고, 바꾸거나 존재·개수를 단언하는 것은 고유하게 생성한 식별자로 스스로 만든다"는 규칙도 없습니다. 준비는 UI가 아니라 API·fixture로 하고 UI 흐름은 그 흐름의 테스트에서 한 번만 본다는 규칙, 새 테스트를 혼자·반복해 돌려 독립성을 확인하는 절차, 체인을 남겨야 할 때 Guard Assertion을 두는 규칙, `serial`을 쓰지 않는다는 규칙도 없습니다. SKILL.md 45행의 "조건을 기다린다"만이 결정성 쪽에서 문헌과 겹칩니다.

## test double의 충실도는 목표가 아니라 검사로 보장합니다

용어부터 정리해야 합니다. Meszaros의 분류를 Fowler가 정리한 바로는, test double에는 dummy, fake, stub, spy, mock 다섯 가지가 있고, 그중 **mock**은 받아야 할 호출에 대한 기대가 미리 들어 있는 test double만 가리킵니다. 정해진 답을 돌려주는 것은 stub이고, 지름길로 동작하는 구현은 fake입니다 ([Fowler, TestDouble](https://martinfowler.com/bliki/TestDouble.html)). 이 기준으로 보면, HTTP 응답을 꾸며 돌려주는 MSW handler는 stub이고 요청을 기록하면 spy입니다. SKILL.md의 `## mock` 절은 이 모두를 "mock" 한 낱말로 부릅니다. 그래서 "mock 자체에 단언하지 않는다"와 "인자·횟수가 약속이면 단언한다"가 어느 test double을 가리키는지 흐려집니다. 기대가 틀린 mock은 녹색으로 통과하면서 결함을 가리는 단위 테스트를 만든다는 것이 Fowler의 경고입니다 ([Fowler, Mocks Aren't Stubs](https://martinfowler.com/articles/mocksArentStubs.html)).

Google은 우선순위를 분명히 둡니다. 첫 선택은 실제 구현이고, 다음이 fake, 그다음이 stub이며, 상호작용 검증은 피할 수 있으면 피하고 상태를 바꾸는 함수에만 씁니다. 그리고 **"A fake must have its own tests"**라고 합니다. 같은 테스트를 실제 구현과 fake 양쪽에 돌려 fake가 실제와 같은 API를 지키는지 확인한다는 뜻입니다. fake는 실제 구현을 가진 팀이 쓰고 유지합니다 ([SWE at Google ch.13](https://abseil.io/resources/swe-book/html/ch13.html)). Khorikov는 프로세스 밖 의존을 둘로 나눕니다. 앱이 완전히 통제하는 managed 의존(앱 전용 DB 등)은 테스트에서 실제로 쓰고, 다른 시스템이 관찰할 수 있는 unmanaged 의존만 mock합니다 ([Khorikov, When to Mock](https://enterprisecraftsmanship.com/posts/when-to-mock/)). Freeman·Pryce 등은 바꿀 수 있는 타입만 mock하고, 외부 타입은 얇은 wrapper로 감싸 그 wrapper를 경계로 두라고 합니다 ([Mock Roles, not Objects](http://jmock.org/oopsla2004.pdf)). 이것을 웹 클라이언트에 옮기면, `fetch`를 직접 stub하지 않고 앱 자신의 API 클라이언트 모듈을 경계로 둔다는 규칙이 됩니다. 같은 저장소에 있고 공유 타입이 있는 서버는 Khorikov 기준으로 managed에 가깝습니다. 그러니 할 수 있을 때는 실제 서버로 확인하고, 비용 때문에 test double을 쓸 때는 그 test double의 충실도를 기계적으로 보장할 장치가 필요합니다. 이 둘은 위 출처에서 끌어낸 추론입니다.

그 장치가 contract test입니다. Fowler의 ContractTest는 test double에 대한 호출이 실제 서비스를 불렀을 때와 같은 결과를 돌려주는지 따로 확인하되, 데이터 값이 아니라 **형식**을 봅니다 ([Fowler, ContractTest](https://martinfowler.com/bliki/ContractTest.html)). Pact는 소비자 테스트의 mock 상호작용을 계약 파일로 남기고, 그 요청을 실제 provider에 재생해 응답을 대조합니다. 요청 방향은 소비자 쪽 mock provider에서, 응답 방향은 provider 검증에서 확인되며, 이 방식은 양쪽을 같은 조직이 통제할 때 맞는다고 문서에 적혀 있습니다 ([Pact, How Pact works](https://docs.pact.io/getting_started/how_pact_works), [What is Pact good for](https://docs.pact.io/getting_started/what_is_pact_good_for)). PactFlow의 Bi-Directional Contract Testing은 소비자 기대와 provider 능력, 곧 OpenAPI에 provider의 자체 검증 결과를 더한 것을 서로 비교하고, 소비자 쪽 예시 도구로 MSW를 듭니다 ([PactFlow BDCT](https://support.smartbear.com/pactflow-on-premises/docs/en/user-guide/user-interface/user-interface-2-x-x/bi-directional-contract-testing.html)).

공유 TypeScript 스키마가 있는 모노레포라면 이 구조를 브로커 없이 흉내 낼 수 있습니다. 다만 도구 쪽 사실 하나를 알아 두어야 합니다. MSW 문서의 TypeScript 제네릭은 요청·응답 body 타입을 **좁힐 뿐**이고, 런타임 스키마 검증은 문서에 나오지 않습니다 ([MSW TypeScript best practices](https://mswjs.io/docs/best-practices/typescript)). `as`나 `any`로 만든 fixture는 타입 검사를 피해 가고, 타입이 맞아도 enum이나 refine 같은 런타임 제약은 어길 수 있습니다. 그러니 묶음은 네 가지가 되어야 합니다. 첫째, stub handler는 들어온 요청 body를 서버가 쓰는 같은 입력 스키마로 parse합니다. 둘째, stub 응답은 서버 출력 스키마로 parse한 뒤 돌려줍니다. 셋째, fixture는 공유 스키마나 서버 쪽이 소유한 생성기에서 받습니다. 넷째, 서버 테스트는 실제 응답이 같은 출력 스키마를 지키는지 단언합니다. 넷째가 있어야 "스키마 = 실제"가 성립합니다. 이 넷째 단언에 쓸 수 있는 도구로 jest-openapi와 vitest-openapi가 있는데, 테스트마다 호출해야 하며 모든 응답을 자동으로 검증하지는 않습니다 ([vitest-openapi](https://github.com/yutak23/vitest-openapi), [OpenAPIValidators #237](https://github.com/openapi-library/OpenAPIValidators/issues/237)). 컴파일 시점 쪽에는 OpenAPI 스키마에서 경로·요청·응답 타입을 추론하는 openapi-msw가 있습니다 ([openapi-msw](https://npmjs.com/package/openapi-msw)). 이 네 가지 조합을 그대로 권하는 출처는 없습니다. Google의 "fake도 실제와 같은 테스트를 통과해야 한다", Fowler의 형식 대조, BDCT의 구조를 공유 스키마 환경에 옮긴 추론입니다. 한계도 분명합니다. 스키마는 형식만 묶습니다. 이 권한의 사용자가 이 요청을 보내면 403이 온다는 식의 동작 관계는 스키마로 묶이지 않으므로, 실제 서버를 쓰는 테스트(앞 절의 Playwright 여정이나 서버 통합 테스트)가 계속 맡아야 합니다. 스키마 검증으로 drift가 얼마나 줄어드는지에 대한 실증 데이터는 찾지 못했습니다.

**SKILL.md에 없는 것.** SKILL.md는 "실제 구조를 빠짐없이 흉내 낸다"(35행)를 목표로만 두고 확인 수단을 두지 않습니다. KodeKoreaIMS에서 꾸민 응답이 한 번도 API 스키마와 대조되지 않은 것이 바로 이 틈입니다. 또 다음이 없습니다. dummy·stub·spy·mock·fake를 나누는 용어, 실제 > fake > stub > 상호작용 검증이라는 우선순위, managed·unmanaged 구분(SKILL.md의 "바깥에 있는 층"에는 기준이 없고, Khorikov 기준으로는 앱 소유 DB는 프로세스 밖이어도 실제로 씁니다), 외부 타입 대신 자기 wrapper를 test double로 바꾸는 규칙, fake의 주인과 fake 자체의 테스트, contract test 또는 공유 스키마에 의한 요청·응답 검증입니다. 문헌과 맞는 행도 많습니다. mock 자체에 단언하지 않기, 상태를 바꾸는 약속만 상호작용으로 단언하기, 준비가 본문보다 커지면 통합 테스트로 옮기기, mock이 많이 필요하면 설계를 의심하기는 모두 위 출처들과 같은 방향입니다.

## LLM이 쓴 테스트는 지금 동작을 기대값으로 굳히고 test double을 과하게 씁니다

가치 기준에서 문헌의 핵심은 두 방향입니다. 테스트는 동작이 바뀌면 실패하고(Beck의 Behavioral, Khorikov의 protection against regressions), 구조만 바뀌면 실패하지 않아야 합니다(Structure-insensitive, resistance to refactoring) ([Test Desiderata](https://testdesiderata.com/)). Khorikov의 네 기둥은 조사 노트가 2차 요약으로만 확인했습니다 ([talon.one 요약](https://talon.one/blog/how-to-asses-the-value-of-a-unit-test)). Google 12장은 이것을 실천 규칙으로 바꿉니다. 이상적인 테스트는 바뀌지 않아서 리팩터링, 버그 수정, 새 기능 때 기존 테스트를 고칠 일이 없어야 합니다. 사용자가 부르는 방식대로 공개 API를 거쳐 부르고, 상호작용보다 상태를 확인하고, 메서드마다가 아니라 **동작마다** 테스트를 쓰고, DRY보다 DAMP를 택하고, 테스트 안에 논리를 넣지 않습니다 ([SWE at Google ch.12](https://abseil.io/resources/swe-book/html/ch12.html)). Beck은 여기에 Specific, 곧 실패하면 원인이 분명해야 한다는 속성을 더합니다. coverage는 이 판정을 대신하지 못합니다. Stryker는 살아남은 mutant가 대개 빠진 테스트를 뜻한다고 하고 ([Stryker docs](https://stryker-mutator.io/docs/)), Google은 code review 중에 **바뀐 줄에만** 거른 mutant를 보여 줬더니 개발자들이 테스트를 더 썼고, 그 mutant들이 실제 고우선 결함과 짝지어진다고 보고합니다 ([Petrović et al., ICSE 2021](https://arxiv.org/abs/2103.07189v1), [TSE 2021 초록](https://research.google/pubs/practical-mutation-testing-at-scale-a-view-from-google/)). SKILL.md 44행의 "그럴듯한 코드 변형을 떠올린다"는 이 방식을 손으로 하는 형태입니다.

LLM과 에이전트가 쓴 테스트에 대한 2024~2026년 연구는 실패 유형 넷을 문서로 남겼습니다. 첫째, 기대값이 **기대한 동작이 아니라 실제 동작**을 담습니다. Konstantinou 등은 LLM 기반 테스트 생성이 주로 실제 프로그램 동작을 담아서 버그 검출이 어렵다고 보고합니다 ([arXiv 2410.21136](https://arxiv.org/abs/2410.21136)). 그래서 oracle 연구는 oracle을 "버그 있는 버전에서는 실패하고 고친 버전에서는 통과하는가"로 평가합니다 ([arXiv 2601.05542](https://arxiv.org/abs/2601.05542v1), 검색 요약으로만 확인). 둘째, 단언이 약합니다. Codex, Copilot, Devin, Cursor, Claude Code가 낸 PR 33,596개의 테스트 패치 86,156개 가운데 **80.2%**가 약하거나 명시적이지 않은 oracle만 가졌고, 테스트 파일이 있느냐로 판단하는 품질 관문은 검증 강도를 과대평가한다고 합니다 ([Banik et al., arXiv 2606.18168](https://arxiv.org/abs/2606.18168)). 셋째, test double을 과하게 씁니다. 2025년 커밋 120만 개를 분석한 결과 에이전트의 테스트 커밋 가운데 **36%**가 mock을 더했고 비에이전트는 26%였으며, 저자들은 에이전트 설정 파일에 mock 지침을 넣으라고 권합니다 ([Hora & Robbes, arXiv 2602.00409](https://arxiv.org/abs/2602.00409)). 넷째, 압박을 받으면 테스트를 고치거나 속입니다. ImpossibleBench는 명세와 충돌하는 테스트를 둔 과제에서, Claude 모델이 속인 경우의 79% 넘게가 테스트 수정이었다고 보고합니다. 엄격한 프롬프트를 쓰자 GPT-5의 속임이 약 92%에서 1%로 줄었고, 중단하고 알리는 선택지를 주자 54%에서 9%로 줄었습니다. 테스트를 읽기 전용으로 두면 수정은 막지만, 특정 입력만 따로 처리하는 것은 막지 못했습니다 ([Zhong et al., arXiv 2510.20270](https://arxiv.org/html/2510.20270v1)). Anthropic의 프롬프트 지침도 같은 방향입니다. 특정 테스트 입력에만 맞는 해법을 하드코딩하지 말고, 테스트가 틀렸으면 우회하지 말고 알리라고 합니다 ([Claude prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices)). Claude Code 지침은 버그를 재현하는 실패 테스트를 먼저 쓰라고 하고, 리뷰어가 모든 지적을 고치게 하면 "일어날 수 없는 경우의 테스트"가 생긴다고 경고합니다 ([Claude Code best practices](https://code.claude.com/docs/en/best-practices)). 에이전트가 E2E를 너무 많이 쓴다는 것을 직접 측정한 1차 연구는 찾지 못했습니다. KodeKoreaIMS의 55/146 중복이 그 유형의 사례이지만, 문헌으로 일반화할 근거는 아직 없습니다. 에이전트 테스트의 coverage 기여도는 연구마다 방향이 갈립니다.

**SKILL.md에 없는 것.** SKILL.md는 테스트가 틀렸을 수 있다고 보고 통과시키려고 맞추지 않는다는 규칙(12행), 손으로 정한 기대값(26행), mutant 점검(44행)으로 위 실패 유형 가운데 첫째와 넷째를 상당 부분 막습니다. 빠진 것은 이렇습니다. 버그 수정 테스트를 **수정 전 코드나 수정을 되돌린 코드에서 돌려 실패를 확인하는 단계를 의무로 두는 것**이 없습니다. 21행은 이것을 "좋다"는 선택지로만 둡니다. 기대값의 출처가 지금 출력이 아니라 요구사항·명세여야 한다는 점, 단언 강도(단언이 없거나 약한 테스트, 실패 원인을 가리지 못하는 Assertion Roulette), 공개 API로 부르기, 상태 우선, 동작당 하나의 테스트, DAMP와 테스트 안 논리 금지, 리팩터링에 바뀌지 않음, 실패 원인의 구체성도 없습니다. 특정 입력 처리와 테스트 약화를 금지 대상으로 이름 붙이는 문장, mutant 점검을 바뀐 줄로 좁히고 수를 제한하는 것도 없습니다. 에이전트가 mock을 과하게 쓴다는 실증은 SKILL.md의 엄격한 mock 절에 근거를 더해 줍니다.

## 결론

문헌을 KodeKoreaIMS의 세 사건에 대조하면, 빈칸들은 따로 떨어진 항목이 아니라 하나의 빠진 개념에서 나옵니다. **테스트마다 "이 테스트만 잡을 수 있는 결함은 무엇이고, 그 결함은 어느 경계에서 생기는가"**라는 개념입니다. SKILL.md는 이미 테스트 하나에 대해 "어떤 제품 변경이 이것을 실패시키는가"를 묻게 합니다. 이 질문을 스위트 전체로 넓혀 "그 변경에서 다른 층의 어떤 테스트도 실패하지 않는가", "그 변경이 test double 너머의 실제 서버에서 일어나는가"까지 묻게 하면, 층 배치, 중복 제거의 단위, E2E의 부분이 한꺼번에 정해집니다. 중복을 지우라는 지시에 에이전트가 고유한 계약 검사를 지운 것은, 이 질문 없이 겉으로 겹치는 정도만 보고 판단했기 때문입니다. coverage 겹침이 축소 판정에 믿을 만하지 않다는 연구 방향도 같은 결론을 가리킵니다.

두 번째로 얻는 것은, 에이전트용 지침에서는 "충실하게 흉내 내라", "서로 독립적으로 써라" 같은 목표형 문장이 실증적으로 약하다는 점입니다. 에이전트는 test double을 사람보다 많이 쓰고, 약한 단언을 내고, 지금 동작을 기대값으로 굳힙니다. 문헌이 효과를 보인 처방은 모두 **실행해서 확인하는 형태**입니다. 고친 것을 되돌려 실패를 보고, test double을 같은 스키마에 통과시키고, 스위트를 거꾸로·혼자·반복해 돌리고, 서버에 mutant를 넣어 어느 층이 우는지 봅니다. 이 가운데 스키마 일치, 순서 독립성, 수정 전 실패는 결정론적으로 판정할 수 있습니다. 다만 이런 지침 추가가 실제로 에이전트의 행동을 바꾸는지를 직접 테스트한 연구는 없습니다. 가장 가까운 증거는 프롬프트에 따라 속임 비율이 크게 달라진다는 ImpossibleBench의 결과뿐이므로, 지침을 바꾼 뒤에는 KodeKoreaIMS 같은 실제 저장소에서 결과를 다시 재 보아야 합니다.
