# 설계 흐름

나중에 SI를 반자동화할 때 쓸 설계 순서다. 아직 스킬에는 넣지 않았다.

2026-10-28 사용자: "객체 설계까지 돌려보니까 알겠다 순서를 객체 설계 -> DB 설계 -> API 설계 이런 식으로 해야겠네", "이거 나중에 SI 자동화할 때 써먹어야지".

## 단계

설계는 단계마다 입력과 규칙을 받아 산출물 하나를 낸다.

| 산출물 | 입력 | 규칙이 있는 곳 |
|---|---|---|
| 객체 설계 | 요구사항(용어집 포함) | `skills/dev/criteria/structure.md` |
| DB 설계 | 요구사항, 객체 설계 | `skills/web/SKILL.md` "데이터베이스 고르기와 설계" |
| API 설계 | 요구사항, 객체 설계 | `skills/web/criteria/web-api.md` |
| UI/UX 설계 | 요구사항 | 없음 |
| 프론트엔드 객체 설계 | 객체 설계, API 설계, UI/UX 설계 | `skills/web/criteria/web-frontend.md` |

## 왜 이 입력인가

- DB와 API는 객체 설계에서 나온다. 둘은 서로에게서 나오지 않으므로 그 사이에는 순서가 없다. 근거: hexagonal architecture에서 DB(persistence adapter)와 API(inbound adapter)는 둘 다 도메인 모델 바깥의 adapter다. Larman『Applying UML and Patterns』의 UP도 도메인 모델을 먼저 세운다.
- API는 요구사항도 받는다. 객체 설계는 무엇이 있는지를 정하고, API의 연산은 유스케이스에서 나온다.
- DB도 요구사항을 받는다. 표의 모양은 객체 설계에서 나오지만, 인덱스·보존·데이터량·동시성 제약은 조회 패턴과 비기능 요구에서 나온다.
- UI/UX는 객체 설계를 기다리지 않는다. 화면에 나오는 개념 이름·상태·종류는 요구사항의 용어집 한 곳을 객체 설계와 함께 가리킨다(DDD ubiquitous language).
- DB나 API를 먼저 세우면 표의 모양이나 전송 형식이 곧 타입이 되어, 동작이 다른 종류가 종류 값과 흩어진 분기로 남는다(2026-10-28 IMS 0.6.0에서 겪음).

## 되돌아가기

뒤 단계에서 객체 설계의 구멍을 찾으면 뒤 단계에서 메우지 않는다. 객체 설계를 고치고, 그 설계에서 나온 산출물을 다시 낸다.
